## 3. 版本号台阶策略（建议 · **不执行**）

发版规则：**只许 `1.2.Z` 每次 +1，不跳号、不退号、不复用已成功发过的 Z**。见 [`版本号发版规则.md`](版本号发版规则.md)。

### 方案 A（推荐 · 省额度）：「先补洞，再一大包」

1. **补洞（不改 versionName）**  
   对 **v1.2.34**（必）、以及核后确认无资产的 **v1.2.32 / v1.2.35**：在 Actions **Re-run failed jobs** / 按规则允许时 `tag -f` 重触发（细则见发版规则「tag 已在、包没出」）。  
   → 目标：历史 tag 都有签名 APK + 私有 Release 资产。
2. **一大包（一次 patch）**  
   以当前 tip（含 G1/G2/G3、#10、#12、a11y、#9、A4；**默认仍不含软 EQ 对外承诺**）走下一次合法 `versionName`：  
   - 本机已是 **`1.2.36`** → 优先用 **v1.2.36** 收掉 §2.1 中 tip 侧全部用户可见项，并在 `版本历史` / Release 说明里**一次写齐**（覆盖原先分散的 36/37/38「占位」叙述，改为「本版合并」）。  
   - 若发版前 tip 又合入必须拆分的内容，再按规则 +1，**不要**为占位数字强行拆三次浪费额度。
3. **软 EQ**  
   E6 勾完后**单独**下一 patch（例如 1.2.37+），文案写清「仅 DEVICE_REJECTED 且用户确认后启用」。

**优点**：少打几次 tag、少烧 Actions 分钟；用户一次升级拿到本晚积压。  
**缺点**：Release 说明较长；回滚粒度粗（可用 `git revert` 单功能补丁再 +1）。

### 方案 B（可选 · 主题台阶）：「三阶对外」

| 台阶 | 建议内容 | 备注 |
| --- | --- | --- |
| 补洞 | 重跑 32/34/35 无包 tag | 同方案 A |
| **v1.2.36** | G1+G2+G3 + #10 + #12 + a11y | 曲库 / 诊断 / 车机掉线 |
| **v1.2.37** | #9 声道平衡 | 听感独立可回滚 |
| **v1.2.38** | A4 文案 | 与占位一致 |
| 其后 | 软 EQ（E6 通过后） | 不与赶工捆 |

**优点**：占位与对外叙事一致、问题好定位。  
**缺点**：多 2～3 次完整 release 流水线，额度紧时不划算。

### 方案 C（不推荐）：每个 commit 一版

违反「省额度」目标；且与现行 patch 节奏不符。

## 4. 额度恢复后操作顺序（清单）

按序做；**任一步红就停，修完再往下，不要并行乱打 tag**。

1. **提 spending limit / 确认额度**  
   GitHub → Settings → Billing / Actions：确认分钟与 artifact 配额可用（历史曾撞过 artifact 500MB；见发版规则排障表）。
2. **核旧 tag 资产**  
   打开 `v1.2.32` / `v1.2.34` / `v1.2.35` 的 Actions run 与 Release：**有无 APK、签名是否齐**。无包 → Re-run（或规则允许的强制重打**同号**），**不要**改成新号「再发一次 1.2.34」。
3. **本地对齐可复现**  
   按 [`可复现构建.md`](可复现构建.md) 核对 JDK / AGP / Gradle；需要时跑 hash 脚本，便于和 CI 产物对照。
4. **真机抽查**  
   用自建 Release 或补出来的 APK，勾 [`真机验证清单.md`](真机验证清单.md) **§5**（优先 R-01/R-02；软 EQ 走 R-03～R-05）。
5. **选定方案 A 或 B**  
   确认 tip、确认 **不**把未通过 E6 的软 EQ 写成「已默认开启」。
6. **跑正式 release**  
   `bash scripts/release.sh <下一合法版本> --verify`（或项目惯用等价命令）。**禁止**手搓 tag 绕过脚本。
7. **核对 Actions**  
   workflow 绿；私有 Release 有各 ABI / universal 资产；签名步骤通过。
8. **更新公共 `latest.json`**  
   确认 `LuckyLearning/Release` 上 `latest.json` 的 `version` 已指向本版（发版规则 § 公共仓库）；`verify-release.sh` 四步链过完。
9. **回写文档**  
   `版本历史.md` 把「main 未发版 / 占位」改成实发版本行；本文件相应项打 ✅；[`规划-下一步.md`](规划-下一步.md) 本晚表状态更新。
10. **（可选）看 CI 提速是否生效**  
    对照 [`spike-CI提速.md`](spike-CI提速.md) 记录本次 wall time。
