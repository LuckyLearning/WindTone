## 一、功能定位与设计原则

悬浮歌词是**唯一能在"离开 App 之后"继续看到歌词**的能力——车机导航页、手机桌面、分屏另一半屏幕。
它与「通知栏/锁屏歌词」是互补关系，不是竞争关系：

| 场景 | 用哪个 |
|---|---|
| 锁屏 / 息屏 | 通知栏歌词（`subtitle` 第二行）——系统级，悬浮窗在锁屏之上不显示 |
| 桌面 / 导航 / 其他 App 之上 | 桌面悬浮歌词 |
| App 内 | 播放页歌词（悬浮窗按设计隐藏，避免重复） |

### 三条不可动摇的设计原则

1. **锁定时零干扰**：默认带 `FLAG_NOT_TOUCHABLE`，手指划过去直接穿透到桌面，绝不误挡导航与桌面操作。
2. **前台不重复**：App 在前台时窗口整体隐藏。例外只有两个——「调整位置」编辑态、开关打开后的 6 秒前台预览。
3. **失败必须自证**：任一环节断掉都要能**不依赖电脑、不依赖 logcat** 地自己看出来（自检 8 项 + 诊断日志 + 设置页状态行 + 开关回退）。

这三条是后续所有改动的前置约束：**任何新功能都不能破坏"锁定态点击穿透"**。这也是为什么本方案**不做**悬浮窗上的播放控制按钮（见 §八）。

## 四、缺口清单（逐条核对代码得出）

### P0 · 正确性与自愈（用户明天就能感知）

#### P0-1 前奏 / 间奏时字幕整体消失（**最影响观感的现存缺陷**）

**现象**：歌曲前奏（还没到第一句）时**什么都没有**；间奏段落若是带时间戳的空行（`[01:20.00]` 单独一行，LRC 里很常见），字幕会**突然消失、下一句才回来**。

**根因**（两处叠加）：
- `LrcParser.kt` L86-89：带时间戳的空文本行**会**生成 `LyricLine(text = "")` 进入 `timestamped`，`indexAt` 完全可能命中它；
- `LyricOverlayBus.Content.visible` 只判 `text.isNotBlank()` → 空行 = `false` → `observeState` 把整个窗口设成 `INVISIBLE`。
- 另外 `indexAt` 返回 `-1`（仍在第一句之前）时，`PlaybackEngine.publishLyricToOverlay` L983 取到 `null.orEmpty()` = 空串，同样隐藏；而"回落到歌名"的分支只覆盖「无歌词 / 无时间轴」的情况，覆盖不到前奏。

**修法**（推荐口径）：
1. 引擎侧维护 `lastNonBlankIndex`：空行 / `index == -1` 时**回溯到最近的非空行**，
   把 `Content` 的 `text` 设为该行内容，并新增 `interlude: Boolean = true`；
2. `prevLine/nextLine` 同样跳过空行（取 `i-1`/`i+1` 方向的最近非空行）；
3. 渲染侧：`interlude = true` 时**当前行也压暗**（视觉上"停在最后一句、变暗"），窗口保持可见、位置不动；
4. 若回溯不到任何非空行（歌曲开头就是空行）→ 回落显示**歌名**（与无歌词路径统一）。

> 为什么不让它"隐藏"？隐藏 = 窗口位置跳变 + 用户以为功能坏了。KTV 与主流播放器的通行做法都是"停在上一句"。

#### P0-2 服务被系统杀掉后不会自愈

**现象**：车机跑长途、或 ROM 省电策略杀进程后，服务没了 → **开着开关却永远不再出现字幕**，直到用户重进 App 或重开开关。

**根因**：`sync()` 只在四个时机被调用 —— App 启动对账、开关切换、自检「重新拉起」、`previewOverlay()`。
播放过程中没有任何重建路径（`START_STICKY` 在 Android 12+ 的后台限制下也不可靠）。

**修法**：在**切歌**与**播放状态变化**两处补一次幂等重建：

```kotlin
// PlaybackEngine（syncCurrentSong 之后 / onIsPlayingChanged 内）
private var lastOverlayReviveAt = 0L
private fun reviveOverlayIfNeeded() {
    if (!prefs.lyricOverlay || !LyricOverlayBridge.canDraw(app)) return
    if (LyricOverlayService.serviceAlive) return
    val now = SystemClock.elapsedRealtime()
    if (now - lastOverlayReviveAt < 30_000L) return   // 防反复失败时高频重试
    lastOverlayReviveAt = now
    LyricOverlayBridge.sync(app, true)
}
```
> 30 秒节流是必须的：ROM 若持续拒绝挂窗，无节流会变成每切一首歌重启一次服务的死循环。

#### P0-3 悬浮歌词逻辑完全不可测（0 项单测）

**现状**：`buildDisplay`（排版组装）、`Content` 去重规则、行数归一（`if (v == 3) 3 else 1`）、`OverlaySnapshot.report()` 的结论分支，**全在 Android 依赖里**，JVM 单测碰不到。
本方案 P0-1 要动内容回落逻辑，**没有测试就直接动是危险的**。

**修法**（先于 P0-1 做，作为其前置）：
1. 新建 `lyrics/OverlayContentResolver.kt`：纯函数
   `resolve(lyrics: Lyrics, positionMs: Long, offsetMs: Int, title: String): Resolved`，
   返回 `Resolved(current, prev, next, interlude)` —— 只依赖 `Lyrics` 数据类，零 Android 依赖；
2. 新建 `lines/OverlayTextComposer.kt`：纯函数
   `compose(resolved, multiLine): List<StyledLine>`（`StyledLine(text, emphasis)`），
   服务侧只负责把 `StyledLine` 转成 `SpannableStringBuilder`；
3. 新增 `test/.../overlay/OverlayContentResolverTest.kt`：覆盖前奏 / 间奏空行 / 最后一行 / 无双语 / 空歌词集 / offset 偏移 等 12~15 项用例。
   目标：单测 **59 → 75+**。

### P1 · 可用性与外观

| # | 缺口 | 现状 | 建议 |
|---|---|---|---|
| P1-1 | **字号不可调** | `OVERLAY_TEXT_SP = 20f` 写死（`LyricOverlayService.kt` L660）。且用 SP 单位会**再乘系统 `fontScale`**：车机或老人模式把系统字号调大后，字幕可能撑出屏幕 | 设置项「悬浮歌词字号」小/中/大（0.85 / 1.0 / 1.2），Prefs 存档位而非裸值；**最终 px 按屏幕宽度夹取上限**（单行不超过屏宽 90%） |

| P1-3 | **暂停行为不可配** | 固定 `alpha = 0.55`（`PAUSED_ALPHA`） | 新增「暂停时：淡出（现状）/ 隐藏」，默认淡出 |

| P1-7 | **灭屏仍在渲染** | 无 `ACTION_SCREEN_OFF` 处理，灭屏后窗口不可见但服务与 200ms tick 照跑 | 监听 `ACTION_SCREEN_OFF/ON`：灭屏时把窗口设 `INVISIBLE` 并暂停字幕更新（内容流仍写 Bus，成本可忽略），亮屏恢复。车机长时间导航时有实际省电收益 |

## 六、关键技术实现要点

### 6.1 内容回落（A2 的核心逻辑）

```kotlin
// lyrics/OverlayContentResolver.kt（新增，纯 Kotlin，无 Android 依赖）
data class Resolved(
    val current: String,
    val prev: String,
    val next: String,
    val interlude: Boolean,   // true = 停在上一句，渲染侧压暗
)

fun resolve(lyrics: Lyrics, positionMs: Long, offsetMs: Int, title: String): Resolved {
    if (lyrics.isEmpty || !lyrics.synced) return Resolved(title, "", "", interlude = true)
    val i = lyrics.indexAt(positionMs + offsetMs)
    val anchor = if (i >= 0 && lyrics.lines[i].text.isNotBlank()) i
    else previousNonBlank(lyrics.lines, if (i < 0) 0 else i)   // 回溯
    if (anchor < 0) return Resolved(title, "", "", interlude = true)
    return Resolved(
        current = lyrics.lines[anchor].text,
        prev = nearestNonBlank(lyrics.lines, anchor, -1),
        next = nearestNonBlank(lyrics.lines, anchor, +1),
        interlude = anchor != i || i < 0,
    )
}
```

> `nearestNonBlank` / `previousNonBlank` 与 `resolve` 同文件，全部纯函数 → 直接进 JVM 单测。

### 6.2 渲染侧（服务）只做"搬运"

```kotlin
// OverlayTextComposer.compose(resolved, multiLine) -> List<StyledLine>
// StyledLine(text, emphasis: Emphasis)   // Emphasis.NORMAL / DIM / DIMMER
// 服务侧：遍历拼 SpannableStringBuilder，按 emphasis 取色
```
好处：颜色/字号/行数这些**外观参数留在服务**（它们依赖 `resources`），**内容与排版决策**进入纯函数层可被测试。

### 6.3 编辑态超时的跨域回传（B4）

服务不能直接改 `PlayerUiState.overlayEditing`（那是播放域的）。链路：

```
LyricOverlayService（60s 无触摸）
  → LyricOverlayBus.requestExitEditing()   // SharedFlow<Unit>，一次性事件
  → PlaybackEngine 收集（init 里）
  → setOverlayEditing(false) → 更新 _player + LyricOverlayBridge.setEditing(false)
  → Bus.editing → 服务退出编辑态、落盘、锁回穿透
```
与现有 `MessageBus`（跨域一次性提示）同一模式，**不新增架构概念**。

### 6.4 新增 Prefs 键（命名沿用现有风格）

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `lyric_overlay_text_scale` | Int | 1（中） | 0=小 1=中 2=大，非法值按 1 |
| `lyric_overlay_bg` | Int | 1（半透明） | 0=无 1=半透明 2=实底 |
| `lyric_overlay_pause_mode` | Int | 0（淡出） | 0=淡出 1=隐藏 |

> 全部走"读时归一"（`if (v == 2) 2 else 1` 这类写法），与 `lyricOverlayLines` 一致，**不用迁移代码**（本项目口径：重装即重置）。

## 七、验收清单

**批次 A**
1. 播放一首**前奏很长**的歌（或手动 seek 到第一句之前）→ 字幕显示歌名，不退化成空白；
2. 播放含**间奏空行**的 LRC → 字幕停在上一句并压暗，**不闪烁消失**；
3. `adb shell am force-stop` 语义等价场景（ROM 杀服务）后切下一首 → 字幕自动恢复；
4. 设置页自检 ⑦ 行显示实际下发内容与 interlude 标记；
5. `testDebugUnitTest` ≥75 项全绿 + `assembleDebug` 通过。

**批次 B**
6. 三档字号在 1080p 手机与车机横屏下都不超出屏宽；
7. 进调整态后放着不动 → 60 秒自动锁回，桌面恢复可穿透；
8. 灭屏 1 分钟后回到桌面 → 字幕立即恢复（不是等下一次歌词跳行）。

**通用**：真机行为项（A2/A3/B4/B6）必须附真机结果，**不能只靠编译通过**——本项目已经因为"编译过了"放过 4 个真机才暴露的缺陷了。

## 八、明确不做

| 项 | 原因 |
|---|---|
| 悬浮窗上的播放控制按钮（暂停/上一首/下一首） | **与原则 1 冲突**：锁定态必须点击穿透；要加按钮就得让窗口吃触摸，桌面操作立刻被挡。播放控制在通知栏与小组件里已有 |
| 悬浮球 / 跟随手势 | 同上，且需要 `GestureDetector` 与窗口拖动争夺事件 |
| 联网歌词搜索、云同步 | 破坏"零网络权限"定位，已多次记录为不做 |
| WebDAV / 用户数据 JSON 导入导出 / 跨版本迁移 | 已拍板否决，不重开 |
| 多显示器支持（P2-3） | 复杂度与收益不成正比，仅记录 |

## 九、待拍板的取舍

1. **间奏时显示什么**？
   - 方案 A（推荐）：停在上一句并**压暗**，窗口位置稳定；
   - 方案 B：显示歌名；
   - 方案 C：什么都不显示（现状）。
2. **字号是否给到"无底板"档**？无底板在亮色壁纸上必然糊（这是已修过的坑），若开放需在设置项里写明"亮色壁纸建议保留底板"。
3. **逐字染色（P2-1）是否值得做**？它是唯一"看得见的差异化"，但要在低端车机上实测帧率后才好承诺；建议排在批次 A/B 落地后再评估。
