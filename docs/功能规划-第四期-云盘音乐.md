# 云盘音乐播放 · 技术方案（第四期）
> **⚠️ 状态：方案已否定（2026-10-14）**——WebDAV 功能已从应用中整体移除（`SongSource.WEBDAV`、`data/webdav`、设置页云盘分组全部删除）。本稿仅作调研存档，不再实施。


> 目标：音乐上传到云盘指定目录 → App 内扫码登录 → 选择目录 → 扫描并播放 → 支持本地缓存。
> **本轮更新（2026-10-13 第二轮调研）**：推翻首轮部分结论，新增 4 条路线对比与推荐。

---

## 零、结论速览（先看这个）

| 路线 | 可行性 | 门槛 | 建议 |
|---|---|---|---|
| **A. 直接用百度网盘官方车机版** | ✅ 已上线，支持比亚迪 | 零开发 | ⭐ **先试这个** |
| **B. 用棉花音乐/拟声等现成播放器** | ✅ 成熟，多网盘+车机 | 零开发 | ⭐ 备选 A |
| **C. 自建 WebDAV 中转（Alist/OpenList）** | ✅ 协议稳定 | 需常开设备/NAS | 有 NAS 才考虑 |
| **D. 自研 App 接百度开放平台** | ⚠️ 基本走不通 | 企业资质+目录隔离 | ❌ **不建议** |
| **E. 自研 App 直连网盘私有接口** | ⚠️ 能跑但违规 | 无 | ❌ 不做 |

**核心结论**：
1. **首轮「版权拦截」的判断需要修正**——不是版权审查，是**平台能力分层**（普通 API 不给流式播放，只给下载）。
2. **真正卡死自研路线的是 2026-06-03 新规**：新创建应用**只能读 `/apps/{appname}` 目录**，你自建的音乐目录 App 根本扫不到。
3. **你的需求已有零开发量的成熟方案**（官方车机版 / 第三方播放器），**建议先试，不必先写代码**。

## 一、首轮结论的修正

### 1.1 「版权拦截」说法不准确（修正）

首轮我写「百度网盘对音频有版权识别会拦截」，这个表述**有偏差且会误导**。准确情况：

| 维度 | 首轮说法 | 实际 |
|---|---|---|
| 性质 | 版权审查，命中即禁播 | **平台能力分层**，普通接口只给下载用途 |
| 对自传文件 | 默认禁用在线播放 | 同样是**能力收敛**，与文件是否合法无关 |
| 判定依据 | 音频指纹 + ID3 + 熵值 | 指纹/元数据确实存在，但**主要机制是接口能力未开放** |

**换句话说**：`dlink` 接口本身是给「下载」用的，不是给「流式播放」用的。要流式播放得走**官方「极速播放」多媒体服务**——那属于「特殊服务」，而**个人应用不支持开通特殊服务**。

### 1.2 真正致命的是这一条（首轮遗漏）

百度网盘开放平台 **2026-07-14** 文档更新：

> 为进一步保障用户网盘数据安全，降低第三方应用误访问、误操作风险，
> **2026年6月3日后在平台创建的应用**，以下接口**仅支持访问 `/apps/{appname}` 目录下的文件**：
> - `/rest/2.0/xpan/file?method=download`
> - `/rest/2.0/xpan/multimedia?method=listall`
> - `/rest/2.0/xpan/file?method=meta`
> - `/rest/2.0/xpan/file?method=move`

**这意味着**：现在新申请的应用，**只能在你网盘里一个被隔离的 `/apps/应用名/` 目录中活动**。
你上传到 `/我的音乐/` 的音乐，App **列不出来、也下载不了**。

> 规避方式：把音乐**重新上传到 `/apps/{appname}/` 下**。
> 但这样你的音乐就被锁进应用私有目录，在网盘 App 里看着别扭、也不方便再整理。

### 1.3 其他两道门槛

- **个人应用能力缩水**：「已创建的个人应用…**只提供网盘基础服务能力，不支持特殊服务的开通及申请**」→ 极速播放（流式）开不了。
- **智能硬件/车机通道不支持个人**：设备管理能力明确「**暂不支持个人应用**」，需企业资质，且要**邮件沟通 1~2 周**（`ext_mars-union@baidu.com`）。
- **平台红线**：禁止「利用个人网盘账号进行企业建站、图床、**搭建网盘迁移工具**等产品行为」——自研第三方网盘客户端有被判定踩线的风险。

> ⚠️ 注：「暂停个人创建应用」这一条在 2026-07-14 的更新日志里已被**删除**，最新文档写的是「完成个人认证后可创建**一个**应用」。所以个人仍能建应用，只是能力受限（见上）。

## 二、你之前问的「为什么自己上传的还被拦」

这是本轮最核心的答疑：

**你上传的文件本身没问题，是「用第三方 App 去读它」这条路径被限制了。**

打个比方：
- 网盘官方 App = 自家门卡，能进所有房间、能开音响；
- 开放平台 API = 给访客的临时卡，**只发到前台（`/apps/xxx`）**，且**不带播放室钥匙**（极速播放未开放）。

所以：
- ✅ **在百度网盘官方 App / 官方车机版里播自己的音乐 → 正常**
- ❌ **自己写 App 通过 API 播 → 拿不到流式地址，且读不到自建目录**

## 三、方案对比（重点）

### 路线 A：百度网盘官方车机版 ⭐ 首选

**实测证据**：百度网盘官网明确列出 ——
> 车载系统×百度网盘，盘中数据车内尽享…***现支持长安、沃尔沃、比亚迪**、吉利领克等车载系统*

且社区反馈：**比亚迪自带应用商店里就能直接下载安装**「百度网盘车机版」。

**能力**（据第三方介绍页整理）：
- 登录后查看网盘全部文件，自动分类
- **直接在线播放网盘云端音乐/视频**（MP3、FLAC、WAV；不支持 APE）
- 大屏适配、**语音操控**（语音搜歌、切歌、暂停）
- 可下载到车机本地做离线
- 与你手机版网盘**实时同步**

**代价**：0 开发量。缺点是与 WindTone 是**两个独立 App**，不能复用你的悬浮歌词、播放队列、车机定制 UI。

**建议**：**先花 10 分钟装上试听**。如果体验够用，第四期云盘功能可以不用做，把精力放在 WindTone 自身的体验上。

---

### 路线 B：现成第三方播放器 ⭐ 备选

调研发现至少 3 款，功能与你的需求**几乎完全重合**：

| App | 云盘支持 | 车机 | 亮点 |
|---|---|---|---|
| **棉花音乐** | 百度网盘、阿里云盘、OneDrive、GoogleDrive、WebDAV、Dropbox | ✅ 车载模式 | 自动刮削封面歌词、无损解码、**桌面悬浮歌词** |
| **拟声** | 阿里云盘、百度云盘、WebDAV | ✅ 车机版通用 | 插件系统、拟物 UI |
| **LightPlayer** | 阿里云盘、百度网盘、WebDAV、NAS | ✅ 车机平板通用 | **桌面歌词、锁屏歌词** |

> **重要价值**：这些 App 存在本身**反证了「云盘播放音乐」在技术上完全可行**，
> 说明存在可用的授权/访问路径（它们大概率是长期运营的开发者账号 + 已获批的能力，
> 或用了 WebDAV 等标准协议通道）。

**棉花音乐**尤其值得注意——它的**桌面悬浮歌词**功能，和你在 WindTone 里刚做的车机悬浮歌词是同一件事。

---

### 路线 C：WebDAV 中转（Alist / OpenList）

**原理**：网盘不提供标准 WebDAV，需要一个「翻译官」把网盘私有接口转成 WebDAV 协议。

```
百度网盘账号 → Alist/OpenList（中间层）→ 对外提供标准 WebDAV → 播放器挂载
```

**关键事实**：
- Alist / OpenList **官方支持百度网盘**（列表、下载、上传、移动、复制全支持）
- 部署方式：Docker / NAS / 常开电脑 / 树莓派
- 对音频**支持在线播放、歌词、字幕**
- WindTone 只需实现一个 **WebDAV 客户端**（协议公开、稳定、无审核风险）

**优点**：协议标准化、不受网盘开放平台审核限制、一次实现可接所有网盘
**缺点**：**需要一台常开设备**（家里 NAS / 软路由 / 云服务器）；车机在外网要访问需做内网穿透

**适用判定**：
- 家里有 NAS 或软路由 → **强烈考虑**
- 没有 → 这条路要额外投入一台设备，性价比低

---

### 路线 D：自研 App 接开放平台 ❌ 不建议

理由已在 §1.3 列全：**目录隔离 + 个人能力受限 + 车机通道要企业资质**。投入产出比极差。

### 路线 E：直连网盘私有接口（逆向）❌ 不做

技术上社区有实现，但违反平台规范、账号有封禁风险，且需要手工维护 Cookie/签名。**明确排除**。

第 3 步：看你有没有常开设备（NAS/软路由）
         ├─ 有 → 走【路线 C】WebDAV：
         │        ① 部署 Alist/OpenList，挂载百度网盘

> 从工程角度，「不写代码就解决问题」永远优于「写一堆代码解决同一个问题」。

## 五、若确定走路线 C（WebDAV），技术要点

### 5.1 对 WindTone 的改动量（比原方案小得多）

复用首轮设计的绝大部分抽象：

```kotlin
enum class SongSource { LOCAL, WEBDAV, CLOUD_BAIDU /*保留，暂不用*/ }

data class Song(
    ...,
    val source: SongSource = SongSource.LOCAL,
    val cloudFileId: String? = null,   // WebDAV 下存 path
    val cloudPath: String? = null,
)

val stableKey: String
    get() = when (source) {
        // ⚠️ LOCAL 分支必须与现有算法完全一致，否则老用户收藏/歌单全失效
        SongSource.LOCAL -> "local:" + (path ?: uri.toString())
        else -> "${source.name.lowercase()}:" + (cloudFileId ?: uri.toString())
    }
```

### 5.2 WebDAV 客户端要点

- **PROPFIND** 列目录（Depth: 1），解析 XML
- **GET** 取文件流，可直接给 ExoPlayer（支持 Range 请求 → 进度条可拖）
- **Basic Auth** 即可，凭证仍用 `EncryptedSharedPreferences` 存
- 建议加 **OkHttp** 依赖（比 `HttpURLConnection` 好处理 Range / 重定向）

### 5.3 目录选择交互

WebDAV 有标准目录树，**可直接复用现有列表 UI**逐级浏览，无需自绘弹层（比百度方案简单）。

### 5.4 缓存

沿用首轮设计：`cacheDir/cloud/webdav/<hash>.<ext>` + Room 索引 + LRU 淘汰，上限默认 2GB。

## 七、附：首轮调研保留内容（架构抽象仍然有效）

首轮设计的**分层抽象**（`CloudAccount` / `CloudSource` / `CloudScanner` / `CloudCacheManager`）
在路线 C 下**依然适用**，只是把 `BaiduCloudSource` 换成 `WebDavSource` 实现：

```kotlin
interface CloudSource {
    val id: String                  // "webdav"
    val displayName: String         // "WebDAV"
    suspend fun startAuth(): AuthSession      // WebDAV 下简化为填地址+账号密码
    suspend fun isAuthorized(): Boolean
    suspend fun listDir(parentId: String): List<CloudEntry>
    suspend fun downloadUrl(fileId: String): String  // 直接返回 url，无需 token 刷新
}
```

**结论**：**架构设计不用推翻，只需替换实现层**。首轮工作没有浪费。

## 八、合规提示

无论走哪条路，**用户授权自己的网盘、访问自己的文件、自己听**都是合规的。红线是：
- ❌ 分享链接解析、全网资源搜索
- ❌ 多人共享一个账号
- ❌ 把云盘当 CDN 对外服务

App 内应在云盘功能处写明：「仅访问你本人授权的文件，数据不出本机」。
