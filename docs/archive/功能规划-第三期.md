# 本地音乐播放器 · 第三期规划（v3.0.0）

主题：**界面样式美化 · 操作易用性优化 · 性能优化**

前两期把「功能有没有」补齐了，这一期解决「好不好用、顺不顺手、快不快」。
所有条目都基于对现有 38 个源文件（8159 行 Kotlin）的逐行审计，不是泛泛而谈。

---

## 一、性能优化

### P1 播放进度与界面状态解耦（本期最大收益）

**问题**：`MusicViewModel.startPositionTicker()` 每 250ms 执行一次
`_player.update { it.copy(positionMs = …, bufferedMs = …, durationMs = …) }`。
`MainScreen` 顶层 `collectAsStateWithLifecycle()` 订阅了 `player`，
于是**每 250ms 整个主界面重组一次**——顶栏、视图标签、列表容器、迷你播放条、
播放页全部重新走一遍 composition。列表里每首歌还要重算
`player.current?.stableKey == song.stableKey`。

**方案**：
- 新增 `PlaybackProgress(positionMs, durationMs, bufferedMs)` 与独立的 `progress: StateFlow`；
- 计时器只更新 `progress`，不再写 `_player`；
- `PlayerUiState` 移除 `positionMs` / `bufferedMs`，只在切歌、seek、播放状态变化时更新；
- 进度以 `State<PlaybackProgress>` 形式**下沉到叶子组件**（进度条、迷你条、歌词面板）读取，
  利用 Compose 的延迟读取，只有真正读它的组件才重组。

**预期**：主界面重组频率从 4 次/秒降到 ≈0；滑动列表时的掉帧明显改善。

### P2 `SharedPreferences` 每 250ms 写盘

`if (pos > 0) prefs.lastPositionMs = pos` 在计时器里，等于每 250ms 触发一次
`apply()`（内部有磁盘写入队列）。改为**每 5 秒或切歌时落一次**。

### P3 拼音转换无缓存

`PinyinIndex.initialOf()` 每次调用都走 `PinyinHelper.toHanyuPinyinStringArray()`。
它被用在 `refreshGroups()` 的 `sortedWith(compareBy { initialOf(it.title) })` 里，
比较次数是 O(n log n)，500 首歌 / 100 个分组 → 近千次汉字解析，且每次切换标签都重算。

**方案**：给单字拼音加 `ConcurrentHashMap` 缓存，给字符串首字母加有上限的结果缓存。

### P4 封面没有位图缓存

`CoverRepository` 只缓存了原始图片**字节**（16MB LRU），
没有缓存解码后的 `Bitmap`。列表每次滑回来都要重新 `decodeScaled`。

**方案**：新增按 `byteCount` 计量的 Bitmap LRU（上限 = 堆内存/8，8~32MB 区间），
key = `stableKey@目标边长`。

### P5 歌单列表 N+1 查询

`refreshPlaylists()` 对每个歌单单独 `withContext(Dispatchers.IO) { songsOf(id) }`，
N 个歌单 = N 次线程切换 + N 次 SQL；同一函数里还重复构建两次 `associateBy` 大 Map。
而它在「加入歌单 / 移除 / 新建 / 重命名」后都会被调用。

**方案**：新增 DAO `allSongs()` 一次取回全部关联行，内存 `groupBy`；Map 只构建一次。

### P6 搜索没有防抖

`setQuery()` 每敲一个键就同步跑一遍
`searchSongs()`（O(n) 过滤 × 每首 2 次拼音查表 + 每次 `refreshLetterIndex()` 的 O(n) 首字母）。

**方案**：输入即时回显，列表过滤延迟 140ms 执行，期间的按键取消上一次任务。

### P7 稳定性注解缺失

`Song`、`LibraryUiState`、`PlayerUiState` 等含 `List` / `Uri` 字段，
Compose 判定为 unstable，导致父级重组时**无法跳过子级**。
这些类全部是「整体 copy 替换」的写法，语义上等价于不可变。

**方案**：标注 `@Immutable`，让强跳过真正生效。

### P8 计时器频率自适应

暂停时仍以 900ms 空转。改为播放中 200ms、暂停 1000ms，
并且只在有控制器的前提下才更新。

### P9 其他

- `formatDuration()` 每次走 `String.format` + `Formatter` 解析，
  列表每行每帧都调用 → 改为手写拼接；
- `applyLibrary()` 在 `_library.update {}`
  的 CAS 闭包里做 `searchSongs()` 重计算，闭包可能被重复执行 → 提到闭包外先算好。

## 二、操作易用性优化

| 编号 | 问题 | 方案 |
|---|---|---|
| U1 | 5 个视图切换用一行 `FilterChip`，小屏拥挤、单手够不到 | 改为底部 `NavigationBar`（图标 + 文字），符合 Android 习惯 |
| U2 | 收藏 / 加入歌单**只能长按**触发，发现性差 | 每行右侧加 `⋮` 更多按钮，长按保留 |
| U3 | 播放页把 13 个操作塞进一个下拉菜单 | 改为底部抽屉，按「音效 / 睡眠 / 速度 / 歌词」分组 |
| U4 | 迷你播放条只是静态展示，进度条不能拖 | 支持拖拽/点击 seek、左右滑切歌、双击播放暂停 |
| U5 | 空态只有一段文字，用户不知道下一步做什么 | 空态加主行动按钮（授予权限 / 导入文件夹 / 去扫描） |
| U6 | 重启后视图标签回到「歌曲」，排序已持久化但视图没有 | 视图标签也持久化 |
| U7 | 封面区只有左右滑切歌 | 补上下滑动调音量（上期遗留项），带音量提示浮层 |
| U8 | 长按、拖拽队列没有触感反馈 | 关键交互加 `HapticFeedback` |
| U9 | Snackbar 与迷你播放条位置冲突 | 移到顶部安全区 |
| U10 | 列表滚动后找不到正在播放的歌 | 列表右侧加「回到当前播放」悬浮按钮 |
| U11 | 触控热区偏小 | 迷你条、列表行统一加大到 ≥48dp |

## 三、界面样式美化

| 编号 | 现状 | 方案 |
|---|---|---|
| V1 | 播放页纯平背景 | 封面主色 → 背景的垂直渐变氛围；封面加阴影 + 播放时呼吸缩放 |
| V2 | 迷你播放条是贴底的直角区块 | 改为浮动圆角卡片（18dp 圆角 + 阴影 + 内嵌细进度条） |
| V3 | 列表行样式零散 | 统一 12dp 圆角卡片、统一选中态、行高与间距统一 |
| V4 | 扫描时是一个转圈 | 骨架屏 + 微光扫过（Shimmer），8 行占位 |
| V5 | 歌词只有颜色区分当前行 | 当前行左侧指示条 + 非当前行缩放层次 + 圆角高亮底 |
| V6 | 空态是一个灰色图标 | Canvas 绘制的唱片插画（渐变底 + 同心纹 + 音符） |
| V7 | 主题只定义了基础色，M3 的 surfaceContainer 系列走默认值，深浅色不协调 | 补全 M3 色板 token 并做种子色微染 |
| V8 | 进度条是默认 `Slider`，看不出缓冲进度 | 自绘细轨道 + 缓冲段 + 拖动放大圆点 thumb + 时间气泡跟随 |
| V9 | 列表切换生硬 | 列表项入场动画（渐显 + 上移） |
| V10 | 分组 / 歌单列表卡片与歌曲列表不统一 | 统一卡片规范，数量用 pill 呈现 |

## 四、验收方式

1. 构建出 `release/本地音乐播放器-v3.0.0-release.apk`；
2. 单元测试保持全绿（歌词解析 28 项）；
3. 真机重点验证：
   - 主界面静止时 CPU 占用明显低于 v2.1（对应 P1/P2/P8）；
   - 快速滚动 1000+ 首歌曲列表不卡顿（对应 P4/P7）；
   - 输入搜索关键词不再逐键卡顿（对应 P6）；
   - 打开歌单标签页迅速出结果（对应 P5）；
   - 重启后停留在上次的视图标签（U6）；
   - 播放页上下滑能调音量、更多菜单变抽屉（U7/U3）。
