> 评审对象：WindTone（包名 `com.luckylearning.windtone`，Kotlin + Jetpack Compose + Media3 ExoPlayer）
> 评审人：架构师 高见远（Gao）
> 评审日期：2026-10-21
> 本文结论均基于实读源码（`app/src/main/java/com/luckylearning/windtone/...`）核对，与正文一并给出文件与行号佐证。

## TL;DR（结论先行，给决策者）

1. **播放内核零改造即可播 http(s) 直链流**：`ExoPlayer` 的 `DefaultMediaSourceFactory` 按 URI scheme 自动选 `DefaultHttpDataSource`，且 `INTERNET`/`ACCESS_NETWORK_STATE` 权限、`LibraryBrowser.looksLikeUri` 的 http scheme 解析均已预埋。把一首歌的 `uri` 换成 `https://...` 就能播，无需改播放引擎。
2. **但「能播」≠「可用」**：远程歌曲没有本地文件，现有的**歌词、封面、曲目元数据、队列/收藏持久化**四条链路会全盘失效或丢数据——这才是改造成本所在。
3. **最大的业务难点是「接哪个源」，不是「能不能播」**：主流网盘官方开放平台对个人应用受限（平台能力分层 + 目录隔离 + 无「极速播放」流式服务），但 WebDAV 中转 / 远程 M3U / 用户自填直链等形态技术门槛低、且更契合 WindTone「数据留在本机」的定位——详见 H 章重新考虑。
4. **推荐落地顺序**：先以「远程 M3U / 用户自填 http 直链」跑通端到端播放做内核零改造验证（阶段 0），再按 Song 模型→持久化→元数据→缓存→具体源 UI 逐层叠加。整体工作量最大的一块是**源接入与 UI**，而非播放内核。

## A. 现有音频播放架构概览

### A.1 主链路（曲库 → 播放 → 输出）

```
[曲库扫描]                       [数据模型]                    [播放内核]
MediaStoreScanner  ┐
FolderScanner     ├─→ MusicRepository.loadLibrary() ─→ List<Song> ─→ PlaybackConnection.toMediaItem(song)
FileScanner       ┘     (合并去重, 短音频过滤)        (uri = stableKey)
                                                                      │
                                                                      ▼
                                              MediaController(MediaLibraryService/PlaybackService)
                                                                      │
                                                                      ▼
                                                          ExoPlayer (Media3)
                                                                      │
                                                                      ▼
                                                                 音频输出
```

关键代码佐证：

- **曲库聚合**：`data/MusicRepository.kt` 合并 `MediaStoreScanner` / `FolderScanner` / `FileScanner` 三个本地来源，输出 `List<Song>`（`loadLibrary()`，第 42 行）。
- **播放项构建**：`playback/PlaybackConnection.kt` 的 `toMediaItem(song)` 用 `MediaItem.Builder().setUri(song.uri).setMediaId(song.stableKey)`（第 67–71 行）。`song.uri` 直接喂给播放器，没有 `DataSource` 类型判断。
- **播放驱动**：`playback/PlaybackEngine.kt` 通过 `setMediaItems(queue.map { toMediaItem(it) })` 把队列交给 `MediaController`（第 642 行）；播放内核是 `PlaybackService.onCreate` 里的 `ExoPlayer.Builder(this)`（第 76 行），**未自定义 `DataSource.Factory` / `Cache`**。
- **服务形态**：`MediaLibraryService`（`PlaybackService`）同时提供「应用内 MediaController 连接」与「车机浏览树」两条通道，浏览树解析在 `LibraryBrowser.resolve()`。

### A.2 元数据/歌词/封面与持久化如何挂在主链上

- **歌词**：`PlaybackEngine.loadLyrics(song)` → `data/LyricsLoader.kt`，按「同目录 `.lrc/.krc/.yrc/.txt` 侧车 → 内嵌 SYLT/USLT/APIC」顺序读取（第 38–92 行），**全部基于本地文件 / Uri**。
- **封面**：`PlaybackEngine.loadArtwork(song)` → `data/CoverRepository.kt` → `MetadataReader.embeddedPicture(context, song.uri)`（第 102 行），**基于本地文件解码内嵌封面**，三级缓存（内存/磁盘 `cacheDir/covers`/原始文件）。
- **持久化**：`Song.stableKey = uri.toString()` 是全工程的身份锚点——`SongIndex.idByUri[stableKey] → dbId` 映射（数据层索引）、收藏/统计/歌词偏移/播放队列都以 `dbId` 为外键（`data/db/Entities.kt` 的 `song_state` / `playlists` / `queue_songs`）。
  - 队列持久化：`PlaybackEngine.saveQueue()` 用 `index.idOf(mediaItem.mediaId)?.let { QueueSongEntity(...) }`（第 340–342 行），**没有 dbId 的歌曲会被直接跳过丢弃**。
  - `SongIndex.rebuild(songs)` 仅吃曲库列表重建 `idByUri`（第 37–40 行）。

> 一句话概括：**「uri 即身份、本地文件即元数据来源、Room.dbId 即用户数据锚点」** 是现有架构的三根支柱。下文联网改造的全部摩擦，都源于「远程歌曲没有本地 uri/文件/dbId」这三点。

## B. 是否支持联网（在线流式）播放 —— 结论先行

### 结论：**播放内核层零改造即可播放 http(s) 流式直链。**

理由（逐条对应代码）：

1. **播放器按 scheme 自动选数据源**：`PlaybackService`（第 76 行）使用默认 `ExoPlayer.Builder(this)`，其内部的 `DefaultMediaSourceFactory` 会根据 `MediaItem` 的 URI scheme 选择 `DataSource`。对 `http`/`https` 自动使用内置的 `DefaultHttpDataSource`（属于 `media3.exoplayer` 默认依赖，**无需额外模块**）。代码里没有自定义 `DataSource.Factory`，意味着默认行为完全生效。
2. **权限已齐**：`AndroidManifest.xml` 已声明 `INTERNET`（第 37 行）与 `ACCESS_NETWORK_STATE`（第 38 行），联网播放**无需补权限**。
3. **浏览树已预埋网络 URI 支持**：`LibraryBrowser.looksLikeUri()`（第 222–225 行）明确识别 `http:` 这类带 scheme 的字符串，并在 `resolve()`（第 209 行）把 mediaId 重新写回 uri；跨 Binder 丢掉 `LocalConfiguration` 后，远程 URI 同样能还原。
4. **播放项构建与传输无关**：`toMediaItem` 直接 `setUri(song.uri)`，一个 `https://...` 的 `Uri` 与本地 `content://`/`file://` 走的是完全相同的代码路径。

**但是**，零改造只意味着「能出声」。以下四件事在零改造下**不成立**，属于「可用化」必须补的改造：

- 无缓存：每次播放都重新下载，断网不可听、重复流量（见 E.5）。
- 远程歌若未写库（`dbId=0`），队列持久化会被跳过、收藏/统计全部失效（见 E.4 / F.4）。
- 歌词、封面、内嵌元数据三条链路对远程 URI 会静默失败（见 D / F.3）。
- 仅支持普通渐进式 http(s) 流，**不支持 HLS/DASH 与 DRM**（见 F.2）。

## C. 音乐源获取途径分析

现状：项目 **100% 本地**。音乐源来自 `MediaStoreScanner`/`FolderScanner`/`FileScanner`；`SongSource` 枚举只有 `MEDIA_STORE`/`FOLDER`/`FILE`（`data/model/Song.kt` 第 7 行）；全工程唯一网络代码是 `data/UpdateChecker.kt`（仅用 `HttpURLConnection` 查 GitHub Releases），**未引入 OkHttp/Retrofit/Coil 任何 HTTP/图片库**（已核对 `app/build.gradle.kts` 依赖仅 `androidx.media3.exoplayer`/`session`/`common`）。

若要联网，需要新增的不是「播放能力」而是「**音乐源获取能力**」。可能的形态分四类：

| 形态 | 描述 | 技术门槛 | 业务门槛 |
|---|---|---|---|
| ① 接在线流媒体/API 拿 http 直链 | 某服务/自有后端返回音频直链 | 低（拿到直链即可播） | **极高**：鉴权、配额、版权、直链是否支持 Range/续期 |
| ② WebDAV 挂载（需常开中转） | 网盘 → Alist/OpenList 转 WebDAV → 挂载 | 中（标准 WebDAV 客户端） | 中：需常开设备 + 内网穿透 |
| ③ 远程 M3U / 网络电台 | 用户导入一个含 http URL 的播放列表 | **极低** | 低：用户自担来源 |
| ④ 用户自填 http 直链 | 用户直接粘贴音频 URL | **极低** | 低：用户自担来源 |

**关于主流网盘开放平台的事实（独立调研结论，不再引用已删除的第四期规划文档）**：

- 主流网盘（以百度网盘为例）的「听自己的音乐」被「平台能力分层」限制——官方 `download` 接口只给下载用途，**「极速播放」流式服务属特殊服务，个人应用无法开通**；且 2026-06-03 后新建应用只能访问隔离的 `/apps/{appname}` 目录，自建音乐目录扫不到。这意味着**自研直连网盘私有接口「能跑但违规、有封号风险」，应明确排除**。
- 但「云盘播音乐」在技术上**完全可行**：第三方成熟播放器（棉花音乐 / 拟声 / LightPlayer）已长期提供多网盘 + 车机播放，说明存在可用的授权/访问路径（长期运营账号 + 已获批能力，或走 WebDAV 等标准协议）。
- **WebDAV 中转（Alist / OpenList）是标准协议、稳定、无审核风险**：网盘 → Alist 转 WebDAV → 播放器挂载；对个人用户而言，只要有一台常开设备（NAS / 软路由 / 云服务器）即可，WindTone 只需实现一个标准 WebDAV 客户端。这正是 WindTone 在 1.0.4 曾实装、1.1.0 移除的能力，抽象层（`CloudSource` / `CloudCacheManager` / `stableKey` 按 source 分区）当时就已设计好、可直接复用。

> **核心判断**：对 WindTone 而言，**最大的业务难点是「接哪个源」，而非「能不能播」**。技术侧（内核 + 协议）几乎不挡路，真正的挡路点是「合法、稳定、带流式直链、且个人开发者拿得到的音乐源」是否存在。建议先做 §G 阶段 0 的零改造验证，把「能不能播」彻底坐实，再决定源形态。

## D. 音频数据解析处理流程（现状 + 联网后如何变）

### D.1 现状（本地）

| 环节 | 现状实现 | 代码 |
|---|---|---|
| 容器/解码 | ExoPlayer 默认提取器（无 ffmpeg） | `PlaybackService` 第 76 行 |
| 歌词 | 同目录 `.lrc/.krc/.yrc/.txt` 侧车 → 内嵌 SYLT/USLT/APIC | `LyricsLoader.loadRaw` 第 38–92 行 |
| 封面 | `MetadataReader.embeddedPicture(context, song.uri)` 内嵌图 | `CoverRepository.loadRaw` 第 102 行 |
| 曲目元数据 | MediaStore 标签 / 扫描时读标签 | `MediaStoreScanner`/`FileScanner` |

### D.2 联网后如何变

| 环节 | 联网后变化 | 备注 |
|---|---|---|
| 容器/解码 | **仍由 ExoPlayer 负责**，行为不变 | 但无 ffmpeg：远程 **WMA/APE/DSF** 同样播不了（与本地同限制） |
| 歌词 | 无本地文件/Uri，现有链路全盘失效 | 需新增「远程歌词」分支：从 `lrcUrl` 拉取，或在入库时一次性抓取缓存 |
| 封面 | 无内嵌可解（`openFileDescriptor(http://)` 直接失败） | 需从 `coverUrl` 拉取并复用 `CoverRepository` 磁盘缓存；或入库时抓取 |
| 曲目元数据 | 无 MediaStore / 本地标签可查 | 来自源 API 返回的标题/歌手/专辑；网络电台则来自 HTTP 响应头（如 ICY `StreamTitle`）或 HLS 内嵌元数据 |
| 播放进度/缓存 | 无缓存，每次重下 | 需 `SimpleCache` + `CacheDataSource`（仅此处要动播放内核，见 E.5） |

**结论**：联网后「能不能播」不变（ExoPlayer 照常解码），但「播出来是什么样」（歌词、封面、标题）与「播得费不费流量/断网能不能听」（缓存）两条线必须重建。

| # | 改动文件/模块 | 改动内容 | 难度 |
|---|---|---|---|
| E.1 | `app/build.gradle.kts` + 新增 `data/remote/` | 引入 **OkHttp**（取元数据/歌词/封面需自有 HTTP 层）。注意：**播放本身可复用 Media3 内置 `DefaultHttpDataSource`，不必为播放引入 OkHttp**；OkHttp 只为源列表/元数据/歌词/封面这些「非播放」HTTP 请求服务（Range、重定向、超时、鉴权头统一管理）。 | 低（引入依赖）/ 集成中 |

| E.4 | `PlaybackEngine.kt`（`saveQueue`/`restoreQueue`）、`SongIndex.rebuild`、`MusicRepository`、DAO | **持久化适配**：远程歌必须写库拿到 `dbId`，否则收藏/队列/统计（`song_state`/`queue_songs`/`playlists` 都以 `dbId` 为外键）全部失效。`SongIndex.rebuild` 要把远程歌一并纳入；`saveQueue` 现有 `index.idOf(mediaId)` 逻辑可直接复用，前提是远程歌已写库。 | 中 |
| E.5 | `PlaybackService.kt`（仅此处动播放内核） | **缓存层**：引入 `SimpleCache` + `CacheDataSource.Factory` 包裹默认 `DefaultHttpDataSource`，复用已有 `cacheDir`（封面已用 `cacheDir/covers`，可并排建 `cacheDir/media`）。否则重播重复下载、断网不可听、费流量——这是播放内核唯一需要动的地方，且 API 成熟、风险低。 | 中 |
| E.6 | 新增源适配模块 + UI（`ui/library/*`、设置页） | **UI 入口**：搜索/在线歌单/授权登录/远程目录浏览。这是工作量最大的一块（占整体 50%+），且高度依赖前面 E.2–E.5 的模型与持久化基础。形态决定具体 UI：M3U 导入只是一个文件解析 + 列表页；WebDAV 需登录/目录树；流媒体 API 需搜索页。 | 高 |

## F. 核心难点与技术限制

1. **音乐源业务选型（最大难点，业务非技术）**：合法、稳定、带流式直链、且个人开发者可拿到的源。主流网盘官方开放平台对个人应用受限（见 C 章），但 WebDAV 中转（自有常开设备）、M3U / 自填直链都可行（见 H 章排序）。**这一步不定，后面 E.6 的 UI 形态就无法收敛。**

2. **加密 / HLS + DRM 流不支持**：项目仅有 `media3.exoplayer`（默认提取器），**无 `media3-exoplayer-hls` / `dash`，也无 DRM 模块**。若选的源是 HLS（很多网络电台、部分流媒体用 HLS）或带 token/DRM，则需额外引入 `media3-exoplayer-hls` 并实现 token 续期。这正是「个人应用拿不到免鉴权流式地址」的本质——平台只给下载用途的接口，流式需另行解决。

3. **元数据（歌词/封面）对齐**：远程无本地文件，现有 `LyricsLoader`/`CoverRepository`/`MetadataReader.embeddedPicture` 对 http URI 会静默失败。`openFileDescriptor(http://...)` 直接抛异常。必须新增远程获取路径，并处理好「在线拉取失败/超时」的降级（回到无歌词/占位封面）。

4. **`stableKey` 不变性（老用户数据安全）**：现有所有用户数据（收藏、歌单、队列、统计、歌词偏移）都锚定在 `stableKey = uri.toString()`。远程歌若复用同一套 key 生成逻辑会与本地碰撞，或直接让老用户本地收藏失效。**务必：本地分支算法不动，远程分支加 source 前缀**，且远程歌写库后 `dbId` 稳定，前端映射跟随 `SongIndex.idByUri` 不变。

5. **缓存与车机弱网**：车机常处弱网/外网场景，无缓存时：重播重下、断网即停、流量高。E.5 的 `SimpleCache` 是必须的，但还要处理：缓存上限与 LRU 淘汰（参考 `CoverRepository` 的 50MB 磁盘上限思路）、车机存储紧张时系统回收 `cacheDir`、后台下载对前台播放的带宽争抢。

6. **音频格式解码（无 ffmpeg）**：远程无损并不等于都能播。默认提取器支持 MP3/AAC/FLAC/WAV/M4A/OGG 等，但 **WMA/APE/DSF** 等需要 `media3-decoder-ffmpeg` 扩展（当前未引入）。远程源若提供这些格式，本地和远程一样播不了——这是独立于「联网」的既有约束，选型时要确认源的主要格式落在默认解码器覆盖范围内。

## G. 改造任务分解（有序、含依赖）

按「最小可用 → 完整」分阶段。**阶段 0 不写任何联网代码也能验证内核零改造结论**，强烈建议先行。

```
阶段0（验证内核零改造）
  ├─ 任务0.1：临时把一首本地 Song 的 uri 改成某个公开 http(s) 直链（如公开测试音频），
  │           直接通过现有 toMediaItem → ExoPlayer 播放，确认能出声、能拖拽、能续播。
  │  产物：可行性实测记录 + 已知缺口清单（无缓存/无封面/无歌词/未入库）。
  │  依赖：无。难度：极低（验证性质）。

阶段1（远程 Song 模型 + 入库）
  ├─ 任务1.1：SongSource 增加 REMOTE；Song 增加 remoteId/coverUrl/lrcUrl；stableKey 按 source 分区。
  ├─ 任务1.2：SongEntity 增加对应列；DAO 支持 upsert 远程歌；SongIndex.rebuild 纳入远程歌。
  ├─ 任务1.3：引入 OkHttp（仅服务源列表/元数据/歌词/封面，播放仍用 Media3 默认）。
  └─ 依赖：阶段0。难度：中。

阶段2（元数据/歌词/封面远程分支）
  ├─ 任务2.1：入库时一次性抓取远程歌词(lrcUrl)/封面(coverUrl)并落磁盘缓存；
  │           LyricsLoader/CoverRepository 增加「远程已缓存」分支，运行时不依赖在线。
  ├─ 任务2.2：运行时降级（拉取失败 → 无歌词/占位封面），不影响播放。
  └─ 依赖：阶段1。难度：中。

阶段3（缓存层）
  ├─ 任务3.1：PlaybackService 引入 SimpleCache + CacheDataSource，复用 cacheDir；
```

## H. 重新考虑：删除「第四期·云盘音乐」规划文档后

### H.1 重新框定的事实

- **内核零改造可播 http(s) 流**：不变（见 B 章），与任何源文档无关。
- **主流网盘官方开放平台对个人应用受限**：这是平台规则事实（能力分层 + `/apps/{appname}` 目录隔离 + 无极速播放流式），自研直连违规且有封号风险，**仍应排除**。
- **「云盘播音乐」技术可行、且已有成熟先例**：第三方播放器（棉花音乐 / 拟声 / LightPlayer）长期提供多网盘 + 车机播放；WindTone 自身在 1.0.4 也曾实装 WebDAV 云盘、1.1.0 移除——说明这条链路工程上跑通过。
- **WebDAV 中转（Alist/OpenList）是标准、稳定、无审核风险的路线**：只需用户自有常开设备（NAS/软路由/云服务器），客户端协议公开。

### H.2 对 WindTone 的源选型重新排序

按「契合产品定位（数据留本机、隐私优先）+ 技术可控 + 落地成本」三维度重排：

| 优先级 | 源形态 | 说明 |
|---|---|---|
| ★ 首选（自托管） | **WebDAV 中转（Alist/OpenList）** | 标准协议、无第三方商业 API 依赖、契合隐私定位；只需用户自有常开设备。可复用 1.0.4 既有的 `CloudSource` / `CloudCacheManager` / `stableKey` 分区抽象。 |
| ★ 兜底（零基建） | **远程 M3U / 用户自填 http 直链** | 无需任何服务器，用户自担来源；阶段 0 验证的自然延伸。 |
| △ 备选 | 网络电台（HLS / ICEcast） | 需补 `media3-exoplayer-hls`；适合「听流」而非「听曲库」。 |
| ✗ 排除 | 主流网盘官方开放平台直连 | 平台能力分层 + 目录隔离 + 违规风险。 |
| ✗ 排除 | 商业流媒体 API（网易云 / QQ 等） | 鉴权 / 配额 / 版权，与 WindTone 本地优先定位冲突，远超个人开发者能力。 |
