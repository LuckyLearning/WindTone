# 在线音乐与音源接入 · 全面规划

> 目标：把「在线播放」提升到与「本地播放」同级，音源解析协议对齐洛雪音乐（LX Music）。
> 基准代码：WindTone `v1.2.61`（code 172）；洛雪参考实现：`lx-music-mobile`（Apache-2.0）。
> 本文所有结论均基于实读两侧源码，关键处标注文件与行号。

---

## 0. 结论先行

1. **真正决定成败的不是「能不能播」，而是「身份」与「取址时机」**。播放内核早已能播 http(s)（`DefaultMediaSourceFactory` 按 scheme 选源，HLS 依赖 `media3-exoplayer-hls` 也已在 `app/build.gradle.kts:324`）。风险集中在：在线歌用什么键做身份、直链异步且会过期时怎么喂给 Media3。
2. **现成范式就在代码里**：云盘那套「占位地址 `aliyun-pending://` → 滑动窗口补链 → `CloudUrlMemo` → `replaceMediaItem` → 401 重取」与在线音源的形态**完全同构**。本方案的核心动作是把这套机制**从「阿里云盘专用」泛化成「在线取址通用」**，而不是另起一套播放链。
3. **音源形态建议：以「脚本运行时」为主（协议兼容洛雪 v2 源脚本），内置直连移植为辅**。理由见 §5 D1 —— 逐行 Kotlin 移植五家源的签名/加密是「一次性成本极高、维护成本永久」的路，且与上游一起腐烂。
4. **数据层必须做的唯一硬决策**：在线歌要不要进 `songs` 表。进 → 收藏/歌单/队列/统计/歌词偏移全部天然复用（这就是「同级」的定义）；不进 → 双套数据、双套 UI，等于承认在线是二等公民。**建议进**，代价是必须给扫描对账加 `origin` 隔离，否则重扫会把在线歌全删。
5. **有一个既有约定需要你拍板**：`MusicDb` 目前只有 `fallbackToDestructiveMigration()`（`data/db/MusicDb.kt:69`），任何 schema 变更都会清空收藏/歌单/统计。本次是纯加列 + 加表，可以补一条无损 `Migration(5,6)`。是否破例，见 §15 Q1。

## 1. 「同级」的可验收定义

不提「同级」这种形容词，落成五条可测断言：

| # | 断言 | 验收方式 |
|---|---|---|
| A1 | 在线收藏的曲目出现在「歌曲 / 专辑 / 歌手」一级列表，与本地混排，可按来源筛选 | 列表条数与筛选联动 |
| A2 | 本地与在线可混排进**同一个**队列并连续播放，切歌无「占位错误」闪断 | 混合队列连播 30 首无失败 |
| A3 | 收藏、歌单、播放统计、最近播放、歌词偏移对在线歌同样成立，且重启后仍在 | 杀进程重启核对 |
| A4 | 缓存、断点续播、A-B、倍速、EQ、悬浮窗、锁屏、车机、蓝牙对在线歌行为一致 | 逐项过真机清单 |
| A5 | 全局搜索同时命中本地与在线，本地优先，在线标注来源；离线时在线结果**灰显**而非消失 | 断网重试 |

「同级」不等于「无差别」。三处**必须显式区分的差异**要写进 UI 与代码：

- 在线歌**没有本地文件**：文件大小、比特率实测、目录定位、同名歌词侧车这些基于文件的能力不成立 → 显示「—」而不是「0」。
- 在线歌**地址会失效**：任何时刻都可能需要重新取址，UI 要有「重新解析」与「换源」动作。
- 在线歌**离线行为不同**：未缓存时断网不可播，要灰显 + 原因，不能静默跳曲。

## 2. 洛雪音乐的实现拆解（读源码所得）

### 2.1 源抽象：每源一套同构模块

`src/utils/musicSdk/` 下 `kw / kg / tx / wy / mg` 各一个目录，每个目录导出**同名同形**的模块：

```
musicSearch.js   search(keyword, page, limit) → { list: [...], total }
musicInfo.js     getMusicInfo(...)            → 详情（含各档 qualitys）
musicUrl.js      getMusicUrl(songInfo, type)  → 直链
lyric.js         getLyric(songInfo)           → { lyric, tlyric, rlyric, lxlyric }
pic.js           getPic(songInfo)             → 封面 URL
leaderboard.js / songList.js / album.js / singer.js   榜单、歌单、专辑、歌手
```

`index.js` 把六源聚合成 `sources` 表并按 id 分发；`api-source.js` 声明每条源的**能力集与音质集**，是「这个源能干什么」的唯一声明处。

**可借鉴的关键点**：接口形状统一 + 能力集声明。这直接对应本方案的 `MusicSource` 接口与 `Capability` 枚举。

### 2.2 自定义源（v2 脚本）的宿主机制

这是洛雪真正的「音源」形态，也是本方案推荐对齐的部分：

| 层 | 实现 | 文件 |
|---|---|---|
| JS 引擎 | QuickJS（JNI），`wang.harlon.quickjs:wrapper-android:2.4.0` | `android/.../userApi/QuickJS.java` |
| 预置脚本 | `assets/script/user-api-preload.js` 注入 `globalThis.lx` | 同上 `getPreloadScript()` |
| 脚本入口 | `lx_setup(key, id, name, desc, version, author, homepage, rawScript)` 后 `evaluate(script)` | `QuickJS.java:143` |
| 双向通道 | `__lx_native_call__(key, action, data)` 出、`__lx_native__(key, action, data)` 入 | `user-api-preload.js:281` |
| 事件集 | `init / request / cancelRequest / response / showUpdateAlert / log` | `src/utils/nativeModules/userApi.ts:69` |
| 脚本 API | `lx.on('request')`、`lx.request(url, opts, cb)`、`lx.utils.{buffer, crypto.{md5, aesEncrypt, rsaEncrypt, randomBytes}}` | `user-api-preload.js:351` |

**为什么脚本不能自己发 HTTP**：QuickJS 无 `fetch`/`XHR`。所以宿主必须提供 `request` 桥 —— 脚本发 `{url, method, data, headers, timeout, binary}`，宿主真发请求，再 `response` 回灌。这条桥是「语言无关」的，Kotlin 侧用 OkHttp / HttpURLConnection 都能实现。

**能力声明在脚本里**：`handleInit(info)` 收到 `{sources: {kw: {type:'music', actions:[...], qualitys:[...]}}}`，宿主据此过滤脚本真正支持的能力（`user-api-preload.js:304-336`）。音质 id 固定为 `128k / 320k / flac / flac24bit`。

### 2.3 解析链与匹配打分

`findMusic()`（`src/utils/musicSdk/index.js:74`）是「已知一首歌的元信息，去多源找同一首」的算法，逐级降级匹配：

1. 时长差 ≤ 5 秒（硬门槛，`isEqualsInterval`）
2. 名字归一化后全等（去空格/标点/引号）+ 歌手互相包含
3. 名字互相包含 + 版本字符（live/伴奏/remix）一致性
4. 专辑全等 + 歌手包含
5. 最后按「最严格匹配优先」分组输出

**这套逻辑必须移植**（`data/online/TrackMatcher.kt`），它解决两个本产品的真实需求：
- 本地歌缺文件 / 想听更高音质 → 用本地元信息去在线补位；
- 用户搜「周杰伦 晴天」→ 多源结果按可信度排序，而不是简单拼贴。

## 3. 总体架构

```
┌────────────────────────────── UI 层 ──────────────────────────────┐
│  抽屉「在线音乐」: 搜索 · 榜单/歌单 · 我的在线收藏 · 云盘(已有)      │
│  一级列表(混排)  ·  播放页(来源徽标/音质/离线态)  ·  车机浏览树       │
└───────────────────────────────┬───────────────────────────────────┘
                                │ Song（唯一数据形态，无「在线版 Song」）
┌───────────────────────────────▼───────────────────────────────────┐
│ 曲库域  MusicRepository / SongIndex / LibraryCore                  │
│   ├─ 本地扫描（MediaStore/Folder/File）→ origin=LOCAL               │
│   └─ 在线入库（搜索结果落库）        → origin=ONLINE                │
└───────────────────────────────┬───────────────────────────────────┘
                                │
┌───────────────────────────────▼───────────────────────────────────┐
│ 在线域  data/online/                                               │
│   MusicSourceRegistry ─┬─ ScriptSource（QuickJS 运行时，主）         │
│                        └─ DirectSource（Kotlin 内置直连，辅）        │
│   OnlineResolver  ← 统一取址入口（音源 / 云盘 / M3U 直链 三实现）     │
│   TrackMatcher · OnlineCache(元数据) · SourceHealth                │
└───────────────────────────────┬───────────────────────────────────┘
                                │ resolve(stableKey) → PlayableUrl
┌───────────────────────────────▼───────────────────────────────────┐
│ 播放域  PlaybackEngine                                             │
│   PendingScheme 泛化：lx-pending:// / aliyun-pending://             │
│   PlaybackWindow（AHEAD=2 / BEHIND=1）+ CloudUrlMemo → UrlMemo      │
│   失效重取(401/403/410) → 换源重试                                   │
│   OnlineMediaCache（SimpleCache，按 stableKey 做键）                │
└───────────────────────────────────────────────────────────────────┘
```

**三条贯穿全局的规则**：

1. **只有一种 `Song`**。不存在 `OnlineSong`。在线与本地在播放域、UI 域完全同构，差异用 `SongSource.ONLINE` 一个枚举 + 少量可空字段表达。
2. **地址永不入库**。`Song.uri` 对在线歌是**占位**（`lx-pending://track#lx:kw:123`），真直链只在进程内 `UrlMemo` 活 4 小时。这一条直接决定了「重启后仍能播」与「不会存一堆过期链接」。
3. **取址只有一个入口**。播放链任何地方都只调 `OnlineResolver.resolve(stableKey, quality)`，不认来源。云盘、M3U、音源三种走同一函数。

## 4. 数据模型变更

### 4.1 键规则（红线：本地分支一字不改）

```
本地   : stableKey = uri.toString()            ← 现有算法，单测钉死，禁止改动
云盘   : stableKey = "aliyun:" + TrackFragment ← 现有，不动
M3U    : stableKey = uri.toString()            ← 地址即身份，不动
在线   : stableKey = "lx:" + sourceId + ":" + songId     ← 新增
```

`lx:` 前缀与 `aliyun:` 一样**不是协议**。`LibraryBrowser.looksLikeUri()` 会把它误判成 URI 塞给播放器（`data/playback/LibraryBrowser.kt:222` 的历史坑，v1.1.71 播放全挂就栽在这）。**必须在 `resolveOne` 里先于 `looksLikeUri` 判断前缀**，这条要写进单测。

### 4.2 `Song` 字段增补（`data/model/Song.kt`）

```kotlin
enum class SongSource { MEDIA_STORE, FOLDER, FILE, REMOTE, ONLINE }   // 新增 ONLINE

data class Song(
    ...
    val source: SongSource = SongSource.MEDIA_STORE,
    /** 在线歌解析所需的全部信息（本地歌为 null）。与 uri 一样走 copy 整体替换 */
    val online: OnlineRef? = null,
)

@Immutable
data class OnlineRef(
    val sourceId: String,      // "kw" / "kg" / "tx" / "wy" / "mg" / "custom:uuid"
    val songId: String,        // 源内 id
    val quality: String,       // 128k / 320k / flac / flac24bit（用户当前选择）
    val availableQualities: List<String>,
    val coverUrl: String? = null,
    val lrcUrl: String? = null,
    val albumId: String? = null,
    val intervalSec: Int = 0,  // 用于 TrackMatcher 时长门槛
    val vip: Boolean = false,  // 需要会员/不可解析 → 列表置灰但保留
)
```

**为什么 `ONLINE` 不能复用 `REMOTE`**：`REMOTE` 的 uri 是**最终地址**，可直接播；`ONLINE` 的 uri 是**占位符**，必须解析。混用会让播放链在任何一处出现「这是什么地址」的猜测，而这正是现有代码刻意避免的（`Song.kt:9` 的注释已经把 REMOTE 的语义钉死）。

### 4.3 数据库（**结论：不需要动 schema**）

原本计划加 `origin` 列 + `online_sources` 表，实现时发现两者都可以省掉，且省掉之后**不需要任何迁移、零数据风险**：

| 原计划 | 实际做法 | 理由 |
|---|---|---|
| `songs.origin` 列 | 复用现有 `songs.source`（值 `'ONLINE'`） | `SongSource` 本来就是「来源」的单一事实源；再开一列必然与它漂移。`source` 已经落库、已有值域 |
| `songs.onlineSourceId/SongId` | 编码进 `songs.uri`（`lx:kw:228908`） | 与云盘把身份编进 fragment 同理，身份只有一处，不会出现「uri 与列不一致」 |
| `songs.onlineQuality` | 不进库，用全局默认音质 | 逐曲音质是「可选偏好」，不是身份；要做也应该进 `song_state` |
| `songs.coverUrl/lrcUrl` | 运行时现取，不落库 | 二者都是**易失地址**，落盘等于存一堆过期 URL。歌词/封面命中后走既有磁盘缓存（`covers/`） |
| `online_sources` 表 | `online_tracks.json`（源内 raw）+ 后续 `sources.json` | 音源是「个位数条记录」，与 `OnlinePlaylistStore` 同一取舍：为它改 schema 不划算 |

**唯一必须改的 SQL**（不是 schema 变更）：`SongDao.markMissing` 增加
`AND source IN ('MEDIA_STORE','FOLDER','FILE')`。不加这一条，每轮扫描都会把在线歌标成
「文件不见了」，随后 `deleteMissing()` 连歌带收藏一起级联删掉。

**另一个必须补的点**：在线歌不在任何扫描结果里，扫描落库后要单独并回内存曲库
（`LibraryCore.persistSongs` 末尾），否则每次扫描都会把它们从界面与队列里「扫掉」，
直到下次冷启动才复原。

已由单测钉死：`LibraryDbTest.scanReconciliationNeverTouchesOnlineSongs`。

## 5. 五个关键设计决策

### D1 · 音源形态：脚本运行时 vs 内置直连移植

| 维度 | A. 脚本运行时（对齐洛雪 v2） | B. Kotlin 逐行移植五家内置源 |
|---|---|---|
| 工作量 | 一套运行时（约 1200 行 Kotlin + 一份 preload） | 每源 800–1500 行，含各自签名/AES/RSA/参数混淆逆向 |
| 上游变化 | 脚本热更新，不发版 | 每次上游改接口/改密钥 = 改 Kotlin + 发版 |
| 生态 | 社区已有脚本可直接导入 | 从零维护，无外部供给 |
| 风险 | QuickJS ABI/沙箱/调试 | 逆向本身是持续对抗 |
| 合规边界 | App 不含任何音源，用户自行导入 | App 内置源 = 责任前移到开发者 |
| 车机 | 需 32 位 so（见 §8.4） | 纯 JVM，无 so |

**结论：A 为主，B 作为可选补充**。但两者共用同一个 `MusicSource` 接口，所以这个决策**不阻塞**——阶段 0 先把接口和播放链跑通，用「假源」验证，之后再决定先做哪个实现。

> 与「用洛雪源码逻辑、只是换个语言」这一要求的差异点，说明白：洛雪自己从 v2 起，内置源与自定义源**走的是同一套 `lx` 事件接口**（`api-source.js` 与 `userApi` 同构）。照抄它的做法，得到的就是「运行时」而不是「五份 Kotlin 移植」。逐行翻译等于只抄了一半，还抄成了会腐烂的那一半。

### D2 · 在线歌是否进 `songs` 表

**结论：进。** 三条依据已写在 §4.3。代价与对策：

- 代价 1：扫描对账要改（3 条约束见上）。
- 代价 2：`songs.uri` 唯一索引要容纳占位地址 → 占位地址本身唯一，`lx-pending://track#lx:kw:123` 可作 uri，唯一性成立。
- 代价 3：`SongIndex.rebuild()` 吃全量列表，在线歌一并纳入即可（`data/SongIndex.kt:37`），无需改结构。

### D3 · 播放链：泛化「占位 + 窗口补链」

现有实现（`playback/PlaybackEngine.kt:836 fillAliyunWindow`、`data/aliyun/AliyunPlaybackWindow.kt`、`playback/CloudUrlMemo.kt`）：

```
setMediaItems(含 pending 项) → onMediaItemTransition → fillWindow(AHEAD=2/BEHIND=1)
  → 取到直链先 remember 进 memo，再 replaceMediaItem
  → 服务端 resolve 时先查 memo，避免地址被剥回占位
  → 401/403 → refreshAliyunUrl 重取一次
```

**泛化方案**（改动最小、风险最低）：

| 现有 | 泛化后 |
|---|---|
| `AliyunPlaybackWindow.PENDING_SCHEME = "aliyun-pending"` | `PendingSchemes`：`aliyun-pending` / `lx-pending`，`isPending(scheme)` 统一判定 |
| `CloudUrlMemo` | 改名不改名的都行，键仍是 `stableKey`，在线歌共用 |
| `fillAliyunWindow()` | `fillPendingWindow()`：对每个 pending 项问 `OnlineResolver` |
| `refreshAliyunUrl(driveId, fileId)` | `resolveFailed(stableKey)`：先同源重取，再换源 |
| `LibraryBrowser.resolveOne` 云盘分支 | 增加 `online:` 分支，同形态返回占位/真直链 |

**首播延迟的处理**（体验关键）：`resolveOne(item, isStart=true)` 已经对起播项现取直链（`LibraryBrowser.kt:259`）。在线歌沿用：起播项同步取（约 200–600ms），其余项走窗口异步补。再加两条：

- 点列表条目时**预热**：点击即发起 `resolve`（不等待），`setMediaItems` 时多半已命中 memo；
- 首句歌词同时起取，避免「先出声、歌词晚 2 秒」。

**为什么不改成「异步 DataSource」**：Media3 的 `ResolvingDataSource` 只能改 DataSpec、不能异步等待；在 `DataSource.open()` 里阻塞会让加载线程卡死，弱网下直接触发播放超时。补链范式与 Media3 的加载模型天然契合，且本项目已在车机上验证过一整年。

### D4 · 网络层：OkHttp vs 继续 HttpURLConnection

现状：零 HTTP 依赖，`UpdateChecker` / `AliyunDrive` / `RemoteTagFetcher` / `NetworkPlaylistFetcher` 全部手写 `HttpURLConnection`。

| 维度 | 继续 HttpURLConnection | 引入 OkHttp |
|---|---|---|
| APK 增量 | 0 | 约 +1.0–1.3 MB（含 okio） |
| 脚本 `request` 桥 | 需自己实现：取消、超时、二进制、gzip、重定向 | 原生全部支持（`Call.cancel()`、`Interceptor`） |
| 并发 | 每请求一线程 + 手写连接池 | 连接池 + 复用 + HTTP/2 |
| 与现有代码一致性 | 高 | 需并存，或逐处迁移（不建议一次性迁） |

**结论：为在线域新增 OkHttp，仅限 `data/net/` 一层，播放仍走 Media3。** 理由是脚本 `request` 桥需要「可取消 + 二进制 + 超时」这组能力，手写 HTTP 在这三点上长期是负债。现有四处 HTTP 代码**不动**（避免为统一而引入回归面），新代码只走新层。

> 若你对包体极敏感（车机 OTA 有硬上限），可走备选：`data/net/HttpEngine` 接口 + `HttpUrlConnectionEngine` 默认实现，OkHttp 作为后续可替换实现。届时只需换实现类。

### D5 · schema 迁移：本次**用不上**，但约定已解锁

原计划要给 `songs` 加 `origin` 等列、新建 `online_sources` 表 —— 那必然触发 `fallbackToDestructiveMigration()`，清空老用户的收藏/歌单/统计。

实现时改成「复用 `source` 列 + 身份编进 uri + 派生数据走 JSON 存档」（见 §4.3 对照表），结果**一次 DDL 都不需要**。所以这个问题本次没有被触发。

但用户的决定已经记录在案（2026-11-24）：**将来真需要动 schema 时，写增量 `Migration(n, n+1)` 而不是依赖 destructive 兜底**，并补一次迁移单测。判据：变更若为纯新增（加列 / 加表），一律写迁移；若要改列语义，再单独评估。

> 这条对后续「下载固化到本地」（§9.3，需要把 `source` 从 ONLINE 改成 FILE 并换 uri）尤其重要 —— 那一步会动既有行，属于必须保数据的那一类。

## 6. 播放链时序（在线单曲）

```
用户点搜索结果的第 3 首
  │
  ├─(1) OnlineResolver.resolve(stableKey) → 直链（同步等待，≤1.5s 超时）
  │       ├─ UrlMemo 命中 → 立即返回（≤1ms，重播/回切场景）
  │       ├─ 音源脚本 musicUrl(quality) → 直链
  │       └─ 失败 → 降级音质 → 仍失败 → 换源(TrackMatcher 匹配同曲) → 仍失败 → 报错可重试
  │
  ├─(2) UrlMemo.remember(stableKey, url)
  ├─(3) setMediaItems(队列全部, index=3)   ← 非起播项 uri 仍为 lx-pending://
  ├─(4) prepare() + play()
  │
  ├─(5) onMediaItemTransition(3) → schedulePendingWindow()
  │       └─ fillPendingWindow(): 为 index 2/4/5 补链 → remember → replaceMediaItem
  │
  ├─(6) 并行：loadLyrics(online lrcUrl) / loadArtwork(online coverUrl) → 落磁盘缓存
  │
  └─(7) 播放错误 403/404 → resolveFailed(stableKey) → 重取一次 → 仍失败 → ErrorSkipPolicy
```

`OnlineMediaCache` 的缓存键必须用 `stableKey`（`CacheKeyFactory` 已支持，`playback/OnlineMediaCache.kt:161`），**不能用直链**——否则每次换签名都是新键，缓存永不命中。这一条在云盘分支已经踩过并解决（`#ay=` 键），在线分支照抄即可。

## 7. 音源运行时设计

### 7.1 组成

```
data/online/script/
  LxRuntime.kt        QuickJS 生命周期、超时、错误边界
  LxBridge.kt         原生桥：request / crypto / buffer / timer / log
  LxScriptSource.kt   MusicSource 实现（search / resolveUrl / lyric / pic）
  LxSourceImporter.kt 脚本导入、元信息解析、版本比较
assets/lx/preload.js  预置脚本（协议对齐，实现自写）
```

### 7.2 桥接动作（与洛雪 v2 契约一致）

| 动作 | 方向 | Kotlin 侧实现 |
|---|---|---|
| `init` | 脚本→宿主 | 记录 capabilities/qualitys，落 `online_sources` |
| `request` | 脚本→宿主 | `HttpEngine` 发真实请求，支持 GET/POST/binary/headers/timeout |
| `cancelRequest` | 脚本→宿主 | `Call.cancel()` |
| `response` | 宿主→脚本 | 回灌 status/headers/body |
| `showUpdateAlert` / `log` | 脚本→宿主 | 静默记录；前者转「源有新版本」提示 |

脚本可见 API：`lx.on('request')`、`lx.request()`、`lx.utils.{buffer.from, crypto.md5/aesEncrypt/rsaEncrypt, randomBytes}`。加密走 `javax.crypto`（AES-CBC/ECB）与 `java.security`（RSA NoPadding、MD5），不需要额外依赖。

### 7.3 许可证

洛雪仓库 `LICENSE` 为 **Apache-2.0**。可以直接复用 `user-api-preload.js`，但需保留版权与 NOTICE 声明；更稳的做法是**按同一契约自写 preload**（约 300 行），彻底避免归属争议，也让「本项目自己的运行时」名实相符。建议自写。

### 7.4 ABI（已定：只出 arm64-v8a）

QuickJS 是 JNI。**2026-11-24 拍板只发布 `arm64-v8a`**（`app/build.gradle.kts` 的 `splits.abi.include` 已收窄），
因此不需要为 v7a / x86 准备 so，也不需要「三级降级」那套兜底 —— 只要 AAR 提供 arm64 即可。

仍保留一条运行时兜底（不是为 32 位，而是为 AAR 缺失 / 加载失败）：

- `System.loadLibrary` 抛 `UnsatisfiedLinkError` 时捕获，隐藏「自定义音源」入口并明示原因，**不允许崩溃**；
- 探测结果进程内缓存一次，不要把 JNI 异常散落到搜索点击路径里。

### 7.5 沙箱与稳定

- **独立进程** `android:process=":source"`：脚本死循环/内存暴涨不拖垮播放进程。这个决定看着重，但对比「车机上歌词悬浮窗被一个第三方脚本卡死」是可以接受的。
- 每次调用 20s 超时（对齐洛雪）；连续 3 次超时 → 该源自动禁用 + 提示。
- 脚本禁文件/网络直连（QuickJS 本身无 IO，桥只暴露受限动作）。
- 脚本全文存 Room，导入时校验必需字段（`id/name/version` + 至少声明一个 action）。

## 9. 音质、缓存与离线

### 9.1 音质降级链

```
用户选 flac24bit → 源支持? → resolve → 成功即用
                          → 失败/不支持 → flac → 320k → 128k
```
降级要**可见**：播放页音质芯片显示实际音质，而不是用户选的那个（避免「我选了无损怎么听着像 128」的困惑）。

### 9.2 缓存

`OnlineMediaCache` 已是完整实现（SimpleCache + 上限档位 + LRU + scheme 路由），**只需两处适配**：

1. 缓存键走 `stableKey`（已支持，确认在线分支传入即可）；
2. 占位 scheme（`lx-pending://`）**不得进 HTTP 工厂** —— `SchemeRoutingDataSource.open()` 已按 scheme 分流（`OnlineMediaCache.kt:299`），加一个分支直接拒绝即可。

已缓存整曲 → 断网可播。判断方式复用 `hasCachedPrefix`（`OnlineMediaCache.kt:232`），但「整曲已缓存」要用 `getCachedLength(key,0,Long.MAX_VALUE) == 文件总长`，不能只看前缀。

### 9.3 「下载到本地」是否要做

**建议放到最后，且做成「固化到本地曲库」而不是「下载管理器」**：

- 在线歌已入 `songs`（D2），下载完成后只需把 `origin` 改成 `local`、`uri` 换成 `file://`，其余用户数据（收藏/歌单/统计/歌词偏移）全部原地保留 —— 这是 D2 决策最漂亮的副产品。
- 但要处理 `stableKey` 变更（`lx:` → `file://`）导致 `SongIndex` 映射与 `queue_songs` 外键的迁移。做法：保留 `dbId` 不变，只改 uri/origin，`SongIndex` 重建时以 dbId 为准。**这条要单独设计，不能顺手做**。

## 12. 合规边界（必须写进产品文案）

事实层面（非判断）：洛雪的内置源调用的是各音乐平台**未公开**的接口，其可用性不受任何授权保障，随平台策略变化；分发一个「自带可用音源」的安装包，风险由分发者承担。

因此本方案的产品形态固定为：

1. **App 不内置任何音源**。首次进入「在线音乐」显示空态 + 「导入音源」引导。
2. 音源由用户自行导入，App 只提供运行时与管理界面，类似播放器提供 EQ 而不提供音乐。
3. 文案明确：「本应用不提供任何音频内容，在线内容来自用户自行配置的音源」。
4. 内置直连源若做（P7），必须**默认关闭**且可整体移除（构建开关），不随默认包分发。

这条同时是「脚本运行时优于内置移植」的第三个理由。

## 13. 明确不做的事（避免范围蔓延

- **不做**账号体系/登录墙（各平台账号态涉及扫码、Cookie 持久化、风控，收益远低于成本）。
- **不做**在线歌与本地歌的「自动全库换源」（3 万首本地曲全去在线匹配 = 请求风暴 + 误匹配）。
- **不做** HLS 电台形态（`media3-exoplayer-hls` 已在，但那是「听流」不是「听库」，另案）。
- **不做**在线歌的逐字歌词（本地都只有逐行，见既有约束）。
- **不碰** `Song.stableKey` 的本地分支（红线）。
