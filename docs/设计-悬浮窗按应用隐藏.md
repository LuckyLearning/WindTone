# 悬浮窗按应用隐藏 + 前台应用记录

> 状态：**已落地**（v1.1.29 起基础能力；DiLink 真机链 v1.1.82–1.1.91 大修）。文首原「尚未落地」已过时，于 2026-10-25 更正。
> 配套调研见 [竞品调研 · 车机音乐应用](竞品调研-车机音乐应用.html)。
> **真机**：用户 2026-10-25 确认 DiLink 相关验证「已验证可以」（见 `真机验证清单.md` P0-78+）。
> 同批独立小功能「车机搜索框语音听写」不属本文范围。

---

## 一、动机

用户车机（比亚迪宋 L DM-i / DiLink）实测：**打开 360 全景影像等全屏应用时，悬浮歌词浮在画面上方挡住视线**；且不止一个应用需要回避（影像 / 泊车 / 视频类等）。用户**没有 adb 权限**，无法用社区方案（`READ_LOGS` 那套）——所以检测手段必须在「免 adb」前提下选。

另一个约束来自调研结论：7 分屏选择器是白名单制（侧载应用进不去）、小迪「默认音乐」是商务合作制 —— **系统级整合走不通，只能在自己 App 内解决**。

## 二、方案总览

```
                    ┌─────────────────────────────┐
                    │  前台应用检测（两个免 adb 通道）│
                    │  ① 无障碍服务（主，事件即时）   │
                    │  ② UsageStats 轮询（备，1.5s） │
                    └──────────────┬──────────────┘
                                   │ 当前前台包名
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
     ┌────────────────┐   ┌────────────────┐   ┌────────────────┐
     │ 隐藏名单判定     │   │ 前台应用记录     │   │ 诊断页展示       │
     │ 命中 → 收起浮层 │   │ 开关开启才记     │   │ 状态 + 历史列表  │
     └────────────────┘   └────────────────┘   └────────────────┘
```

三条规则红线：

1. **无权限就放行**：检测通道一个都没通时，按「不隐藏」处理 —— 绝不让权限问题导致悬浮窗反而消失。
2. **记录默认关**：`foreground_log_enabled` 默认 `false`，用户在设置里显式打开才开始记录（这是行为记录，默认开不合适）。
3. **一切本地**：记录只写 `files/foreground_app_log.tsv`，不联网、不上传；清应用数据即清。

## 三、前台应用检测（两个通道，谁通用谁）

### ① 无障碍服务（主通道）

`ForegroundAppService : AccessibilityService`，只订阅 `typeWindowStateChanged`（不设 `packageNames` 过滤，要的是全部应用），事件里取 `event.packageName` 即为当前前台应用。

- **即时**（事件驱动，无轮询延迟）；
- 用户开启后**常驻记录**（这正是「听风在后台也要记」的关键 —— 服务独立于界面活着）；
- 授权路径：系统设置 → 辅助功能 → 听风 → 开启。**迪丽上这一页的确切路径未知**，诊断页放跳转按钮（`ACTION_ACCESSIBILITY_SETTINGS`）+ 文字路径说明。
- manifest 必须 `android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"` + `res/xml/foreground_app_service.xml` 配置。

### ② UsageStats 轮询（备通道）

`UsageStatsManager.queryEvents` 每 1.5s 拉一次，取区间内最后一个 `ACTIVITY_RESUMED` 的包名。权限用 `AppOpsManager` 探测（`android:get_usage_stats`），已授权才启动轮询；未授权时诊断页给跳转（`ACTION_USAGE_ACCESS_SETTINGS`）—— **迪丽有没有这一页同样未知**，所以它只是备胎。

### ③ logcat 实测（诊断项，不作正式通道）

用户最初想要「日志监听」路线。事实：Android 4.1 起应用只能读自己的日志，读全量需 `READ_LOGS`（signature 级，只能 adb 授予）—— **用户无 adb，此路不通**。但诊断页保留一个「日志可读性实测」按钮：万一迪丽放松了限制，实测通过就自动加成为第三来源（零成本，不成也不亏）。

## 四、隐藏名单（「不显示悬浮窗的应用」）

- 设置 → 歌词 → 桌面悬浮歌词区块新增行：**「不显示悬浮窗的应用」**，副标题 = 「已设 N 个」；点开弹窗。
- 弹窗内容：`PackageManager` 查全部**可启动应用**（MAIN/LAUNCHER），每行 = 图标 + 应用名 + 包名 + **开关**；顶部搜索框（车机友好：大行高、大开关、搜索实时过滤）。
- 勾选状态持久化为 `Set<String>`（新键 `lyric_overlay_hidden_apps`，默认空）；行尾 **↺ 一键清空**（符合「每个可调项都要能恢复默认」的既定规矩，清空 = 回到出厂默认）。
- **空名单 = 功能完全不介入**（检测都不启动，零开销）；名单非空或记录开着时，检测通道才运行。
- 弹窗是自绘 Compose（复用设置弹层模式），不引用任何第三方组件。

## 五、前台应用记录（开关控制，默认关）

- **关于与诊断 → 调试 → 前台应用记录**（「调试」分区默认隐藏，v1.1.31 起需在「关于」卡连点 5 次解锁）开关（默认关；v1.1.31 从「设置 → 歌词」搬过来 —— 记录是排障手段，不该占用歌词设置），副标题说明记录范围与「关掉不影响名单」。
- **每条历史右侧有「加入名单」**（v1.1.31）：点一下即把该包名加入下方名单（已在名单的显示「已在名单」并禁用），查包名 → 加名单不再需要复制粘贴。
- 记录时机：检测通道每次发现**前台应用切换**写一条 —— `时间 \t 包名 \t 应用名`（应用名在写入时解析，解析不到就只存包名）。**连续同一个应用不重复记**（轮询 1.5s 看到同一个只留一条）；A→B→A 算两次切换，都记。
- 存储：`files/foreground_app_log.tsv`，**滚动保留 300 条**（写满截断头部）。**不动数据库 schema**（项目红线：改 schema 要 version+1，一个诊断日志不值得）。
- 诊断页（关于与诊断 → **调试** → 「前台应用记录」；该分区默认隐藏，关于卡连点 5 次解锁）：
  - 检测源状态三行（各带跳转 / 测试按钮）；
  - 「当前前台」实时行（开着诊断页时也能看到自己，便于验证）；
  - **历史列表**：最新在上，三列（时间 / 应用名 / 包名），可滚动；
  - 「复制全部」（复制成纯文本，用户可直接发给开发者预置默认名单）、「清空」（二次确认）。
- **为什么历史是关键**：悬浮窗的价值全在「听风在后台」时，实时显示反而看不到；正常用车 → 停车后打开听风 → 看历史 → 把 360 等应用勾进隐藏名单，这是本功能的主要使用路径。

## 六、显隐规则（扩纯函数，不加分支）

现有 `OverlayVisibility.show(...)`（v1.1.22 抽出，四种例外已上单测）新增一个入参：

```kotlin
foregroundHidden: Boolean  // 当前前台应用在隐藏名单里
```

判定在服务侧完成：`foregroundHidden = prefs.hiddenApps.isNotEmpty() && currentPkg in prefs.hiddenApps`（纯函数 `overlayHiddenForForeground(pkg, hiddenSet)` 单独可测）。规则叠加后仍是一条 `return`，不引入新的嵌套分支。既有规则（全屏前台不画 / 仅后台 / 调整 / 预览 / 暂停隐藏 / 灭屏）逐条保持，新增单测覆盖「名单命中时即使其它条件都满足也不画」。

## 九之二、实现要点与一次真实回归（2026-10-19）

真机反馈：「名单勾了几个，但没起效，悬浮窗还在」。**判定逻辑没错，是通道没接上**：
`ForegroundAppState.currentPkg` 原本只在 `LyricOverlayService` 判可见性时**读一次**（`.value`），
没有进 `combine` —— 检测端（无障碍服务 / UsageStats）写包名**不产生任何既有事件**，
所以切到名单应用后没有任何东西触发重判，只能等下一句歌词（暂停或歌词无变化时永不发生）碰巧重算。

修法：把 `currentPkg` 作为**第六路**并入收集循环（`combine(visuals, ForegroundAppState.currentPkg)`），
包名一变立即重判显隐。`LayoutContractTest.overlayServiceSubscribesToForegroundPackage` 在源码层钉住这条，
并禁止再出现 `pkg = ForegroundAppState.currentPkg.value`。

⚠️ 教训：**「写」与「读」之间必须有一条订阅关系**。这类缺陷的形态是「代码全对、就是没接上」，
纯函数单测永远抓不到（`OverlayVisibility` 一直全绿），要在源码层加契约测试。

模拟器复核（Android 15 / 1080×2400）：桌面悬浮窗可见 → 打开名单内的 Settings → 悬浮窗消失；
退回桌面恢复；**暂停播放**后再进 Settings 仍然收起（旧实现唯一躲不过的那条路径）。

## 十、风险与未决

| 风险 | 应对 |
|---|---|
| 迪丽「辅助功能」页路径未知 | 诊断页给 `ACTION_ACCESSIBILITY_SETTINGS` 跳转 + 文字路径；跳不开就说明手动路径 |
| 迪丽可能没有「使用情况权限」页 | UsageStats 只是备胎；两个通道都没有时放行（不隐藏）+ 诊断页明说 |
| 无障碍服务名义权限重，用户可能不敢开 | 诊断页写清「只读窗口状态变化、不读内容、不联网」；设置副标题常驻显示当前哪个通道在工作 |
| 记录文件被清（清应用数据） | 可接受，诊断功能不承诺长期留存 |
| 应用列表很长时弹窗性能 | `queryIntentActivities` 一次拿全，LazyColumn + 搜索本地过滤（几百个应用无压力） |

## 十一、与既有决议的关系

- **7 分屏 / 小迪语音**：已证伪或观望（见竞品调研），本文不触碰系统整合，全部在自己 App 内解决。
- **悬浮歌词「仅后台显示」「全屏高度」**等既有规则不变，本文只在其上叠加「指定应用前台时收起」。
- 本设计**不动数据库 schema**、不新增危险权限（无障碍服务与使用情况权限都是用户手动授予的特殊权限，非运行时权限）。

## 十二、车机实测（2026-10-24，比亚迪 DiLink）与修复

### 12.1 现象

车机上点「无障碍设置」只弹一句「打不开无障碍设置页，请手动前往：设置 → 辅助功能」，
设置里也找不到这一项。用户侧表现为「功能彻底不能用」，而不是「少开一个开关」。

### 12.2 根因

DiLink 把 **无障碍设置入口整个裁掉**：`Settings.ACTION_ACCESSIBILITY_SETTINGS` 在本机
没有对应 Activity，`startActivity` 抛 `ActivityNotFoundException`。旧实现 catch 后只弹
toast —— 等于把用户留在死路里。

三条外部证据（用于确认「不是我们写错，是系统没这个页面」）：

1. 车机圈子通行做法是装 MacroDroid / 按键助手，再用
   `adb shell pm grant <pkg> android.permission.WRITE_SECURE_SETTINGS` 绕过系统设置页 ——
   说明**服务本体还在**，被裁的只是 UI 入口。
2. DiPlay（DiLink 5.1 仪表盘工具）在隐私说明里明确写了用 **Android Usage Access**
   跟踪车机 Activity，并提示「Usage Access 可在 BYD 导航里撤销」——
   说明 **DiLink 保留了「使用情况访问」这条通道**。
3. 2026 款（2606 固件起）比亚迪收紧了 ADB 扫码授权，新车上「靠 adb 开无障碍」这条路
   正在关闭。因此**不能把 adb 当主推方案**。

### 12.3 修复

| 位置 | 改动 |
|---|---|
| `ForegroundAppDetector` | 跳转由单条 action 改为候选链：标准 action → `ACCESSIBILITY_DETAILS_SETTINGS`（API 31+，用字面量，SDK 里解析不到）→ 各 ROM 显式组件；全部失败返回 false，不再只 toast |
| 同上 | 新增 `canOpenAccessibilityPage` / `canOpenUsageAccessPage`：如实回答「本机有没有这一页」，供 UI 与报告用 |
| 同上 | 兜底**不进候选链**：`ACTION_SETTINGS` 只作路径向导里的显式按钮，避免「设置首页打开了」被误判成成功 |
| 诊断页 | 跳转失败弹路径向导：三条 DiLink 路径 + 使用情况访问等效方案 + 复制说明 + 打开系统设置 |
| 诊断页 | 本机无无障碍页时，**把「使用情况访问」排到前面**，无障碍按钮改文案为「无障碍设置（本机无此页）」 |
| 新增 `ForegroundProbe` | 一键排障报告：机型/系统、服务是否在案、`ENABLED_ACCESSIBILITY_SERVICES` 原文、UsageStats 的 AppOps 模式、电池优化白名单、当前前台包名、设置类应用里的 accessibility Activity、每个候选 Intent 的解析结果、可选 adb 命令 |
| 同上 | 报告落盘 `Android/data/<pkg>/files/diagnostics/fg_probe_<时间>.txt`，并支持整段复制 —— 车机上不方便粘贴时用文件取回 |

### 12.4 为什么这样能"解决问题"

- **功能不依赖无障碍**：UsageStats 轮询（1.5 秒）本来就是独立通道，名单非空或记录开启时
  由 `LyricOverlayService` 启停，与无障碍互不阻塞。车机上开「使用情况访问」即可用。
- **两个通道都没有时**：如实显示「两个页面都被裁掉」，并说明需要 adb —— 不再假装能用。
- **不再靠猜**：报告把「有没有这个页面 / 服务是否在案 / 授权给了没有」变成可回传的文本，
  下一轮修复不需要再让用户描述界面。

### 12.5 仍需真机确认（P0-78）

1. DiLink 上「使用情况访问」页是否存在、授权后 `usageStatsGranted` 是否转 true；
2. 报告能否正常落盘并复制；
3. 只有 UsageStats 时，切到名单内应用悬浮窗是否在 ~2 秒内收起；
4. 车机息屏 / 待机 10 分钟后，轮询是否还活着（电池优化白名单那一行据此判断）。

### 12.6 报告回传后的二次定位（2026-10-24 晚，v1.1.83）

车机（BYD DiLink 5.0 / Android 12 / API 32）回传的报告给出三条硬事实：

1. **无障碍页在 `com.byd.carsettings`**：
   `com.byd.systemsettings.accessibility.AccessibilityMainActivity`（同包另有 `DescriptionActivity`）。
   此前我们只猜过 `com.android.settings` 与 `com.byd.settings`，所以七条候选全部「×」。
   处置：加入硬编码候选 + 增加**动态发现**（枚举设置类应用里含 accessibility 的 Activity），换固件不必再改代码。
2. **`com.android.settings` 系全部不可解析，`USAGE_ACCESS_SETTINGS` 可解析** ——
   证实「使用情况访问」是这台车上的稳定通道，不需要 adb。
3. **报告自身有一处假阴性**：「服务已声明在案：否」。原因是旧实现用
   `queryIntentServices(MATCH_DEFAULT_ONLY)` 查，而无障碍服务的 intent-filter 没有
   `CATEGORY_DEFAULT`，必然查不到。已改为按组件名 `getServiceInfo`，并顺带打印 `exported`。

另外发现一个真实缺陷：服务声明为 `exported="false"`。绑定方是 system_server（跨进程），
非导出组件根本绑不上 —— 即使用户在系统里勾了也无效。v1.1.83 改为 `exported="true"`
（BIND_ACCESSIBILITY_SERVICE 是 signature 级权限，只有系统能绑，放开导出不增加攻击面）。

最后补上「电池优化白名单」入口：车机息屏会冻结后台，轮询停摆的表现是
「白天能用、过一夜失效」。这一项同样不需要 adb。
