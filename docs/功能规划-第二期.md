### 新发现的 bug（读代码得出，非推测）

**B1 · 播放统计根本没写进去 —— 第一期 2.2 是假的**
```
PlayStatDao.bump()      →  "UPDATE play_stats SET playCount = playCount + 1 ... WHERE songUri = :uri"
MusicViewModel.recordPlay() →  只调用 bump()，全工程无 INSERT
```
`play_stats` 表里**只有收藏操作会插入行**（`toggleFavorite` → `insert`）。
对一首从未收藏的歌，`bump()` 命中 0 行 → `playCount` 永远是 0。
后果：「最近播放」「最常播放」两个入口实际**长期为空**，播放次数统计也是死的。

**B2 · 队列不持久化**
`restoreQueueIfNeeded()` 只按 `prefs.lastSongUri` 恢复**单曲**，
重启后队列退化成一首歌，用户精心排的队列全丢。
修复：把整个队列的 stableKey 列表 + 当前下标存入 Prefs。

**B3 · Room 无迁移路径**
`fallbackToDestructiveMigration()` + `version = 1`。
本期要给 `play_stats` 加字段，若无 `Migration` 会**静默清库**（歌单、收藏全没）。

**B4 · 逐字歌词每行末字被重复拼接**
`WordLyricsParser.parseWords()` 里有一段「补尾巴」逻辑：
`content.substring(lastTag.range.last + 1)` 被追加到最后一个字上。
但上一个字的取文范围（`from..content.length`）**已经覆盖到行尾**，
于是 `[0,1000]<0,500,0>你<500,500,0>好` 会被解析成 `words = ["你", "好好"]`，
整行文本变成「你好好」。
而 `LrcParser` 的增强标签路径没有这个问题 —— 属于两个解析器行为不一致的漏网 bug。

**B5 · 播放次数会被 `replaceMediaItem` 虚增**
回填封面 / 下发通知栏歌词都会调用 `replaceMediaItem`，
它会触发 `onMediaItemTransition`，而该回调里无条件 `recordPlay()`。
修 B1 之后若不同时处理，每首歌会被多计 1~N 次播放。

### 关于「纯本地」定位
当前 App **不申请任何网络权限**（清单里只有存储/前台服务/通知权限），是可验证的隐私卖点。
7.4 / 云同步会打破它。建议：主包保持纯本地，联网能力做成**首次使用时才申请**的可选开关，
且在设置页明示当前网络状态。
