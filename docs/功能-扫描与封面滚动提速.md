# 扫描速度与「全部歌曲」封面滚动优化

## 背景

两条用户可感知的卡顿：

1. **扫描慢**：`lastSeenAt` / `markMissing` 只是落库后的软删对账，不是扫描期的跳过条件。
   除冷启动「10 分钟 + 指纹一致」这一处节流外，每次手动扫描 / 改范围 / 增删目录 / 热插拔
   都会把三个来源从头走一遍。其中三处是纯浪费：落库逐条 SQL、扫描后再查一次全表拿指纹、
   SAF 对媒体库已收录的文件重读一遍标签。
2. **快速下滑掉帧**：封面的解码尺寸 / 采样 / 缓存预算三条红线早已合规，剩下的问题在调度层 ——
   滚出视口的解码**无法取消且必定写盘**、进入视口无条件把位图清空导致闪烁与二次重组、
   `MediaMetadataRetriever` 没有并发闸门。

## 本轮改动

### 一、扫描

| 点 | 改动 | 为什么 |
| --- | --- | --- |
| 落库批量化 | `SongDao.insertAll` 改返回 `List<Long>`，新增 `updateAll`；`persistSongs` 把新歌 / 旧歌分两组各一次批量写 | 3000 首时旧实现是 3000 次独立 SQL + 3000 次协程调度；虽已在同一事务里省掉 fsync，常数仍可观 |
| 指纹顺带产出 | `MediaStoreScanner.Result.fingerprint`；`scan()` 在遍历 cursor 时同时累计 `max(_ID)` 与总行数；`LibraryCore.rememberScanFingerprint` 直接用 | 旧实现一次自动扫描要查 3 次 MediaStore，其中记指纹那次是为「记一笔」单独拉的全表 cursor |
| SAF 跳重复读标签 | `FolderScanner.scan(skipTagRead = …)`；`MusicRepository` 把媒体库已收录的「文件名小写 + 字节数」键集合传下去 | 全盘模式下同一条目已被 MediaStore 收过一次，再开 `MediaMetadataRetriever`（1 次 fd + 7~9 次 extractMetadata）纯属重复。**只在媒体库确实产出了该条目的前提下跳过**；指定目录模式（SAF 是唯一来源）保持原样 |
| 歌词候选剪枝 | `MediaStoreScanner` 的目录列举缓存改为只保留歌词文件，匹配走 `LyricsMatcher.pickBest` | 旧实现把目录下全部文件名（含几百个 mp3）都拿去跑 `score`，深扫时是 O(歌曲数 × 目录文件数) |
| 云盘「扫描为歌单」并发 | `AliyunScanRules.scan` 同层目录按 `MAX_PARALLEL_DIRS = 4` 一组并发列目录 | 旧实现纯串行 BFS，100 个子目录就是 100+ 个串行 RTT。**归并严格按 BFS 队列顺序**，`files` / `skipped` / 进度回调的观感与旧实现一致 |

### 二、封面（`CoverRepository` / `CoverArt`）

| 点 | 改动 | 为什么 |
| --- | --- | --- |
| 等待者归零即取消 | 新增 `CoverInFlight<T>`（等待者引用计数）；`cover()` 的 in-flight 表值从裸 `Deferred` 换成它 | 单飞任务刻意不挂调用方 Job（多等待者共享），但旧实现因此「没有任何人等了，解码、压缩、写盘也照跑」。快速下滑滚过几百首 = 白解几百张、白写几百个文件 |
| 取消检查点 | `decodeInto` 在每段昂贵工作前 `coroutineContext.ensureActive()` | 阻塞式 IO / 解码不可中断，靠检查点让被放弃的任务尽早退出，不再写盘 |
| 原始读取并发闸门 | `loadRaw` 的 dispatcher 改为 `Dispatchers.IO.limitedParallelism(4)` | 冷缓存快速下滑会瞬间堆起几十个 MMR，`Dispatchers.IO` 默认可并发 64 个 |
| 首帧同步命中 | 新增 `CoverRepository.peek()`（只读位图 LRU，零 IO）；`CoverArt` 的 `remember` 初值直接取它，并删掉无条件 `bitmap = null` | 旧实现每次进入视口先画占位、再协程往返、再重组画图，快速下滑时每行都闪一下 |
| 占位 Brush 复用 | `val coverBrush = remember(coverKey) { AppVisual.coverBrush(coverKey) }` | `coverBrush()` 每次调用都 new 一个 `Brush`，`background()` 会因此每次重组都判定需要重绘 |
| 诊断可验证 | `Stats` 新增 `inFlightNow` / `abandonedDecodes`，`MemoryProbe` 输出「封面请求：在途 / 已放弃」 | 否则改完无法从诊断包证明快速下滑是否真的变省 |

## 红线遵守

- **解码尺寸**：`targetPxFor()` 未改，仍是「`roundToPx()` 物理像素 1:1，只有 ≥512px 给 1.25」。
- **采样**：`decodeScaled` 两段式（`inSampleSize` 粗降 + `fitSize`/`createScaledBitmap` 精确收尾）未改。
- **缓存预算**：仍挂 `Runtime.maxMemory()`（`/16` 夹 4~16MB、`/48` 夹 1~2MB），未写死 MB 数。
- **`Song.stableKey`**：未触碰；`songs.uri` 仍等于 `stableKey`。
- **数据库 schema**：未改，仍 v5，不触发重建。

## 验收

- 单测：`CoverCacheTest` 新增 4 项等待者取消语义；`LibraryDbTest` 新增批量插入 / 更新主键保持；
  `AliyunScanRulesTest` 新增「同层并发但归并有序且不超上限」；`MusicRepositoryMergeTest` 新增指纹格式一致性。
- 诊断包 `[内存]` 段：`封面请求：在途 N 已放弃 M`。快速下滑后 `M` 应明显大于 0，
  且 `封面解码：原始` 次数不应随「滑过的行数」线性增长。
- 真机：冷启动 / 手动重扫的耗时对照；「全部歌曲」快速下滑的掉帧观感。
