# 版本历史

版本号遵循语义化版本；`versionCode` 每发一版 +1，打上 `vX.Y.Z` 的 tag 后由 GitHub Actions 自动构建签名 APK 并创建 Release。

> ⚠️ 标注了「重建数据库」的版本会清空歌单 / 收藏 / 播放统计 / 歌词偏移（详见[权限与更新](权限与更新.html)）。

| 版本 | 主要内容 |
|---|---|
| **1.1.68** | **修复：登录成功后报「账号没有可用的盘（响应里没有任何 drive_id）」**（用户真机：扫码已经成功，读账号信息停在这句）。<br>• **根因**：盘 id 在 `/v2/user/get` 的根字段 `default_drive_id`（同时可能有 `resource_drive_id` / `backup_drive_id`）。OpenList 网页驱动、小雅、aligo 都是从这里取的。`/v2/databox/get_personal_info` 现行响应通常只有容量和会员权益，没有盘 id。1.1.67 只解析后者，登录成功也会被判成「没有盘」。<br>• **改法**：盘 id 改从 `/v2/user/get` 读，`get_personal_info` 里的旧字段 `personal_drive_info` 仍作兜底；`api.alipan.com` 这份用户信息里没有可用盘 id 时，再问一次 `user.aliyundrive.com/v2/user/get`。JSON null 不再被当成盘 id。两个用户接口都失败时，把 401 等真实错误抛出来，不再盖成「没有盘」。<br>• 本版**不重建数据库**（schema 仍为 v5）。 |
| **1.1.67** | **修复：扫码登录成功后全部接口 401「登录状态已失效」—— 扫码令牌改打网页版 API（总根因修复）**（用户真机：登录成功，读账号信息弹「登录状态已失效，请重新扫码授权」）。<br>• **总根因（读 OpenList `alicloud_cs.ts` + AList 网页版驱动源码定位，逐项 curl 实测）**：扫码登录拿到的是**网页版应用**的令牌，只能在网页版 API（`api.alipan.com` 的 `/v2/file/list`、`/v2/file/get_download_url`、`/v2/databox/get_personal_info`、`/v2/user/get`）上用；拿去打开放平台 OpenAPI（`openapi.alipan.com/adrive/v1.0`）一律 401。**1.1.56 以来 app 一直在拿网页令牌打 OpenAPI —— 之前所有「播放失败 / 授权失效」都是这个根因的各种表现**（OpenList 自己的网页驱动调的也是网页 API）。<br>• **API 按令牌来源分家族**：扫码线（CS）→ 网页 API（照 AList 网页版驱动逐字对齐）；自备密钥线（OA）→ OpenAPI（原样保留）。列目录 / 取直链 / 盘信息全部按来源自动选家族，网页线请求补 `Referer/Origin` 头。<br>• **刷新端点修正**：1.1.64 把开放平台 `oauth/access_token` 当「免凭据端点」是误判——实测它必须带 client_id（缺它回 `BadRequest: client_id 不能为空`，OpenList 那条转发线现在也是这么挂的）。真正的免凭据端点是网页账号接口 `auth.alipan.com/v2/account/token`（body 只要 grant_type + refresh_token，实测假 RT 回 `InvalidParameter.RefreshToken`，形态被完整接受）。扫码线刷新现在直连它，失败才落 OpenList 兜底链；「手动粘贴令牌」也改为优先按网页线试。<br>• **盘信息**：网页线改用 `/v2/databox/get_personal_info`（资源库 / 备份盘 id）+ `/v2/user/get`（昵称，多字段名兼容），解析失败给出明确报错。<br>• 单测 **780** 项全绿；本版**不重建数据库**（schema 仍为 v5）。 |
| **1.1.66** | **修复：登录成功后「播放自检」报 BadRequest / 页面永远停在「正在读取账号信息…」**（用户真机反馈：扫码登录成功了，但账号信息读不到，自检报「取直链失败：阿里云盘返回错误：BadRequest」）。<br>• **诊断**：自检报错不是根因 —— 截图里「正在读取账号信息…」还挂着，说明盘 id（drive_id）是空的；拿空 drive_id 去调 `getDownloadUrl`，阿里云盘按约定回 `BadRequest`（请求参数无效）。真正失败的是**前一步「读取账号信息」**，但它的报错只在弹窗出现一次，关掉后页面上只剩一句永远挂着的「正在读取账号信息…」，真实原因就此失踪。<br>• **修法**：①「读取账号信息」失败后**常驻显示失败原因 + 「重试读取账号信息」按钮**，不再一闪而过；②「播放自检」发现盘 id 为空时**自动补拉一次账号信息**，仍失败就把真实原因写进自检结果（「取不到账号的盘 id：xxx」），而不是拿空参数去撞 BadRequest；③「播放本目录全部音频」同样加盘 id 空值守卫；④`BadRequest` 错误码翻译成「请求参数无效（多为 drive_id / file_id 为空或不匹配，不是登录问题）」，不再误导排障方向。<br>• 单测 **776** 项全绿；本版**不重建数据库**（schema 仍为 v5）。 |
| **1.1.65** | **修复：阿里云盘 App 扫不出应用内二维码（内容已验证是正确的）—— 渲染改逐像素 1:1、码放大到满宽、新增「换一张」与自救指引**（用户反馈：阿里云盘 App「识别不到」，微信扫出后跳到 App 下载地址）。<br>• **先给结论：码的内容是对的。** 用户截图里的二维码经解码器验证就是官方登录地址（`passport.aliyundrive.com/qrcodeCheck.htm?lgToken=…`）；微信扫出后跳到阿里云盘 App 的下载地址是**正常现象** —— 这个登录地址只有在阿里云盘 App 的登录流程里打开才有意义，用浏览器（微信内置浏览器也一样）打开一律跳 App 下载。所以「微信跳下载页」不代表码有问题。<br>• **修掉一个渲染硬伤**：位图尺寸（模块数 × 整数倍）几乎不可能恰好等于弹层宽度，此前让 `Image` 把 735px 位图缩到 780px 视图（1.06 倍最近邻），模块边界出现 ±1 像素的不均匀。现在反过来：先按可用像素宽生成位图，再把**视图定成位图的精确尺寸** —— 全链路 1:1，零缩放、零重采样。<br>• **二维码放大**：从固定 260dp 改为**占满弹层可用宽度**（手机上约 340dp），模块越大摄像头越容易合焦、越不怕摩尔纹；并给模块放大倍数加了下限（≥4 像素/模块）。<br>• **弹层新增「换一张」**：怀疑这张码已经死了（扫不上且长时间无反应）时手动换新码；正常过期仍会自动换。<br>• **扫不上自救指引直接写在弹层里**：①调高屏幕亮度、离 20~30cm 再扫；②**截屏后用阿里云盘「扫一扫」选「相册」识别这张截图**（截图是全分辨率，几乎必成）；③点「换一张」再试；④兜底走「网页获取令牌」手动粘贴。<br>• **实验记录**（JVM 复刻渲染链路 + JPEG 压缩污染）：1:1 与 1.06 倍最近邻两种渲染都能被解码器稳定解出 —— 内容层是稳的，摄像头扫不出来更可能是环境因素（屏幕摩尔纹 / 亮度 / 对焦距离），所以这版把能控制的都控制住，并给出不依赖摄像头的出路。<br>• 单测 **775** 项全绿；本版**不重建数据库**（schema 仍为 v5）。 |
| **1.1.64** | **修复：扫码确认后 app 永远停在二维码页 —— 扫码授权改为直连阿里官方，不再经过第三方中转**（用户真机反馈：手机上登录了，app 没反应；重新生成的码又被提示过期）。<br>• **根因（读 OpenList-APIPages 服务端源码定位）**：那个服务的「扫码会话」存在 Cloudflare / EdgeOne Worker 的**内存 Map** 里（`alicloud_cs.ts` 的 `loginSessions = new Map()`）。生成二维码和轮询状态的请求一旦落到不同实例，会话就查不到，轮询固定报 403「会话验证失败」。而 app 把轮询错误**静默吞掉**，于是「手机上确认了、界面毫无动静」；重新生成的码是另一个会话，阿里云盘 App 自然提示「二维码过期」。curl 实测：同一个指纹 2 秒内连发 generate → check，照样「会话验证失败」——与服务端实例分布有关，客户端怎么做都救不回来。<br>• **改法：顺着服务端源码看下去，那三步只是把阿里云官方 passport 接口包了一层**，服务端没有持有任何密钥。现在 app 直连官方：<br>　① `passport.alipan.com/newlogin/qrcode/generate.do` 生成二维码（实测 0.6 秒，取 `codeContent` + 轮询凭据 `ck/t`）；<br>　② `passport.alipan.com/newlogin/qrcode/query.do` 轮询状态（表单 `appName=aliyun_drive&fromSite=52&ck&t`，约 2 秒一次），`NEW / SCANED / CONFIRMED / EXPIRED`；<br>　③ CONFIRMED 时响应里的 `bizExt`（Base64 的 JSON）**直接带着 accessToken / refreshToken / expiresIn**，无需再问第三方。<br>会话数据（ck/t）由本机持有，彻底没有「跨实例丢会话」这回事，也不再依赖任何第三方服务的可用性。请求形态照抄驱动：浏览器 UA + `Referer/Origin` 指向 passport + `X-Requested-With`。<br>• **刷新同样去第三方**：扫码登录线（CS）的令牌改走**官方免凭据端点** `openapi.aliyundrive.com/oauth/access_token`（`grant_type=refresh_token`，OpenList 在线接口背后就是转发这一个请求），成功则完全不经过第三方；失败自动落到 OpenList 兜底链（来源线优先、双站轮换），老的「手动粘贴令牌」路径不受影响。<br>• **轮询失败不再静默**：连续失败 2 次起，弹层显示「连接不稳，正在自动重试（第 n 次）：原因」，成功一次即清零 —— 扫码确认后界面不动时终于有迹可循，而不是无限「已扫码：请在手机上确认授权」。<br>• 测试重写为官方接口的解析用例（生成解析 / 状态映射 / bizExt 解码含空白与垃圾输入 / URL 拼装含参数转义 / passport 请求头），共 **774** 项单测全绿；本版**不重建数据库**（schema 仍为 v5）。 |
| **1.1.63** | **修复：阿里云盘 App 扫不出应用内的二维码（还嫌出码慢）**（用户真机反馈：1.1.62 的码「阿里云盘提示识别不到」，而且「卡了很久才生成」）。<br>• **根因一：白边只有 1 个模块。** 二维码规范要求静区（四周白边）**≥4 个模块**，此前 `MARGIN = 1`，扫码器连定位图形都框不准，阿里云盘 App 直接报「未识别到二维码」。<br>• **根因二：两次非整数缩放把边缘糊掉了。** 先 `encode(content, QR_CODE, 600, 600)` 把 37 个模块硬摊到 600 像素（每模块 16.2 像素，不是整数），再被 Compose Canvas 缩到 220dp 逐格重画一遍（每格约 1.1 像素），抗锯齿于把每个模块的边缘糊成半灰、模块之间 0.5 像素的缝隙直接消失 —— 屏幕上看着仍是二维码，机器读不出来。<br>• **新做法：一个模块一格打底 + 整数倍放大。** `AliyunQrCode` 用 `encode(..., 0, 0, MARGIN = 4)` 拿到「符号本身 + 4 模块静区」的原始矩阵（倍数恒为 1，不做任何小数缩放），再按 `targetPx / 模块数` 向下取整成**整数倍**放大，每个模块恰好 `scale × scale` 个同色像素，边缘永远落在整像素上，不会有过渡灰边。渲染也从「Canvas 逐格 drawRect」改成「直接生成 Bitmap → `Image(FilterQuality.None)`」，画布尺寸 = 位图尺寸，1:1 不重采样。<br>• **显示尺寸 220dp → 260dp**，白边算进图片内，深色主题下也不透出底色；同时**取弹层实际可用宽度上限**（`BoxWithConstraints`）—— 320dp 宽的小屏上弹层正文只有约 216dp，硬塞 260dp 会被裁掉一侧，等于整张码废掉；位图按夹完的尺寸重新生成，显示尺寸与位图尺寸始终一致（否则缩放又会引入重采样）。<br>• **出码慢同时解决**：两个授权站改用**并行竞速**（谁先回用谁，另一个立刻 `cancel()`），等待时间从「.cn 慢就再等 .org」的两段之和，降为两者里较快的那个（实测 1.1 秒出码，之前最长要 8 秒以上）。多出来的服务端会话几分钟后自然过期，无副作用。<br>• 新增 `AliyunQrCodeTest`（11 条）。这组测试不只断言结构 —— 它把生成的像素**直接喂给 ZXing 解码器走完整识别流程**：覆盖 8 种屏幕密度（240~1040 px）、4 模块静区、整数倍放大、模块内无杂色像素、静区纯白、不同内容不同图；解不回来立刻变红。以后任何「看着像二维码但扫不出」的回归都跑得过不去。<br>• 单测 **768** 项全绿；本版**不重建数据库**（schema 仍为 v5）。 |
| **1.1.62** | **新增：网盘「播放自检」**（用户反馈云盘歌单播放失败但只拿到一个 `ERROR_CODE_IO_UNSPECIFIED`，无从定位）。<br>• 阿里云盘页新增「播放自检（测直链）」：取当前目录第一首的直链，发一个只读前 1KB 的真实请求，直接给出结论——「直链可下载：HTTP 206，收到 1024 字节，用时 N ms」/「HTTP 403 没有权限」/「连不上直链服务器（主机名）」。<br>• 一次自检就能把问题缩到一层：直链能下 → 问题在播放器侧（本地缓存或文件格式）；直链下不了 → 网络 / 令牌 / 文件位置问题，与播放器无关。<br>• 顺带说明：本版起每次播放失败都会往诊断日志写一条 `playback-error`（1.1.60 起），「设置 → 关于与诊断 → 查看日志」里能看到错误码、目标主机与完整异常链。 |
| **1.1.61** | **修复：扫码授权一直停在「正在生成二维码…」**（用户真机反馈，1.1.60 仍可复现）。<br>• 主因是域名：授权服务有两个站——`api.oplist.org.cn`（腾讯 EdgeOne 中国大陆节点）与 `api.oplist.org`（全球 Cloudflare）。国内移动网络实测前者 0.6 秒、后者 6 秒以上甚至完全连不上，而我们此前只打全球站。<br>• 改为**国内站优先、全球站兜底**（生成二维码时逐个试，连接 6s / 读 10s 短超时）；选中的站点随会话带回，保证轮询与取令牌打同一个站（会话存在服务端，跨站查不到）。令牌刷新同样改成国内站优先。<br>• 不再静默重试：生成失败立刻把原因显示出来（含两个站各自的失败信息）+「重试」与「网页获取令牌」两个出口；生成超过 3 秒显示「已等待 N 秒」，超过 10 秒提示可换用网页方式——让「慢」和「卡死」可区分。 |
