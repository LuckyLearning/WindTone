# A12 / A13 / A14：磁盘缓存上限、日志合并、DataStore 写合并

> 版本锚点：代码已合入 main（**尚未发版**）。对应 `docs/规划-资源性能续开发.md` §4.1。
> 三项都是「冷热路径卫生」：不改功能语义，只去掉随运行时间累积的写盘与分配。

## A12 · 磁盘缓存硬上限

### 现状盘点（先查有没有，再决定加不加）

| 目录 | 上限 | 结论 |
| --- | --- | --- |
| `covers/` | `trimDisk`（累计 64 张或 30s 检查一次，超配额淘汰） | 已有 |
| `online_media/` | 128MB（`OnlineMediaCache` 配额 + LRU） | 已有 |
| `updates/` | 下载前先删同目录旧包 | 已有 |
| `parallel/` | 陈旧分段文件超时清理 + 收尾全删 | 已有 |
| `crash/` `boot/` | `KEEP` 条数上限 | 已有 |
| **响度缓存文件** | **无上限** | **本次补上** |

### 改动

`LoudnessCache` 从 `ConcurrentHashMap` 改为 **LRU 表**（`LinkedHashMap(accessOrder=true)`），
条数硬顶 `MAX_ENTRIES = 20000`（约 6600 首歌；一首歌落 track / album / 结果三条）。
淘汰按「最久没被问到」—— 用户真回去听那首歌时重新分析一遍即可，这本来就是纯缓存。

两处容易写错的地方：

1. **不能「一淘汰就重写文件」**：表满之后每次 `put` 都会淘汰一条，一条一重写等于
   每条都全量重写一份两万行的文件（比不加上限还糟）。改为**淘汰攒够 64 条**才整理一次，
   期间磁盘最多多留几十行，读取时由「后写覆盖前值」兜底。
2. **锁**：`accessOrder=true` 时连 `get` 都会改结构，读写必须串行（频率是每首歌几次，
   不在绘制热路径上）。

上限做成构造参数，单测传小值，避免测试真的写两万行文件。

## A13 · 事件日志合并

`DiagLog` 仍是 300 条内存环形、不落盘（这部分本来就轻：车机实测 104 条 / 52 分钟）。
真正的浪费是**同一事件被连着报很多次**（导航与桌面来回切时「前台 → 同一个包名」成串出现），
每条都要格式化一次时间戳。

现在紧邻的相同 `(tag, msg)` 会合并成一行并在行尾标 `×N`：

```
13:46:32.803 [FG] 前台 → com.byd.launchermap ×5
```

- 只合并**紧邻**的相同事件，中间插了别的事件就重新开一条（排障靠的是先后顺序）；
- 合并行沿用首次出现的时间戳，不为计数再格式化一次；
- `clear()` 同时重置合并状态，否则清空后第一次写入会被误并进已清掉的上一行。

## A14 · DataStore 写合并

设置页拖悬浮窗的宽度 / 高度 / 位置 / 透明度时，同一个键会在几十毫秒内被写十几次，
每次都开一个 DataStore 事务 —— IO 队列被塞满、设置页跟着迟钝，而中间那些值没有意义。

现在同键写入**合并成一次落盘**（120ms 窗口，只留最后一次）：

- **为什么安全**：读的权威一直是 `SharedPreferences`（setter 里同步 `apply()`，读路径全走它）。
  DataStore 目前只是双写镜像，晚 120ms 落盘不影响任何读取；进程若在窗口内被杀，
  丢的是镜像里的中间值，下次启动 `warmUp` 从 `SharedPreferences` 补齐。
- **保序**：`ioScope` 是 `limitedParallelism(1)` 单线程，flush 与其它写串行，不同键不会乱序。
- flush 采用「循环取空」：拖到一半窗口结束时，新值会被下一轮带走，不会漏。

改动范围刻意限定在**真正会被连拖的六个键**（宽度 / 字幕高度 / 全屏高度 / X / Y / 底板透明度），
其余设置项保持原样 —— 一次点一下的开关不值得引入这层间接。
