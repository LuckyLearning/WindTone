# WindTone 数据层重构规划（v3 → v4）

> 更新：2026-10-14 · 范围：**持久化与数据流**（Room / SharedPreferences / 文件缓存）
> 不含 UI 视觉与播放引擎（另行梳理）。
> 前提：**不为旧的存储格式、老客户端、双写兼容做任何妥协**——按「这个产品最终该长什么样」来设计。

---

## 一、现状体检

### 1.1 一张图看清现在数据散在哪

| 存放处 | 内容 | 问题 |
|---|---|---|
| `songs_cache`（Room） | 扫描结果全集 | 表名是"缓存"，实际是曲库；每次扫描 **全量 clear + insertAll** |
| `play_stats`（Room） | 播放次数 / 最近播放 / 累计时长 / **收藏** | 收藏混在统计里，"清空统计"要特判 SQL 才能保住收藏 |
| `song_overrides`（Room） | 标题/艺术家/专辑覆盖 | 与统计、歌词偏移本属同一首歌的同一类数据，却被切三处 |
| `scanned_folders`（Room） | 目录登记 | 与 `prefs.folderUris` **双真相**，须手工同步 |
| `playlists` / `playlist_songs` | 歌单 | 关联键是超长 URI 字符串 |
| Prefs `folderUris` | 目录列表（带顺序） | 与表双写 |
| Prefs `queue_keys` / `queue_index` | 整个播放队列 | **用分隔符把数组拼成一个巨型字符串**存 KV；队列变了就全量重写 |
| Prefs `last_uri` / `last_pos` | 断点续播 | 与队列表重复职责 |
| Prefs `lyric_offset_song_<hashCode>` | 逐曲歌词偏移 | key 用 `songKey.hashCode()`——**哈希冲突会串歌**；无法枚举、无法随歌清理、清缓存不生效 |
| Prefs `search_history` | 搜索历史 | 数组存 KV，列表操作靠字符串解析 |
| 内存 `PinyinIndex` | 拼音全拼 / 首字母 | 每次扫描后 **全量重建**（含汉字转拼音），冷启动 CPU 大户 |
| 内存 `CoverRepository` | 封面字节 + 解码位图 | **纯内存**，进程一死全部重来，长列表滚动反复解码 |
| 文件 `filesDir/crash/` | 崩溃日志 | ✅ 合理，保持 |
| 文件 `cacheDir/updates/` | 更新 APK | ✅ 合理，保持 |

### 1.2 五个真问题（按严重度）

**① 歌曲主键是超长 URI 字符串。**
`Song.stableKey = uri.toString()`，SAF 树 URI 长这样：

```
content://com.android.externalstorage.documents/tree/primary%3AMusic/document/primary%3AMusic%2F华语%2F周杰伦%2F晴天.mp3
```

它同时是 3 张表的主键、1 张表的复合主键的一部分、LruCache 的 key、MediaItem 的 mediaId、
Compose `key = {}` 的键、拼音索引的键。**同一个字符串在内存里被复制十几份**，
在 SQLite 里被反复做长前缀比较，删除歌曲时要靠 `startsWith` 前缀扫描去清缓存。

**② 扫描落库是"推倒重来"。**
`MusicViewModel.kt:485`：

```kotlin
db.songCacheDao().clear()
db.songCacheDao().insertAll(result.songs.map { SongCacheEntity.from(it) })
```

每次扫描把整张表删干净再插回去。后果：
- 写库时间随曲库规模线性增长（3000 首 ≈ 3000 次插入）；
- **任何真实的行 ID 都不稳定**，所以现在只能靠 URI 当外键；
- 表之间不能建外键/级联，删除联动只能手写（`MusicViewModel.kt:946-950` 连做 4 次 delete + 1 次缓存淘汰）。

**③ 一首歌的状态被切成 4 份存在 3 个地方。**
收藏、播放次数、累计时长在 `play_stats`；标题覆盖在 `song_overrides`；
歌词偏移在 Prefs 的散列 key 里；封面在内存 LruCache 里。
读一次列表要 2 次全表查询 + 1 次 Prefs 读；删一首歌要 4 处清理；**任何一项忘了清就是脏数据**。

**④ Prefs 在干数据库的活。**
`queue_keys`（数组拼字符串）、`folder_uris`（数组）、`search_history`（数组）、
`lyric_offset_song_*`（按 key 散列存储、无界增长）。
这四类都是"成表、按 key 查、会增长"的数据，正是 Room 的形态，却挤在 XML KV 里。

**⑤ 派生数据没有缓存层。**
拼音索引每次全量重建；封面每次冷启动重新解码。这两项是**唯一有用户可感知的卡顿来源**
（低端机冷启动与长列表快速滚动）。

> 说明：把主键从 110 字节的字符串换成 8 字节整数，索引体积能从约 1.3 MB 降到约 100 KB，
> 但这点体积对现代手机**不值得**作为理由。真正的价值是 ②③④ 说的**结构正确性与可维护性**。
> 本规划不靠"省空间"说事。

## 二、设计目标与原则

1. **单一事实源**：每类数据只在一个地方存，不存在"两处都要改"。
2. **关系显式化**：用整数主键 + 真实外键 + `ON DELETE CASCADE`，把"删歌要清哪些地方"交给数据库，不靠人记。
3. **曲库 ≠ 缓存**：扫描结果升格为**曲库**，文件暂时不可见时保留行（软删），收藏/歌单/统计不丢。
4. **写入可增量**：扫描落库、队列保存、时长累计都能增量写，不推倒重来。
5. **状态内聚**：一首歌的本地点状态，一行拿全。
6. **Prefs 只放标量偏好**：全局开关、数值、枚举。凡是成表的一律进 Room。
7. **可搬运**：结构化之后，用户数据要能一键导出/导入（换机、重装、排障）。

### 3.2 表设计（v4 全量）

```sql
-- ① 曲库：扫描得到的媒体元数据。唯一真相。
CREATE TABLE songs (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  uri           TEXT    NOT NULL UNIQUE,      -- 原 stableKey，唯一自然键
  source        TEXT    NOT NULL,             -- MEDIA_STORE / FOLDER / FILE
  title         TEXT    NOT NULL,
  artist        TEXT,
  album         TEXT,
  albumId       INTEGER NOT NULL DEFAULT 0,
  durationMs    INTEGER NOT NULL DEFAULT 0,
  sizeBytes     INTEGER NOT NULL DEFAULT 0,
  mimeType      TEXT,
  displayName   TEXT    NOT NULL,
  path          TEXT,
  folderId      INTEGER REFERENCES folders(id) ON DELETE SET NULL,
  trackNo       INTEGER NOT NULL DEFAULT 0,
  lrcUri        TEXT,
  dateAdded     INTEGER NOT NULL DEFAULT 0,
  lastSeenAt    INTEGER NOT NULL DEFAULT 0,   -- 增量扫描：本轮见到的时间戳
  missingSince  INTEGER NOT NULL DEFAULT 0    -- 0=可用；>0=本机暂不可见（软删）
);
CREATE INDEX idx_songs_folder  ON songs(folderId);
CREATE INDEX idx_songs_album   ON songs(albumId);
CREATE INDEX idx_songs_missing ON songs(missingSince);

-- ② 导入目录：唯一真相，同时取代 scanned_folders 与 prefs.folderUris（含顺序）
CREATE TABLE folders (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  treeUri  TEXT    NOT NULL,                  -- 持久化读权限的树 URI；无则空串
  docId    TEXT    NOT NULL UNIQUE,           -- primary:Music/华语 或 绝对路径
  name     TEXT    NOT NULL,                  -- 叶名（列表标题）
  fullPath TEXT    NOT NULL,                  -- Music/华语（分组消歧）
  sort     INTEGER NOT NULL,                  -- 用户添加顺序
  addedAt  INTEGER NOT NULL,
  songCount INTEGER NOT NULL DEFAULT 0        -- 冗余计数，避免分组时再分组统计
);

-- ③ 每曲一行本地状态：合并原 play_stats + song_overrides + 歌词偏移
CREATE TABLE song_state (
  songId        INTEGER PRIMARY KEY REFERENCES songs(id) ON DELETE CASCADE,
  favorite      INTEGER NOT NULL DEFAULT 0,
  playCount     INTEGER NOT NULL DEFAULT 0,
  lastPlayedAt  INTEGER NOT NULL DEFAULT 0,
  playedMs      INTEGER NOT NULL DEFAULT 0,
  lyricOffsetMs INTEGER NOT NULL DEFAULT 0,
  overrideTitle  TEXT,                        -- NULL = 不覆盖
  overrideArtist TEXT,
  overrideAlbum  TEXT,
  updatedAt     INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_state_favorite ON song_state(favorite) WHERE favorite = 1;

-- ④ 歌单
CREATE TABLE playlists (
  id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL, createdAt INTEGER NOT NULL
);
CREATE TABLE playlist_songs (
  playlistId INTEGER NOT NULL REFERENCES playlists(id) ON DELETE CASCADE,
  songId     INTEGER NOT NULL REFERENCES songs(id)     ON DELETE CASCADE,
  position   INTEGER NOT NULL,
  addedAt    INTEGER NOT NULL,
  PRIMARY KEY (playlistId, songId)
);
CREATE INDEX idx_ps_song ON playlist_songs(songId);

-- ⑤ 队列与播放态
CREATE TABLE queue_songs (
  position INTEGER NOT NULL,
  songId   INTEGER NOT NULL REFERENCES songs(id) ON DELETE CASCADE
);
CREATE INDEX idx_queue_pos ON queue_songs(position);
CREATE TABLE player_state (            -- 永远只有一行
  id            INTEGER PRIMARY KEY CHECK (id = 1),
  currentSongId INTEGER,
  positionMs    INTEGER NOT NULL DEFAULT 0,
  shuffle       INTEGER NOT NULL DEFAULT 0,
  repeatMode    INTEGER NOT NULL DEFAULT 0,
  updatedAt     INTEGER NOT NULL DEFAULT 0
);

-- ⑥ 搜索历史
CREATE TABLE search_history (
  query TEXT PRIMARY KEY, usedAt INTEGER NOT NULL, hits INTEGER NOT NULL DEFAULT 1
);
```

### 3.3 关键决策与理由

| 决策 | 理由 | 代价 |
|---|---|---|
| **`songs` 升格为曲库（不再是缓存）** | 文件暂不可见（SD 卡未挂 / 权限被撤 / 目录临时离线）时用 `missingSince` 软删，收藏/歌单/统计**不丢**；恢复可见后自动回来 | 需要"清理失效歌曲"的维护入口 |
| **`song_state` 三合一宽表** | 读列表一次 JOIN 拿全；删歌一条 CASCADE；"清空统计"只 UPDATE 统计列，天然不影响收藏与编辑 | 高频写（累计时长）与低频写同行；用内存累积 + 定期落库化解 |
| **`queue_songs` + `player_state` 入表** | 队列不再是巨型字符串；播放位置/模式成为**单行可查询状态**，多进程（车机/通知栏/悬浮歌词）读同一真相 | 队列变更时整表事务重写（几百行，< 5 ms，无感） |
| **`folders` 单一事实源** | 消灭 `folderUris` 与登记表的双写；目录顺序、叶名、完整路径、歌曲数一处管理 | 首次读取时需要异步加载（现在是同步 Prefs） |
| **MediaItem.mediaId 仍用 URI 字符串** | Media3 的 `mediaId` 本就是字符串语义，且要在**没有数据库的播放进程**里跨进程比对；换库/重装后也稳定 | 播放侧保留字符串比较（开销可忽略） |
| **`Song` 增加 `dbId`，而 `stableKey` 保留不动** | UI 层 `stableKey` 的用法（Compose key、集合查找、收藏判断）**数百处，零改动**；持久化边界内部才用 `dbId` | 需要一处 `uri → dbId` 的回填 |
| **Prefs 保留 SharedPreferences，不迁 DataStore** | 保留的只剩十几项标量；换 DataStore 收益是"响应式 + 异步"，而调用点有几十处需要同步改异步，性价比低。需要响应式时用 `OnSharedPreferenceChangeListener` + `callbackFlow` 即可轻量达成 | 后续如有强需求再单独评估 |

## 四、性能设计（哪些是真有感的）

| 项 | 做法 | 收益 |
|---|---|---|
| **封面磁盘缓存** ⭐ | `cacheDir/covers/<dbId>-<px>.webp`，LRU 上限 50 MB；内存 LruCache 作为一级，磁盘二级 | 冷启动后长列表滚动**零解码**——目前最明显的掉帧来源 |
| **增量扫描落库** ⭐ | 扫描前记 `scanStart`；用 `INSERT ... ON CONFLICT(uri) DO UPDATE`（Room 2.6 的 `@Upsert`）分批 500 行写入，行尾带 `lastSeenAt = scanStart`；扫完 `UPDATE songs SET missingSince = now WHERE lastSeenAt < scanStart` | 写库从 O(n) 全量降到 O(变更)；**行 ID 稳定**，外键与状态不再断链 |
| **拼音索引增量构建** ⭐ | `PinyinIndex` 按 `dbId` 缓存，只对新出现/改名的歌建索引；搜索面板首次打开时才构建（懒加载） | 冷启动去掉最大一块 CPU 开销 |
| **写库降频** | 累计收听时长在内存累加，切歌 / 暂停 / 每 30 秒 / 进程退出时落库一次（现在每次 tick 都可能写） | 减少 SQLite 写事务与 fsync |
| **读取合并** | 列表加载由「2 次全表查询 + 1 次 Prefs」改为**一条 `LEFT JOIN` 查询** | 冷启动少两次全表扫描 |
| **索引补全** | `songs(folderId)` / `songs(albumId)` / `playlist_songs(songId)` / `queue_songs(position)` / `song_state(favorite) WHERE favorite=1`（部分索引） | 分组、专辑详情、收藏页免全表 |
| **删除联动** | 由「4 处手写 delete + 前缀扫描清缓存」变为一条 `DELETE FROM songs WHERE id = ?`（CASCADE 接管） | 正确性 + 少一次 LruCache 全键扫描 |
| **WAL / 预编译** | Room 默认 WAL；DAO 全部 `suspend`，写操作走单线程串行 | 读写不互斥 |

> 关于"体积"：整数主键省下的空间约 1 MB 量级，**不作为立项理由**，只作为附带好处。

## 五、管理方便（产品能力，不只是代码整洁）

1. **设置页 ·「关于与诊断」新增「导出我的数据」**
   导出 JSON：歌单、收藏、播放统计、歌词偏移、标签编辑，**以 `uri` 为键**（不是 dbId）。
   换机 / 重装 / 排障可一键恢复；这是散 KV 结构下做不到的能力。
2. **数据维护统一收口**（`data/DataMaintenance.kt`）
   - 清理失效歌曲（`missingSince > 0 且超过 N 天`）
   - 清空播放统计（保留收藏）
   - 重置全部本地状态（二次确认）
   - 重建封面缓存 / 清空搜索历史
3. **曲库自检**：索引与表不一致、孤儿 `song_state`、无主目录等，一次扫出报告（诊断页展示）。
4. **文档同步**：`docs/数据库设计-MusicDb.md` 改 schema 必须同步，本规划落地后该文档整体重写为 v4 版。

## 六、迁移方案（v3 → v4，用户数据尽量不丢）

> "不考虑兼容"指的是**不妥协于旧结构**，不是"故意丢用户数据"。迁移代码照写。

**两段式，各司其职：**

**A. 表间搬迁（`Migration(3, 4)`，纯 SQL + 游标）**
1. 建 `folders`：合并 `scanned_folders` 行与 `prefs.folderUris`（后者提供 `sort` 顺序）。
2. 建 `songs`：从 `songs_cache` 逐行搬，`id` 由 SQLite 分配，`missingSince = 0`，`lastSeenAt = 0`。
3. 建 `song_state`：`play_stats`（favorite/playCount/lastPlayedAt/playedMs）与 `song_overrides`（三列覆盖）
   按 `uri` 匹配 `songs.id` 合并入行；无匹配的丢行并记日志。
4. 建 `playlist_songs`：按 uri → id 重建。**歌单里存在但曲库没有的 uri**，
   补一行 `missingSince = now` 的占位 `songs` 行——**绝不因为一次重构就吃掉用户的歌单**。
5. 建 `queue_songs` / `player_state`：暂空（队列在 Prefs，由 B 段写入）。
6. `DROP TABLE songs_cache, play_stats, song_overrides, scanned_folders`。

**B. Prefs 搬迁（一次性任务，`MusicApp` 启动时执行，带 `prefs.doneV4Migration` 标志）**
> Migration 里拿不到 `Context` 的 Prefs，所以 Prefs 的部分必须放在能拿到 Context 的地方做。

1. 遍历全部 `lyric_offset_song_*` 键 → 对每首歌算 `stableKey.hashCode()` 反查 → 写 `song_state.lyricOffsetMs`
   （旧数据本身存在哈希冲突串歌的可能，能救回多少算多少）。
2. `queue_keys`（uri 列表）→ `queue_songs.songId`；`queue_index` → `player_state.currentSongId`；
   `last_pos` → `positionMs`；`shuffle` → `shuffle`。
3. `search_history` → `search_history` 表。
4. 删除已迁移的 Prefs 键（用 `edit().remove()` 逐个移除，并 `apply()`）。

**风险与对策**
| 风险 | 对策 |
|---|---|
| 迁移中途失败半途而废 | Room 迁移本身在事务里，失败自动回滚；Prefs 段用标志位保证幂等（可重入） |
| 3000 首搬迁耗时 | 游标逐行 + 单事务；预估 < 1 s；迁移期间显示启动页 |
| uri → id 映射漏项 | 迁移后跑一次自检：`songs` 行数 == 旧 `songs_cache` 行数 + 占位行数 |
| 回退 | 迁移前把 `music_player.db` 复制为 `music_player_v3.bak`（一次性，成功后可清理） |

**⚠️ 测试抓出的两个真机上必崩的 bug（已修）**

1. `createV4Tables` 里用 `CREATE TABLE IF NOT EXISTS playlist_songs` 建新结构——
   但 v3 已有同名旧表（主键 `songUri`），建表被静默跳过，紧接着建 `songId` 索引直接抛
   `table playlist_songs has no column named songId`。**所有 v3 老用户升级都会在这里失败**（配合
   `fallbackToDestructiveMigration` 甚至会清库）。修法：该表交给 `migratePlaylists` 先 DROP 再重建。
2. 给歌单补位「占位歌」的 INSERT 漏了 `songs` 里 NOT NULL 且无 DDL 默认值的列
   （`albumId` / `durationMs` / `sizeBytes` / `mediaStoreId` / `trackNo` / `dateAdded`），
   抛 `SQLiteConstraintException`。**凡是"歌单里有、曲库里没有"的歌存在就会触发**。

> 教训：手写迁移一定要用「真实旧库 → 跑迁移 → 让 Room 校验 schema」的方式跑通，
> 只做静态比对（对着 json 看 DDL）发现不了这两类错。

**与本文档前九节的差异（实现时调整过的部分）**

- 实体数量落地为 8 张（本文档 §3.2 写 6 张）：多出 `playlists`（v3 已有，沿用）与 `search_history`（顺手迁了）。
- `song_state` 没有按 plan 里"只加一列到 song_overrides"的分步走，而是一步合并成宽表——
  反正 v4 是一次性迁移，分步没有收益。
- 封面磁盘缓存文件名以 `dbId` 为主键（`dbId == 0` 才回退到 `u<uri.hashCode()>`），
  比纯 hashCode 更稳（不会哈希碰撞串图）。
- 迁移测试由"手写一个 Cursor 适配器 + sqlite-jdbc"改为 **Robolectric**：
  能得到真实 Android `Cursor`/`SQLiteDatabase`，且 Room 会做 schema 校验，覆盖面更大。

### 11.2 分域架构

```
MainActivity ── viewModel() × 4
   ├─ LibraryViewModel   （曲库域，约 1250 行）──┐
   ├─ PlayerViewModel    （播放域，接口委托）  ─┤
   ├─ UpdateViewModel    （更新域，接口委托）  ─┼──→ AppContainer（手写服务定位器，by lazy）
   └─ SettingsViewModel  （维护域）            ─┘        │
                                                       ├─ MusicRepository / MusicDb / Prefs
                                                       ├─ SongIndex   ⭐ uri↔dbId + 每曲状态表
                                                       ├─ MessageBus  ⭐ 跨域一次性提示（SharedFlow）
                                                       ├─ PlaybackEngine   （播放域持有者）
                                                       ├─ UpdateRepository （更新域持有者）
                                                       └─ DataMaintenance
```

**关键手法**

| 手法 | 说明 |
|---|---|
| **接口委托**（Kotlin `by`） | `PlaybackEngine : PlayerActions`（37 个方法）、`UpdateRepository : UpdateActions`（12 个）；
`PlayerViewModel` / `UpdateViewModel` 各一行 `PlayerActions by engine` 就把动作整体转出，自己只剩几十行 |
| **`state/` 独立包** | 四个 `*UiState` 从 `ui/` 抽出，避免 `playback` 反向依赖 `ui` |
| **`SongIndex`** | 曲库域与播放域之间**唯一**的共享状态（`idOf(uri)` / `stateOf(song)` / `bump()`），取代原先散在 God Object 里的 `idByUri` + `songStates` |
| **`MessageBus`** | 提示不再借道 `LibraryUiState.message`，播放/更新域不必再认识曲库状态 |
| **引擎生命周期修正** | 引擎升级为应用级单例（无 `onCleared()`）：进度计时器改为「退后台且没在播时自 break」，由 `setAppForeground(true)` / `onIsPlayingChanged` 重新拉起 |
| **主题取色下沉** | `ThemeColorExtractor` 从 `ui/` 移到 `data/`（它本就无 UI 依赖） |
