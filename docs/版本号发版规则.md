# 听风 WindTone 发版规则（版本号 + 发版流程）

> **适用范围**：本项目所有正式发版。版本号固定三段式 `X.Y.Z`，仅允许第三位修订号单向 +1，前两段在当前 **1.2** 线上冻结。
> **本文件是发版规则的唯一真源**，由原《版本号发版规则》与《发版规范：Release 说明与多平台产物》合并而来；两个旧文件已废弃，发版相关事宜一律以本文件为准。
> **当前版本**：`1.2.8`（versionCode 118，2026-10-27）。

---

## 一、版本号规则（X.Y.Z · 仅修订号递增）

> 目的：让版本演进可预期、可审计、无歧义，避免跳号、回退、格式漂移带来的排查与兼容问题。

### 1.1 格式定义

```
X.Y.Z
```

- **X（主版本号 / Major）**：项目级大版本标识。
- **Y（次版本号 / Minor）**：项目级小版本标识。
- **Z（修订号 / Patch）**：**唯一允许在发版时变动的字段**，每发一版 +1。

| 约束项 | 规则 |
| --- | --- |
| 段数 | 固定 3 段，段间用**英文句点 `.`** 分隔，不允许使用其他分隔符 |
| 字符 | 每段为**非负十进制整数**，不允许字母、符号或空格 |
| 前导零 | **禁止**（如 `1.2.05` 非法；`1.2.5` 合法） |
| 取值下限 | 每段 ≥ 0 |
| 取值上限 | 建议单段 ≤ 9999；超过时按实际工程承载上限执行，但**不得回绕归零** |
| 总长度 | 无硬性限制，但应保持简洁可读 |

### 1.2 递增约束（核心）

设上一发版版本为 `X.Y.Z_prev`，本次发版版本为 `X.Y.Z_new`，则必须满足：

```
Z_new = Z_prev + 1
```

即：**每次发版只能将修订号恰好加 1**。

| 约束 | 说明 | 违规示例 |
| --- | --- | --- |
| **禁止跳号** | 只能 +1，不得 +2 及以上 | `1.2.3 → 1.2.5` ✗ |
| **禁止回退** | Z 只能增大，不得减小或复用历史值 | `1.2.4 → 1.2.3` ✗ |
| **前两段冻结** | X、Y 自本规则生效后**永不变更**（当前冻结在 `1.2`） | `1.2.5 → 1.3.5` ✗ |
| **格式一致** | 始终 3 段、无前导零、纯数字 | `1.2.5 → 1.2.05` ✗ |
| **编号唯一** | 每个 Z 值仅对应一次发版，不可重复占用 | 已发 `1.2.7` 后不允许再出 `1.2.7` ✗ |
| **连续无空洞** | 不允许跳过某个 Z 值长期空置后再用 | 发到 `1.2.6` 后直接跳 `1.2.8`，`1.2.7` 永不出现 ✗ |

**每次发版前逐项核对：**

- [ ] 新版本号 = 上一版本号，仅 Z + 1
- [ ] X、Y 与上一版本完全相同
- [ ] 无前导零、无字母/符号、段间仅用 `.`
- [ ] 该 Z 值历史上从未使用过
- [ ] 构建号（Android `versionCode`）已同步递增（单调 +1）

### 1.3 与构建号（versionCode）的映射

| 字段 | 含义 | 本规则下的行为 |
| --- | --- | --- |
| 版本名 `versionName` | 对外展示，如 `1.2.8` | 严格遵循 §1–§2 的 X.Y.Z 与 +1 约束 |
| 构建号 `versionCode` | 系统内部整数，单调递增 | 每发一版 +1（如 117→118→119），与 Z **不必数值相等**，但**必须唯一且递增** |

> 版本号**单一来源**在 `app/build.gradle.kts` 顶部：`val appVersionName = "1.2.8"` 与 `val appVersionCode = 118`。CI（`android-release.yml`）会读取此处并与 tag 做一致性校验。改版本只改这两行——它们**故意不放进 Version Catalog**，因为 `scripts/release.sh` 与 `.github/release-notes` 渲染器都用 `grep` 按这个固定文本格式解析，搬走会连带改掉整条发版链路。
>
> ⚠️ `versionCode` 与 `versionName` 的数值不必相等（历史上 X.Y 曾推进，code 因此不简单地等于 Z）。当前：`1.2.8` / `118`。

### 1.4 适用范围与本产品历史说明

- **为什么只用 patch**：本产品功能形态与架构长期稳定，交付节奏以持续小幅修订为主（Bug 修复、文案/资源微调、小优化、合规更新），不需要用主/次版本对外传达「破坏性变更」或「重大新功能」。团队希望版本号简单、可预期、易追溯。若未来确需变更 X 或 Y，视为**规则升级事件**，须单独评审并书面记录，不属本规则日常发版范畴。
- **本产品历史线（备查）**：立项初版 `1.0.0`；早期在规则固定前曾推进 `1.0.x → 1.1.x → 1.2.x`。**自 2026-10-26 起确定为「只递增第三位」政策**，`1.2` 为冻结线，后续只动 Z。
- **一次回退事故（不再重演）**：曾误发 `1.3.0`（tag 与 Release 都在）后回退到 `1.2.4 → 1.2.5`（code 115 > 114，覆盖安装无碍）。⚠️ 已知遗留：`UpdateChecker.isNewer` 比的是**版本名**，所以装过 `1.3.0` 的设备在应用内查不到 `1.2.5`，需手动装一次包才能恢复自动更新链路；根治需改成按 `versionCode` 比较（尚未改，动之前先问）。

**演进示例（以当前冻结线 `1.2` 为基，正向连续）：**

| 发版次序 | 版本号 | 相对上一版 | 典型发版内容 |
| --- | --- | --- | --- |
| 0（冻结线起点） | `1.2.0` | — | 进入 1.2 线 |
| 1 | `1.2.1` | +1 | 首版后首次修订 |
| … | `1.2.2` … | +1 | 连续修订 |
| 8 | `1.2.8` | +1 | 当前版本 |
| 9 | `1.2.9` | +1 | 末位进位前最后一版 |
| 10 | `1.2.10` | +1 | **跨 9→10 边界，仍仅 +1**（不会出现 `1.3.0`） |
| … | `1.2.11` … | +1 | Z 持续增长，绝不回绕为 0 |

**反例对照（一律禁止）：**

| 起始 | 操作 | 结果 | 违规点 |
| --- | --- | --- | --- |
| `1.2.3` | 跳至 `1.2.5` | ✗ | 跳号（+2） |
| `1.2.4` | 回退 `1.2.3` | ✗ | 回退 |
| `1.2.5` | 改 `1.3.5` | ✗ | 改动前两段的冻结字段 |
| `1.2.5` | 写 `1.2.05` | ✗ | 前导零 |
| `1.2.7` | 已发后再发 `1.2.7` | ✗ | 编号重复占用 |
| `1.2.6` | 跳 `1.2.8`（7 空置） | ✗ | 制造编号空洞 |

## 二、发版产物（多平台 / 多变体）

### 2.1 ABI 分包（4 个包）

本项目的 native 依赖只有 `libandroidx.graphics.path.so`（4 个 ABI 合计约 37 KB），分包带来的体积收益很小（每个包约省几十 KB）。分包的主要价值是让用户在 Releases 页面**按设备架构选择**、并让**车机 / 老设备**拿到明确的 v7a 包，而不是压缩体积。

- 产物（4 个）：
  - `WindTone-v1.2.8-arm64-v8a.apk`（绝大多数手机 / 车机）
  - `WindTone-v1.2.8-armeabi-v7a.apk`（较老的 32 位设备）
  - `WindTone-v1.2.8-x86_64.apk`（模拟器 / ChromeOS / 部分平板）
  - `WindTone-v1.2.8-universal.apk`（全架构合一，拿不准架构时选它）
- **只有 CI 显式传 `-PabiSplits=true` 时才开启分包**：本地开发默认关闭，`assembleDebug` / `installDebug` 仍然只产出一个包，不会让 IDE 部署或调试变麻烦。
- 命名统一由 `androidComponents.onVariants` 处理（ABI 过滤 → `-<abi>`；无过滤 → `-universal`）。

### 2.2 命名规则

```
WindTone-v<X.Y.Z>-<abi>.apk      # 单 ABI 包
WindTone-v<X.Y.Z>-universal.apk  # 全架构包
```

应用内更新（`data/UpdateChecker.kt`）必须同步按本机 ABI 选包，否则会 404：候选顺序为 **本机 ABI → 其它 ABI → universal → 历史单包命名**（最后一条保证 1.0.6 及以前的老版本能升级上来）。设置页「关于」有 **CPU 架构** 行，用户可对照 Releases 里的包名。

### 2.3 分发仓库（公共）

源码仓库已**公开**（`LuckyLearning/WindTone`）。应用内更新仍走公共分发仓，以便匿名、稳定读 `latest.json` 与 APK（不依赖源码仓 GitHub Releases 匿名配额）。因此每个版本在打完 tag、建好源码仓 Release 之后，还要往公共仓库 **`LuckyLearning/Release`** 发一份。

```
Release/
├─ README.md                      # 索引：软件名 / 目录 / 最新版本（脚本自动刷新）
├─ LICENSE
└─ WindTone/                     # 软件名（英文，便于拼直链）
   ├─ latest.json                # ★ 应用内更新读这个
   └─ v1.2.8/                    # 一个版本一个目录，最多保留 5 个
      ├─ WindTone-v1.2.8-arm64-v8a.apk
      ├─ WindTone-v1.2.8-armeabi-v7a.apk
      ├─ WindTone-v1.2.8-x86_64.apk
      ├─ WindTone-v1.2.8-universal.apk
      ├─ notes.md                # 该版本的 Release 说明（模板渲染结果）
      └─ checksums.txt           # sha256sum -c 可直接校验
```

- **保留策略（自动）**：发布新版本时自动删掉第 6 个及更旧的目录（`sort -V` 倒序）。
- **`latest.json`**：客户端散落在旧版本上，清单只能**加可选字段**，不能改名/删字段；应用侧解析按「缺字段给默认值」写（坏数据一律折成「检查失败」，不崩）。
- **发布方式**：以「快照」方式 force push 到公共仓库 `main`（每次一个孤立提交），避免 5 版本 × 4 包 × 3MB 逐版堆积；然后实查远端 `latest.json` 的 `version` 是否已更新。**失败即让工作流红**——宁可发版失败，也不要「源码仓 Release 有包、公共仓库还是旧版本」（应用内更新永远升不上去）。

## 三、发版流程（一键发版 + 验证链）

> 目标：说一句「发版」就能一条命令出结论，不需要人工/AI 再分多次去点 REST、轮询 CI、下包验签。
> 三个脚本分工：`release.sh`（发）→ `verify-release.sh`（验四步）→ `verify_apk.py`（验签）。

### 3.1 命令速查

| 目的 | 命令 |
| --- | --- |
| 发补丁版并**一路验到底**（推荐，阻塞 10~20 分钟） | `bash scripts/release.sh patch --verify` |
| 指定版本号发版 | `bash scripts/release.sh 1.2.9 --verify` |
| 只看看会改什么，不动仓库 | `bash scripts/release.sh patch --dry` |
| 发完只推、不等 CI | `bash scripts/release.sh patch` |
| 事后单独补跑验证链 | `bash scripts/verify-release.sh v1.2.9` |
| CI 已确认跑完，只核后半段 | `bash scripts/verify-release.sh v1.2.9 --skip-ci` |
| 只下包验签 | `python scripts/verify_apk.py v1.2.9` |

开关与位置参数**顺序不限**（`--verify patch` 与 `patch --verify` 等价）。`--verify` 会自动带上四步验证链，所以**建议直接放后台跑**：

```bash
bash scripts/release.sh patch --verify > build/release.log 2>&1 &
```

⚠️ **不要用 `release.sh | tail` 判断成败**——管道会吃掉退出码。以输出里出现 `✓ 已推送 vX.Y.Z（远端已确认）` 为准。

### 3.2 `release.sh` 内部顺序（顺序本身有讲究）

| # | 步骤 | 为什么放在这个位置 |
| --- | --- | --- |
| 1 | 跑 `testDebugUnitTest` | **必须在改版本号之前**。反过来的话单测一失败，仓库就留下「版本号已改但没提交」的脏状态；下次重跑读到的就是已经 +1 过的 code，于是再 +1（2026-10-14 踩出过 code 6）。 |
| 2 | 渲染 Release 说明预览 | 正文来自 `.github/release-notes/template.md`，只替换版本号，**不需要手写也不让 AI 写**。 |
| 3 | 写 `appVersionName` / `appVersionCode` | 版本号唯一出处在 `app/build.gradle.kts` 顶部。 |
| 4 | `commit` + `git tag` | 提交信息固定为 `release: vX.Y.Z`。 |
| 5 | 推送 + **远端 REST 实查** | 不信任推送方返回值（早年 6 次 tag 推送静默失败的根因）。查不到就补推一次，仍查不到就大声失败并给出手动命令。 |
| 6 | （`--verify`）调用 `verify-release.sh` | 见 3.3。 |

### 3.3 四步验证链（每一步都对应一次真实事故）

| # | 检查 | 失败意味着什么 | 不查会怎样 |
| --- | --- | --- | --- |
| ① | 远端 `git/refs/tags/<tag>` 存在 | tag 推送静默失败 | Release 根本没触发，却以为发完了 |
| ② | workflow `conclusion == success` | 构建失败 | 只看资产会看到**上一版**的资产，误判成功 |
| ③ | Release 资产恰好 4 个 ABI | 少打了某个变体 | 部分架构用户装不上 |
| ③b | 公共仓库 `latest.json` 指向本版 | publish 步骤没跑完 | 应用内更新拿不到新版（**不阻塞**，只警告） |
| ④ | APK 签名证书 + 包内版本串 | CI 缺 `KEYSTORE_BASE64` / 发了旧包 | 「构建成功但装不上」 |

第 ④ 步的签名指纹 golden：

```
75EAECCD7CAB0DB4E30170F52091B3BF80AC0F1D6F89235433EBE2B5876E7398
```

⚠️ **为什么必须核包内版本串**：各版本经 zipalign 对齐后**字节数可能完全相同**（1.1.52 / 1.1.53 / 1.1.54 三个 universal 包都是 3414642 字节）。只看大小会误判成「发了旧包」，所以 `verify_apk.py` 会解压 `AndroidManifest.xml` 找 UTF-16LE 编码的版本串再对一次。（本机没有 apksigner / Android SDK，脚本直接解析 APK Signing Block，在其中扫描 X.509 证书 DER 做 SHA-256。）

### 3.4 失败补救手册

| 现象 | 补救 |
| --- | --- |
| ① tag 查不到 | `bash scripts/push.sh origin vX.Y.Z`，再 `bash scripts/verify-release.sh vX.Y.Z --skip-ci` |
| ② workflow 红 | 打开 Actions 看日志；修完在 GitHub 上 `Re-run failed jobs` 即可，不用重发版 |
| ②b workflow 红在「上传构建产物」，日志含 `Artifact storage quota has been hit` | **不是代码问题**：账号的 artifact 配额满了（Free 版 500MB，历史产物按 90 天累积）。已改为 `continue-on-error`（2026-10-30），此步失败不再挡发版；若仍红，检查是否有人把这一步的 `continue-on-error` 去掉了。彻底清理需在 GitHub 网页 Actions → 该 run 的 Artifacts 区手动删除，或等 GitHub 重算（6~12 小时）——本机 PAT **没有 Actions 写权限**（DELETE artifact 返回 403） |
| tag 已在、包没出（Release 0 个资产） | 版本号已进 main 但 CI 没跑完发布。修好原因后**不要改版本号**：`git tag -f vX.Y.Z <新 HEAD>` 重打 + 删远端旧 tag 再推（`DELETE /git/refs/tags/vX.Y.Z`），或重跑该 run |
| ③ 资产不足 4 个 | 同上，通常是构建中断；确认 `RELEASE_REPO_TOKEN` 存在 |
| ③b latest.json 还是旧版 | 等几分钟再 `bash scripts/verify-release.sh vX.Y.Z --skip-ci`；持续不符要查 CI 的 publish 步骤 |
| ④ 签名不匹配 | CI 的 `KEYSTORE_BASE64` / `KEY_*` secrets 丢了，补上后**重新打 tag**（版本号需 +1） |
| 版本号改了但没发成 | 先把 `app/build.gradle.kts` 改回去再重跑，**不要**直接重跑（会 +1 两次） |

### 3.5 环境与权限注意

- 访问 GitHub 必须**出沙箱**（沙箱内 TLS 会被断）：调用方需 `dangerouslyDisableSandbox`。
- 本机 PAT 是 **fine-grained**，只能开 Pages / 重跑工作流 / 改仓库 About 之外的操作；公共仓库 `LuckyLearning/Release` 的读取走匿名 raw 优先，拿不到才回退 contents API。
- Android 构建必须使用**非 GraalVM** 的 JDK 21（`JAVA_HOME` / `WINDTONE_JDK`）。脚本会在检测到 GraalVM 时尝试切到本机可用的 OpenJDK；GraalVM 在 `JdkImageTransform` 阶段必败。
- 网络调用全部加 `--offline`，避免 Gradle 尝试联网解析依赖。

## 四、Release 说明（固定模板，禁止手写 / AI 写文案）

### 4.1 模板机制

- **决定：不再每个版本手写说明。** 正文由固定模板渲染，发版时只替换占位符，人不需要动任何文案。
- 模板文件：`.github/release-notes/template.md`（唯一需要维护的文案）。
- 占位符：`{version}` / `{version_code}` / `{date}`（CI 自动替换）。
- 特例覆盖：`.github/release-notes/v{版本}.md` 存在则用它、忽略模板（平时不建）。
- 渲染内容涵盖：产品一句话介绍、本版变化摘要（固定措辞「若干功能调整与问题修复」）、覆盖升级保留数据说明、适用设备与安装方式、应用内更新入口、隐私声明，以及页脚的 `versionCode` + 构建日期。

### 4.2 约束（红线）

- **发版说明不让 AI 写文案**：`.github/release-notes/template.md` 是唯一正文，`release.sh` 只做版本号替换。
- **历史快照类文档刻意保留原话**（如 `版本历史.md` 中各版本的原始描述、早期 Release 正文）：改历史即伪造史实，不要回去「修正」它们。
- 模板里的安装包名是 ABI 分包命名；历史单包版本（如 `1.0.6` 的 `WindTone-v1.0.6.apk`）页面保持原样不强行套模板。

## 五、一句话总纲

> **X.Y 立项/冻结后不再动，Z 每发版 +1，不跳号、不退号、不改前两段的格式与取值；版本号唯一出处在 `app/build.gradle.kts`，发版只走 `release.sh` 一条命令并跑完四步验证链。**
