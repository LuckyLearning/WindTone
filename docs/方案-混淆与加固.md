# 方案：源码混淆与加固（评估稿）

> 状态：**仅方案与影响评估，未改动构建配置**。待确认后再实施。
> 评估时间：2026-10-25　适用版本：v1.1.96

## 0. 结论先行

建议分三步走，**不建议现在上第三方加固壳**：

| 顺序 | 做什么 | 为什么 |
| --- | --- | --- |
| 第一步 | 打开**应用自身代码**的混淆（现在被 keep 掉了）+ 归档 mapping + 加 retrace 脚本 | 收益确定、风险可控，是本项目唯一"该做但没做"的一项 |
| 第二步 | 加**签名一致性校验**（防改包二次分发） | 同一目标下比加固便宜得多，且不伤自更新链路 |
| 第三步 | 视需要再评估加固 | 加固会改变签名、破坏覆盖安装、且与无障碍/悬浮窗/自更新三处都有冲突面 |

一句话：**开源项目的混淆不提供保密，只抬高改包成本和减小体积；真正防二次分发的是签名校验，不是壳。**

## 1. 现状盘点（实测，不是推测）

| 项 | 现状 | 影响 |
| --- | --- | --- |
| R8 代码压缩 | 已开（`isMinifyEnabled = true`） | 只有第三方库被混淆 |
| 资源压缩 | 已开（`isShrinkResources = true`） | 已生效 |
| 应用自身代码 | **未混淆**：`proguard-rules.pro` 里有 `-keep class com.luckylearning.windtone.** { *; }` | 自家 90+ 个类名、方法名全部原样保留 |
| mapping.txt | **未归档**（CI 只上传 APK） | 一旦开始混淆，崩溃栈/用户回传堆栈将不可读，且**无法事后反推**（R8 的映射不可逆推，必须当时那份） |
| R8 模式 | AGP 8.7.2，full mode 默认开启 | 规则比旧版更严格，反射/序列化类要显式 keep |
| 反射点 | 代码里没有 `Class.forName`；只有 `ForegroundAppService::class.java.name` 这类运行时取名的用法 | 混淆后仍自洽，风险低 |
| 关键组件 | AccessibilityService、BootReceiver、WidgetProvider、TileService、PlaybackService、LyricOverlayService | 组件类名由系统/manifest 引用，需按需 keep（组件本身 R8 会自动保留，但**内部被调用的方法**要注意） |

## 2. 目标与边界

这个仓库是**公开源码**（GitHub 可见），必须先说清楚混淆能带来什么、不能带来什么：

**能带来**

- APK 体积再降一档（当前 3.73MB universal；预计再降 0.2~0.5MB，取决于字符串与类名占比）；
- 抬高"拿 APK 改个名/去广告/塞后门再分发"的门槛；
- 降低被针对性逆向定位关键逻辑（如在线授权、更新源）的成本——只是**抬高成本**，不是阻止。

**不能带来**

- 不能保护算法或密钥：源码本身是公开的，混淆只作用于编译产物；
- 不能阻止有人从源码自行编译一个功能相同的分叉（这是开源许可允许的）；
- 不能替代签名校验：改包者可以直接 patch 掉混淆后的判断。

## 3. 方案分层

### L1 应用代码混淆（推荐先做）

**做法**

1. 删掉 `-keep class com.luckylearning.windtone.** { *; }`，改为**精准 keep**：
   - 组件清单（Service / Receiver / Provider / TileService / Activity）：主要靠 manifest 与 R8 自动保留，但要检查内部回调方法名是否被反射调用；
   - Room：`@Entity` / `RoomDatabase` 子类已有规则，保留；
   - 枚举 `values()/valueOf()`：已有规则，保留；
   - pinyin4j：classpath 读数据表，已有规则，保留；
   - `BuildConfig`：`VERSION_NAME` 等字段被大量读取，保留字段名（否则反射/序列化会炸）；
   - Compose / Media3：消费者规则已覆盖，无需手写。
2. `-repackageclasses` 可选（把剩余类挪进统一包名），进一步压缩常量池。
3. 保留 `SourceFile,LineNumberTable`（已有）——没有行号和源文件名，mapping 也拼不回可读栈。

**收益**：体积下降；类名/方法名不可读；改包者需要先脱壳级逆推。

**影响与代价**

| 影响面 | 具体表现 | 应对 |
| --- | --- | --- |
| 崩溃定位 | `CrashLog` 存的栈是混淆后的（`a.a.b`） | 归档 mapping + 提供 `retrace` 脚本；诊断包里附带 `mapping 版本号`，便于按版本反查 |
| 诊断包 | `[环境]` 里的类名/字段、`[事件日志]` 的 tag 不受影响（tag 是字符串常量）；但堆栈段会变 | 同上；文档里写清"混淆版本需 retrace" |
| 系统无障碍页 | 显示的服务名取自 manifest 的 `android:label`（`@string/app_name`），不是类名 | 无影响 |
| 桌面快捷方式/小组件深链 | 依赖 `action` 字符串与 `Intent` extra，不依赖类名 | 无影响 |
| 自更新 | 比较的是 `versionName/versionCode`，不依赖类名 | 无影响 |
| 构建时间 | R8 full mode 下多几十秒 | 可接受 |

**工作量**：改动 1 处配置 + 补 3~5 条 keep + 全量回归一轮；预计半天（不含真机回归）。

### L2 字符串加密 / 资源混淆（不建议现在做）

- 常见做法是接 StringFog 类插件或自定义 ASM 插桩，把字符串常量加密、运行时解密。
- **冲突**：与 R8 内联、与 Compose 的字符串常量、与诊断包里的中文文案（大量）叠加，容易把"可读的诊断信息"也加密掉；且这类插桩一旦与 R8 full mode 同用，常见结果是编译通过、运行期才炸。
- **收益有限**：改包者真正想要的是"跳过校验"，而校验逻辑靠 L3 就够。
- 结论：**搁置**。等 L1 稳定运行 1~2 个版本后再评估。

### L3 签名与完整性校验（推荐与 L1 同期做）

**做法**

1. 启动时读取本 APK 的签名证书 SHA-256，与内置白名单比对（当前证书指纹 `75EAEC…7398`，release.sh 已在验这条）；
2. 校验失败**不崩溃**，只做降级：禁用"检查更新 / 在线播放授权"等联网便利功能，并在诊断页显示一行红字；
3. 可选：校验 `versionCode` 与 `latest.json` 的一致性，防止旧版重放。

**为什么它比加固有效**：改包者必须重签名才能安装，重签名就必然与原证书不符；而加固壳是"提高逆向成本"，签名校验是"直接让改包版本不能用关键功能"。

**影响**

- 自己编译的 debug 包、社区自编译包会被判为"非官方"→ 必须**只降级、不封禁**，否则开源分支的用户体验会被误伤；
- 签名校验代码本身也要 keep（不能被混淆删掉）；
- 与 CI 的签名一致性：release.sh 已验签，可复用同一白名单，避免两处硬编码不一致。

### L4 第三方加固壳（360 加固 / 腾讯乐固 / 梆梆等）

**收益**：DEX 整体加密、反调试、反注入，比 R8 强一个数量级的逆向门槛。

**代价（逐条都是本项目会踩到的）**

1. **必须重签名**：加固产物用你的证书重签，但**证书里的 APK 内容变了**；更要紧的是——如果哪天证书换过（或加固方代签），老用户安装新包会因签名不一致而**安装失败，必须先卸载**，卸载=歌单与偏好全丢。这是加固最容易被低估的一点。
2. **启动变慢**：首次启动要解密 DEX，DiLink 这类车机 CPU 一般，冷启动可能多 0.5~1.5s；本应用已经有过"车机首帧黑屏"的历史（BootDiagView 就是为解决它而写），加固会让这条历史风险复活。
3. **与系统组件冲突面大**：无障碍服务、悬浮窗、前台服务、开机自启、桌面小组件、磁贴——这些恰恰是加固壳最容易出问题的区域（壳会改 `Application`、改类加载器）。本项目**核心功能全压在这几条上**。
4. **崩溃栈几乎不可读**：壳会打乱行号与类名，mapping 也可能失效；用户回传的堆栈价值大幅下降，而我们目前所有远程排查都依赖它。
5. **CI 侵入**：多数加固要账号/联网/客户端，需要在发布流水线里插一步"上传→加固→下载→重签→验签"，release.sh 的四步验证链要重写；加固失败=发版卡住。
6. **开源一致性下降**：APK 与公开源码不再一一对应，社区无法复现构建（可复现构建是开源项目的重要信任基础）。

**结论**：现阶段**不做**。若未来确实要上，建议：先在独立渠道（如"车机专版"）灰度 → 保留一条不加固的官方渠道 → 加固版只在你自己的分发仓库上线。

## 4. 影响矩阵（一页看清）

| 维度 | L1 混淆 | L3 签名校验 | L4 加固 |
| --- | --- | --- | --- |
| 包体 | −0.2~0.5MB | ≈0 | +2~4MB |
| 冷启动 | ≈0 | +20~50ms（读签名） | +0.5~1.5s |
| 崩溃可定位性 | 需 retrace（有 mapping 就没问题） | 无影响 | **显著变差** |
| 覆盖安装 | 无影响 | 无影响 | **可能失败（需卸载）** |
| 无障碍/悬浮窗/自更新 | 需回归 | 需回归降级分支 | **高风险，需逐项验** |
| CI 改动 | 加"归档 mapping"一步 | 无 | 需接加固流水线 |
| 维护成本 | 低（keep 规则随代码演进） | 低 | 高（每次发版多一段链路） |
| 开源一致性 | 保持 | 保持 | 下降 |

## 5. 无论选哪条，都必须先补的三件事

1. **mapping 归档**：CI 里把 `app/build/outputs/mapping/release/mapping.txt` 与 APK 一起上传为 artifact，并在 Release 页面附一份按版本命名的副本（`mapping-v1.1.96.txt`）。**没有这一步，L1 一上线就等于自断排查能力。**
2. **retrace 脚本**：`scripts/retrace.sh <mapping> <stack.txt>`，封装 `retrace` 命令行；同时更新诊断包说明"混淆版本请附 mapping 版本号"。
3. **回归清单**（本项目的"高危区"）：无障碍开启/重启掉线恢复、悬浮窗收起/展开与双钮、按应用隐藏、开机自启、桌面小组件、磁贴、在线播放（阿里云盘/百度网盘）、自更新下载安装、崩溃日志导出。这份清单必须逐项过一遍，不能只看"能启动"。

## 6. 建议的落地节奏与回滚

| 阶段 | 内容 | 验收 | 回滚 |
| --- | --- | --- | --- |
| W1 | L1 配置 + mapping 归档 + retrace 脚本 | 单测全绿；真机跑第 5 节回归清单；用 retrace 还原一条故意制造的崩溃栈 | 恢复全局 keep 一行即可 |
| W2 | L3 签名校验（只降级不封禁） | 官方包功能全开；自编译包只掉"联网便利功能"且有提示 | 加开关关掉校验 |
| 观察期 | 连续 2 个版本观察崩溃可定位性 | 用户回传的栈能在 5 分钟内 retrace 出可读位置 | — |
| 之后 | 再评估 L2 / L4 | — | — |

## 7. 需要你拍板的三件事

1. **L1 是否现在做**：我建议做，但要连同 mapping 归档一起，否则不划算。
2. **L3 的降级策略**：签名不符时是"只提示"还是"禁用检查更新与在线播放"？我建议后者——既能阻止改包分发，又不会误伤自编译用户的核心播放功能。
3. **L4 是否永久放弃**：我的建议是"至少今年不做"；如果你更在意防逆向而不是工程成本，我们再单独排期，并把上表里的 6 条代价逐条做验证。

## 8. 附：本项目当前的混淆规则现状（供对照）

```
-keepattributes SourceFile,LineNumberTable      # 保留行号，好事
-renamesourcefileattribute SourceFile
-keepattributes *Annotation*, Signature, InnerClasses, EnclosingMethod
-keep class com.luckylearning.windtone.** { *; } # ← 这一行让自家代码完全不混淆
-keepclassmembers enum * { values(); valueOf(); }
-keep class net.sourceforge.pinyin4j.** { *; }
-keep class * extends androidx.room.RoomDatabase { <init>(); }
-keep @androidx.room.Entity class * { *; }
-dontwarn androidx.media3.**
```

删掉第四行是本方案 L1 的核心动作；其余规则保留。
