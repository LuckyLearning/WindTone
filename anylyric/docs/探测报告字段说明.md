# AnyLyric 探测报告字段说明

> 适用版本：0.2.10 及以后（含 L0b 取词通道、在线补词、掉线看门狗）。
> 对应代码：`diag/Probe.kt`、`diag/DiagRules.kt`、`diag/ResourceSampler.kt`、`diag/Perf.kt`、`session/SessionHub.publishSnapshot()`。

这份文档解释探测报告里**每一行、每一个字段**的含义，以及怎么用它判断问题出在播放器、权限、窗口还是本应用。

---

## 1. 报告从哪里来、怎么导出

设置页 →「通道探测」→ 打开「调试日志」→ 在别的应用里播放 → 回到探测页。

调试打开后：

- 探测页每 **2 秒**重建一次报告；
- 歌词链路每次刷新都会更新快照（`Probe.snapshot`）；
- 资源占用每 **60 秒**往日志里写一条 `[资源]`（首条延迟 3 秒）。

导出有三条**设备内**路径，都不需要 adb / USB / 开发者选项：

| 按钮 | 结果 |
|---|---|
| 分享 | 拉起系统分享面板，文本 + 文件（可选） |
| 复制 | 整份报告进剪贴板 |
| 保存 | 写入公共下载目录 `Downloads/anylyric-probe-yyyyMMdd-HHmmss.txt` |
| 清空 | 清空日志缓冲并重置计数器（`Perf.reset()`） |

> 调试关闭时 Probe **零采集**：不写日志、不采样资源、不构建快照、不做跨进程权限查询。探测页会直接显示「调试日志未开启」。

## 2. 报告整体结构

```
=== AnyLyric probe report ===      ← 头部：时间 / 版本 / 设备
[ENV]                              ← 屏幕与字体
[PERMISSION]                       ← 两项权限 + degraded
[SESSION]                          ← 会话数、选中会话、展示用歌名/歌手
[METADATA KEYS]                    ← 元数据键全表（文本值）
[NOTIFICATION FIELDS]              ← 通知文本字段
[TITLE TIMELINE]                   ← 原始 TITLE 变化时间线 + 伪歌名判定
[SOURCE ATTEMPTS]                  ← L0 / L0b / L1 / L2 逐层尝试
[CLOCK]                            ← 进度回跳、是否带时间轴
[WINDOW]                           ← 悬浮窗是否挂上/量到
[HIDE]                             ← 按应用隐藏：无障碍状态 / 前台包名 / 是否让位
[RENDER]                           ← 最后一次真正推给窗口的文本
[PROCESS]                          ← 日志缓冲状态
[RESOURCE]                         ← 内存 / CPU / 线程 / FD / GC
[WORK]                             ← 工作量计数器
=== CONCLUSION ===                 ← 自动判因（code + evidence）
[LOG]                              ← 最近 300 条分段日志
```

前 14 段是「事实」，`CONCLUSION` 是按固定优先级给出的第一条结论，`[LOG]` 是原始事件流。

---

## 3. 头部

| 字段 | 含义 | 备注 |
|---|---|---|
| `time` | 生成报告时的墙钟时间（epoch 毫秒） | 用来和用户描述的时间点对齐 |
| `uptime` | 从 Probe 初始化到现在的时长，格式 `+123s456` | **不是开机时长**，进程重启会归零 |
| `version` | AnyLyric 版本名（`BuildConfig.VERSION_NAME`） | 例如 `0.2.10` |
| `api` | `Build.VERSION.SDK_INT` | 例如 31 / 33 / 37 |
| `device` | `厂商/型号` | 例如 `HONOR/PGT-AN00` |
| `brand` | `Build.BRAND` | 用于识别 BYD / DiLink 等车机 |
| `package` | `applicationId` | 正式包 `com.anylyric`，调试包带 `.debug` |

## 4. `[ENV]`

| 字段 | 含义 | 为什么关心 |
|---|---|---|
| `displayCount` | 系统报告的显示器数量 | 多屏车机上，悬浮窗输出屏与比例换算会受影响 |
| `fontScale` | 系统字体缩放倍率 | 影响 `sp → px` 换算与文字宽度，异常值会让排版看起来「偏大/偏小」 |

## 5. `[PERMISSION]`

```text
listenerGranted=true listenerConnected=false degraded=true canDrawOverlays=true
```

| 字段 | 含义 |
|---|---|
| `listenerGranted` | **系统设置里是否勾选**了通知使用权（读 `enabled_notification_listeners`） |
| `listenerConnected` | **本进程此刻是否被系统绑定**（`onListenerConnected` 是否来过） |
| `degraded` | `listenerGranted && !listenerConnected`：授权在、服务没绑 |
| `canDrawOverlays` | 是否有「显示在其他应用上层」权限 |

两个关键区别：

- **已授权 ≠ 已连接**。应用被回收后重新打开，前者仍为 true，后者要等系统重新 bind。
- `degraded=true` **不等于不能用**：`getActiveSessions` 的权限边界是授权列表，L0/L1 与进度照常工作，缺的只有 L2（通知文本）与推送事件，由 8 秒一次的低频查询代偿。

---

## 6. `[SESSION]`

| 字段 | 含义 |
|---|---|
| `sessions` | `getActiveSessions()` 返回的会话数 |
| `playing` | 其中 `PlaybackState.STATE_PLAYING` 的数量 |
| `chosen` | 实际选中的会话包名；`none` 表示没有 |
| `title` | **展示用**歌名（多键兜底 + 粘住 + BYD 兜底后的值），trim 后截断 40 字 |
| `artist` | **展示用**歌手，同上 |
| `duration` | 时长（毫秒）；`< 10 秒`的值已按「秒」纠正为毫秒 |

> `title` 不是原始 TITLE。原始 TITLE 的逐次变化看 `[TITLE TIMELINE]`。
> 如果两者不一致，通常说明：原始 TITLE 是歌词（伪歌名），展示层用了兜底的真实歌名，或者新值为空时粘住了上一次的值。

会话选择顺序：优先 `STATE_PLAYING`；没有播放中的会话时，优先「有 TITLE」的会话；再按 `lastPositionUpdateTime` 取最新。

## 7. `[METADATA KEYS] count=N`

逐行 `键 = 值预览`。

| 项 | 说明 |
|---|---|
| `count` | `MediaMetadata.keySet()` 的键数量 |
| 键 | 播放器写入的原始键名，例如 `android.media.metadata.TITLE`、`com.byd.mediacenter.metadata.LYRICS` |
| 值预览 | 只取**文本类**值，换行压成空格，截断 60 字；位图/数字显示为 `null` |

为什么不解码封面：`Bitmap` 跨进程传输是车机 OOM 的常见来源，而本应用不需要封面。键名仍然全量保留，用来判断「播放器到底把歌词放在哪个键」。

---

## 8. `[NOTIFICATION FIELDS]`

当前选中会话那个包的通知文本字段：

| 键 | 来源 |
|---|---|
| `android.title` | `Notification.EXTRA_TITLE` |
| `android.text` | `Notification.EXTRA_TEXT` |
| `android.subText` | `Notification.EXTRA_SUB_TEXT` |
| `android.bigText` | `Notification.EXTRA_BIG_TEXT`（展开态正文，可能多行） |
| `android.tickerText` | `Notification.tickerText`（不是 extras 常量） |

这些是 L2 通道的输入。若 `android.bigText` 是多行歌词，可能被当成逐行流；若只有歌名/歌手，L2 会判定为「没有歌词」。

## 9. `[TITLE TIMELINE] events=N pseudo=<bool>`

```text
[TITLE TIMELINE] events=4 pseudo=true
  1834021 我穿上大头皮鞋
  1837012 走过那条熟悉的街
```

| 字段 | 含义 |
|---|---|
| `events` | 当前 15 秒窗口内记录的 TITLE 变化条数 |
| `pseudo` | 判定结果是否为 **PSEUDO**（伪歌名） |
| 每行 `atMs` | `SystemClock.elapsedRealtime()`，**开机以来的毫秒**，不是墙钟 |
| 每行 `title` | 原始 TITLE，trim 后截断 40 字 |

PSEUDO 的判据（三条同时成立）：

1. 15 秒窗口内 TITLE 变化 ≥ 2 次；
2. `duration / mediaId / artist / 专辑 / 音轨` 指纹未变（变了就是真换歌）；
3. 相邻变化间隔的中位数 ≤ 8 秒。

`pseudo=false` 不代表标题一定是真歌名：刚换歌的前几秒是 `UNKNOWN`，长间奏也可能翻回 `STABLE`。展示层还有一道强信号：展示值与任一歌词行完全相同时不显示标题。

## 10. `[SOURCE ATTEMPTS]`

责任链按顺序尝试，**第一个产出非空行集的来源获胜**；无论成败，每次尝试都记录在这里。

```text
  L0 HIT lines=27 cost=1ms
  L0b MISS reason=no_extras cost=0ms
  L2 MISS reason=no_notification cost=0ms
```

| 字段 | 含义 |
|---|---|
| `HIT` | 命中，`lines=` 解析出的行数，`cost=` 本次耗时（毫秒） |
| `MISS` | 未命中，`reason=` 原因（见下表） |

### 来源 ID

| ID | 通道 | 说明 |
|---|---|---|
| `L0` | `MediaMetadata` 自定义键 | 键名白名单（lyric/lrc/歌词）+ `[mm:ss.xx]` 内容特征；支持 JSON 解包 |
| `L0b` | `PlaybackState.extras` | `lyrics` 整段 LRC；`lrc_line_1~3` 滚动三行（第 1 行为当前句） |
| `L1` | `TITLE` 逐行推送 | 已判定 PSEUDO 时，把 TITLE 缓冲当作歌词行 |
| `L2` | 媒体通知文本 | 含 LRC 特征则解析；多行正文在 PSEUDO 时作为逐行流 |
| `ONLINE` | 在线补词 | **不在这里出现**：它是异步旁路，命中时只体现在 `hitSource` / 状态卡 |

### 未命中原因

| reason | 来源 | 含义 |
|---|---|---|
| `no_metadata` | L0 | 根本没有 `MediaMetadata` |
| `no_string_value` | L0 | 元数据里没有字符串值（只有 Bitmap / Long） |
| `no_lyric_key` | L0 | 有字符串，但没有歌词键、内容也不像 LRC |
| `no_extras` | L0b | `PlaybackState.extras` 为空 |
| `no_lyric_field` | L0b | extras 里没有 `lyrics` / `lrc_line_*` |
| `stable_title` | L1 | TITLE 没有高频变化，不是逐行流 |
| `too_few_lines` | L1 | 已判 PSEUDO，但缓冲不足 2 行 |
| `no_notification` | L2 | 这个包没有通知文本 |
| `no_lyric_text` | L2 | 通知文本里没有歌词特征、也不是多行 |

> `L0` / `L0b` / `L1` 的 `cost` 正常应在 0~2ms；持续偏高说明解析缓存没生效或歌词文本异常大。

## 11. `[CLOCK]`

```text
[CLOCK] jumps=0 timed=true l1OnlyOnPause=false
```

| 字段 | 含义 |
|---|---|
| `jumps` | 进度**回跳**计数：回退超过 5 秒，且不在换歌/重播附近 |
| `timed` | 当前歌词是否**全部带时间轴** |
| `l1OnlyOnPause` | TITLE 是否只在暂停时更新（AVRCP 门控特征） |

判读：

- `jumps` 只有配合 `timed=true` 才有意义；L1 逐行流按最后一行定位，与 progress 无关，回跳不会让歌词错位。
- `jumps` 持续增长 + `timed=true` → 带时间轴的歌词可能对不齐，原因通常在发布端。
- `l1OnlyOnPause=true` + `pseudo=true` + `hit=L1` → 发布端在 AVRCP 门控下丢更新（见判因码 `AVRCP_GATE`）。

## 12. `[WINDOW]` 与 `[HIDE]`

```text
[WINDOW] attached=true measured=true hiddenByRule=false
[HIDE] a11yConnected=true events=32 enabled=true hiddenApps=3
  foreground=com.example.video inList=true suppressed=false ownUi=false
```

`[WINDOW]`：

| 字段 | 含义 |
|---|---|
| `attached` | 歌词窗的 View 是否已挂到 `WindowManager` |
| `measured` | View 是否已经有非零宽高（`width>0 && height>0`） |
| `hiddenByRule` | 是否因「无歌词时隐藏」被主动收起（开启该开关且当前没有歌词行） |

`[HIDE]`（v0.2.11，按应用隐藏）：

| 字段 | 含义 |
|---|---|
| `a11yConnected` | 无障碍服务**此刻是否真的连着**；`false` 而系统里勾着 = 被 ROM 杀了 |
| `events` | 服务实际订阅的事件位掩码。**必须含 32**（`TYPE_WINDOW_STATE_CHANGED`）；缺了就是订阅没生效，一个事件都收不到 |
| `enabled` | 「按应用隐藏」总开关 |
| `hiddenApps` | 名单里勾了几个应用 |
| `foreground` | 最近一次稳定下来的前台包名；`unknown` = 服务连上后还没收到过窗口切换 |
| `inList` | 这个前台包名是否命中名单 |
| `suppressed` | 悬浮窗此刻是否正在让位（本应用界面可见也算） |
| `ownUi` | 让位是因为**本应用自己的界面**在屏上（设置页/诊断页），而不是名单命中 |

读法：

- `inList=true` 但 `suppressed=false` → 判定链没跑通，看 `enabled` / 开关是否真的落盘；
- `foreground=unknown` + `events` 不含 32 → 订阅没生效（ROM 覆盖了 XML），服务是「连着的哑巴」；
- `foreground=unknown` + `events=32` → 订阅正常但系统不派发事件，或用户从没切过应用；
- `a11yConnected=false` → 勾了没用：服务没在跑，重新去系统设置关开一次；
- `suppressed=true` 且 `ownUi=true` → 你在看 AnyLyric 自己的页面，不是故障；
- `suppressed=true` 且 `inList=true` → 按应用隐藏正常工作。

> 设置页「按应用隐藏 → 实时前台应用」里能直接看到最近切过的 20 个应用包名，
> 列表为空本身就说明「一个事件都没收到」，比翻报告更快。

`attached=false` 而 `hit` 有值 → 歌词取到了但窗口没挂上，优先查悬浮窗权限/窗口被移除。
`attached=true` 但 `measured=false` → 挂上了却没量到尺寸，多半是布局问题。

## 13. `[RENDER]`

这是**最后一次真正交给 `WindowManager` 的文本**，用来回答「歌词已经取到了，为什么屏幕上没有」。

```text
[RENDER] text=我穿上大头皮鞋 context=2 title=沙漠骆驼 prompt=false attached=true measured=true
```

| 字段 | 含义 |
|---|---|
| `text` | 当前行，截断 24 字 |
| `context` | 上下文行条数（副行） |
| `title` | 标题，截断 12 字；`none` 表示这一帧不显示标题 |
| `prompt` | 是否是提示语（「正在获取歌词…」/「暂无歌词」） |
| `attached` / `measured` | 推送当时的窗口状态 |

同一份内容不会被重复记录（内部按 `text/context/title` 的哈希去重），所以 `[RENDER]` 只会在内容真正变化时出现。

---

## 14. `[PROCESS]`

| 字段 | 含义 |
|---|---|
| `cachedLogLines` | 日志缓冲当前条数，上限 **300** |
| `dropped` | 因超过上限被丢弃的条数 |

`dropped` 持续增长说明事件量很大或很久没清日志。日志是环形缓冲，只保留最近 300 条，不是完整历史。

## 15. `[RESOURCE]`

```text
[RESOURCE]
  pss=110.4MB private=44.1MB java=7.5MB/384.0MB native=31.1MB
  code=33.0MB graphics=11.0MB system=22.0MB  (code/graphics/system 为共享部分按比例分摊)
  cpu=26% threads=33 fd=248 gc=6
  uptime=37s
```

| 字段 | 来源 | 含义 |
|---|---|---|
| `pss` | `Debug.getMemoryInfo().totalPss` | 整进程 PSS（MB）。**含共享库按比例分摊**，不等于「本应用独占」；ROM 裁剪时显示 `?` |
| `private` | `totalPrivateDirty` | 本进程**独占**的脏页（MB）。进程被杀后能真正回收的量 —— 这是最该看的数字 |
| `code` | `summary.code` | 代码段（dex / oat / .so 映射）分摊到本进程的部分 |
| `graphics` | `summary.graphics` | 图形缓冲（GPU / SurfaceFlinger 分配的 buffer）。**悬浮窗越大这块越大** |
| `system` | `summary.system` | 系统侧共享部分（ashmem、字体、系统库） |
| `java=used/max` | `Runtime` | Java 堆已用 / 上限（MB） |
| `native` | `Debug.getNativeHeapAllocatedSize()` | 原生堆已分配（MB），含 Skia 字体与渲染缓存 |
| `cpu` | `/proc/self/stat` 的 utime+stime 差值 | **区间均值**（%），不是瞬时值；首次或读不到为 `?` |
| `threads` | `/proc/self/status` 的 `Threads:` | 线程数 |
| `fd` | `/proc/self/fd` 条目数 | 文件描述符数 |
| `gc` | `Debug.getRuntimeStat("art.gc.gc-count")` | ART GC 累计次数 |
| `uptime` | `elapsedRealtime - 进程启动时刻` | 本进程已运行秒数 |

判读：

- **先看 `private`，不要只看 `pss`**：`pss=110MB` 而 `private=44MB` 时，另外 66MB 是
  代码段、字体、图形驱动等共享页按比例摊过来的，任何应用都会背这份账。
  车机上「PSS 100 多」本身不是异常。
- **`graphics` 偏大**：悬浮窗尺寸大 → GPU buffer 大。把窗口调小是唯一有效的降法。
- **`pss` 不涨而 `java` 堆涨**：内存还没被回收压力逼着还，不一定是泄漏。
- **`threads` / `fd` 只增不减**：泄漏嫌疑最大（网络连接、线程池、窗口 surface）。
- **`gc` 频繁**：歌词切句可能发顿。
- **`cpu` 高但 `[WORK]` 很低**：单点开销（某段代码贵），不是事件量放大。
- **`cpu` 高且 `[WORK]` 也高**：事件量放大（例如每秒一条通知把责任链当轮询跑）。

## 16. `[WORK]`

```text
[WORK] refresh=1820 chain=46 skip=1712 render=44 tick=37
```

| 字段 | 含义 |
|---|---|
| `refresh` | 进入刷新的次数（事件合并之后） |
| `chain` | 真正重跑责任链（读元数据 + 解析歌词）的次数 |
| `skip` | 被短路掉的次数（外来通知、内容未变） |
| `render` | 把文本推给悬浮层的次数 |
| `tick` | 定时行推进的次数 |

判读：

- `refresh` 高、`chain` 低 → 短路/指纹生效，健康。
- `chain` 接近 `refresh` → 输入一直在变（事件量放大，或输入指纹失效）。
- `render` 远小于 `chain` → 内容没变时悬浮层自己又挡了一层，正常。

`[资源]` 日志行的尾部还会带**分钟增量**：`| +refresh=… +chain=… +skip=… +render=… +tick=…`。一行里同时看「这分钟烧了多少 CPU」和「这分钟干了多少活」。

---

## 17. `=== CONCLUSION ===`

```text
=== CONCLUSION ===
code=OK
evidence=hit=L1
```

| 字段 | 含义 |
|---|---|
| `code` | 判因码（见下表） |
| `evidence` | 触发该判因的关键事实 |

判因按固定优先级取**第一条命中**：**权限 → 会话 → 通道 → 时钟 → 窗口**。

### 判因码速查

| code | 触发条件 | 含义与处理 |
|---|---|---|
| `PERMISSION_LISTENER` | `listenerGranted=false` | 通知使用权未授予；去系统设置勾选 |
| `LISTENER_UNBOUND` | 已授权、未连接，且 `hit=none` | 已授权未绑定；点「重新连接」，仍不行就关开一次开关 |
| `PERMISSION_OVERLAY` | `canDrawOverlays=false` | 缺悬浮窗权限 |
| `NO_SESSION` | `sessions=0` | **播放器侧事实**：没有任何应用发布媒体会话 |
| `SESSION_INACTIVE` | `sessions>0, playing=0` | 有会话但没在播放 |
| `AVRCP_GATE` | `pseudo && hit=L1 && l1OnlyOnPause` | **发布端限制**：只在暂停时更新标题，不是本应用能修的 |
| `NO_CHANNEL` | `hit=none` | **播放器侧事实**：完全没有暴露歌词通道 |
| `CLOCK_UNSTABLE` | `jumps>2 && timed=true` | 发布端进度回跳，带时间轴的歌词可能对不齐 |
| `OVERLAY_NOT_ATTACHED` | `viewAttached=false` | 悬浮层没挂上 |
| `OVERLAY_NOT_MEASURED` | `measured=false` | 挂上但没尺寸 |
| `HIDDEN_BY_RULE` | `hiddenByRule=true` | 开了「无歌词时隐藏」且当前没有歌词行，悬浮窗被主动收起 |
| `HIDDEN_BY_APP` | `suppressed=true` | 按应用隐藏生效中：前台应用在名单里（或是本应用自己的界面）。**这是预期行为**，退出该应用自动恢复 |
| `OK` | 以上都不命中 | 正常；`evidence` 里带 `hit=<来源>`，降级时附 `degraded=true` |

> 最容易误报成 Bug 的两类：`NO_SESSION` / `NO_CHANNEL` 是播放器没给；`AVRCP_GATE` 是发布端在蓝牙门控下丢更新。这三类都不是 AnyLyric 的故障。

## 18. `[LOG]`

段名与用途：

| 段名 | 记录什么 |
|---|---|
| `[权限]` | 授权/连接状态变化、`requestRebind` |
| `[会话]` | 会话绑定、BYD 媒体控制回调的元数据 |
| `[通知]` | 哪些包有通知文本、字段名 |
| `[歌词]` | 判定变化、责任链结果、在线补词请求/命中 |
| `[渲染]` | 推给窗口的文本（与 `[RENDER]` 同源） |
| `[时钟]` | 进度回跳等时钟事件 |
| `[资源]` | 每分钟一条资源采样 + 工作量增量 |
| `[更新]` | 检查更新、下载、安装 |
| `[设置跳转]` | 跳系统设置的成功/失败 |
| `[隐藏]` | 按应用隐藏的让位/恢复，附「自身界面 / 名单命中 / 前台包名」 |

每行格式：`[段] +123s456 message`，时间同样是「Probe 启动以来的时长」。

## 19. 常见组合怎么读

| 现象 | 报告特征 | 结论 |
|---|---|---|
| 没有任何歌词 | `sessions=0` | 播放器没发会话（`NO_SESSION`） |
| 有会话但没歌词 | `sessions>0 playing=0` | 没在播放（`SESSION_INACTIVE`） |
| 有会话、在播放、没歌词 | `[SOURCE ATTEMPTS]` 全 MISS | 播放器没给任何通道（`NO_CHANNEL`）；看 `[METADATA KEYS]` 确认键名 |
| 只有标题、没有歌词行 | `pseudo=false` + L1 `stable_title` | TITLE 是稳定歌名，不是逐行流 |
| 歌词只有两句 | `L1 HIT lines=2` 或 `L2 HIT lines=2` | 来源能力上限，不是 bug |
| 标题在滚歌词 | `pseudo=true` / 展示值与歌词行相同 | 伪歌名；展示层应隐藏标题或改用 BYD 兜底 |
| 歌词取到了但屏幕没有 | `hit=L1` 但 `attached=false` | 窗口没挂上（`OVERLAY_NOT_ATTACHED`） |
| 屏幕有窗口但空白 | `attached=true measured=false` | 布局没量到尺寸 |
| 卡顿/发热 | `[WORK]` 与 `[RESOURCE]` 对照 | 看是事件量放大还是单点开销 |
| 歌词对不齐 | `jumps>2 timed=true` | 发布端进度回跳（`CLOCK_UNSTABLE`） |
| 切到某应用后歌词消失 | `[HIDE] inList=true suppressed=true` | 按应用隐藏生效（`HIDDEN_BY_APP`），预期行为 |
| 勾了名单却不隐藏 | `a11yConnected=false` | 无障碍服务没在跑，去系统设置关开一次 |
| 服务连着但从不隐藏 | `foreground=unknown` | 看 `events` 是否含 32：不含 = 订阅没生效；含 = 系统没派发事件 |
| 服务开着、名单也有，仍不隐藏 | `inList=true suppressed=false` | 判定链没跑（开关没落盘 / `enabled=false`） |

## 20. 字段口径与限制

1. **时间基准**：头部 `time` 是墙钟；`uptime`、`[TITLE TIMELINE]` 的 `atMs`、`[LOG]` 的时间戳都是**开机/进程内的相对时间**，跨设备对比请用差值。
2. **截断**：`[SESSION]` 40 字、`[METADATA KEYS]` 60 字、`[RENDER]` 文本 24 字、标题 12 字、`[TITLE TIMELINE]` 40 字。报告里不会出现整段歌词或文件路径。
3. **不采集**：封面 Bitmap、音频、通知正文以外的内容、用户输入。
4. **零采集**：调试关闭时 Probe 不采样、不计数、不构建快照。
5. **快照 + 环形日志**：报告是「当前事实 + 最近 300 条日志」，不是完整历史；要更长的时间线请在复现前后各导出一次。
6. **`token` 与隐私**：报告不含 token、不含账号信息；分享前可自行检查 `[METADATA KEYS]` 是否包含你不想外传的曲目信息。

## 21. 一页版：拿到报告先看什么

1. `CONCLUSION.code` —— 先看结论码，`OK` / `LISTENER_UNBOUND` / 其它。
2. `[PERMISSION]` —— 两个权限 + `degraded`。
3. `[SESSION]` —— 有没有会话、有没有在播放、选中了谁。
4. `[SOURCE ATTEMPTS]` —— 哪一层命中/为什么没命中。
5. `[TITLE TIMELINE]` —— 原始 TITLE 是不是歌词。
6. `[WINDOW]` + `[HIDE]` + `[RENDER]` —— 取到了为什么没显示（窗口没挂上？还是按应用隐藏了？）。
7. `[WORK]` + `[RESOURCE]` —— 性能和长跑资源。
