# AnyLyric

WindTone 的轻量分支：旁听车机上任意播放器**已经发布**的媒体会话，把播放器自己暴露的歌词画到悬浮层。

**它不是播放器** —— 不播放声音、不申请音频焦点、不控制播放、不读文件。网络**只**用于应用内更新。
0.2.11 起多了一个**无障碍服务**，但它只做一件事：收窗口切换事件拿前台包名（`canRetrieveWindowContent=false`，
读不到屏幕内容），用于「按应用隐藏悬浮窗」；不开也能用全部其它功能。

- 包名：`com.anylyric`（与 `:app` 不同，可同机共存）
- 平台：Android 12+（`minSdk = 31`）
- 运行时依赖：仅 `kotlin-stdlib`

## 一期范围（当前实现）

只做「直接获取」，用来验证车机播放器到底有没有把歌词放进可被旁观的系统通道。

| 通道 | 来源 | 判定 |
|---|---|---|
| L0 | `MediaMetadata` 自定义键 | 键名白名单（lyric / lrc / 歌词）+ `[mm:ss.xx]` 内容特征双判，解析出 ≥2 行才采纳；值若是 JSON（`{"lyrics":...}`）先解包 |
| L0b | `PlaybackState.extras`（`lyrics` / `lrc_line_1~3`） | 整段 LRC 解析出 ≥2 行才采纳；滚动三行取第 1 行为当前句。BYD 车机走这条 |
| L1 | `TITLE` 逐行推送 | 曲目指纹（包名 / duration / mediaId / artist / 专辑 / 音轨）不变而 `TITLE` 在 8 秒内变化 ≥2 次 → 判定「伪歌名」，切逐行模式 |
| L2 | 媒体通知文本 | 含 LRC 特征则解析；或多行正文且已判定伪歌名时作为逐行流 |

**不实现**：L3 本地 `.lrc`、L4 在线／无障碍**取词**。二者只在 `LyricsSource` 接口上预留挂载点，**不写实现**。
`INTERNET` 权限只给「检查更新」用，歌词链路始终不联网、不读本地文件。

> 0.2.11 新增的无障碍服务与「无障碍取词」是两件事：它只订阅窗口切换事件读取 `packageName`，
> 不解析节点树、不读文本、不碰其它应用的内容，仅用于「按应用隐藏悬浮窗」。

因此多数普通播放器会显示「暂无歌词」——这是**一期预期结果，不是缺陷**。一期验收标准是通道探测报告，不是歌词覆盖率。

### 歌名 / 歌手：稳定获取

真机上「时不时取不到歌名」有两个来源：只读 `TITLE` / `ARTIST`（不少播放器只填 `DISPLAY_TITLE` /
`ALBUM_ARTIST` / `DISPLAY_SUBTITLE`），以及换歌 / 切前后台的一瞬间元数据为空、上一次值被直接覆盖。

现在的取值顺序：

1. **标准元数据多键兜底**：`TITLE` → `DISPLAY_TITLE`；`ARTIST` → `ALBUM_ARTIST` → `DISPLAY_SUBTITLE`。
2. **粘住上次非空值**：新值为空时保留上一次展示值；只有换歌（mediaId / duration / album / track
   变化）或会话切换才清空。换歌瞬间不会再出现标题消失。
3. **BYD 兜底**：BYD 车机标准会话常常很稀疏，绑定 `com.byd.mediacontroller` 的第三方 SDK
   （只读 Bundle，不调播放控制），拿媒体中心的真实 TITLE / ARTIST / LYRICS。仅在 BYD 系包名生效，
   避免切到别的播放器后沿用上一首的歌名。
4. **伪歌名判定仍看原始 TITLE**：展示值会被粘住或替换成 BYD 的歌名，拿它判定就丢了「一行一变」
   的特征；原始 TITLE 与歌词行相同则展示层隐藏标题。

### 首屏延迟的两条硬约束（v0.1.1）

1. **缓冲必须早于判定**：每次 TITLE 变化就进 L1 缓冲，不等判定成立。否则判定前看到的
   第一二句会被永久丢弃，首屏要多等一个歌词周期。判定成立时缓冲整体回填。
2. **判定只要两条证据**：`minChanges = 2`（8 秒内两个不同标题）。要求三条会让首屏
   白等 6~15 秒。两条就够的前提是曲目指纹未变，且「歌名 → 歌名 - 播放中」这类
   后缀变体已单独排除（`TitleTimeline.isTrivialVariant`）。

空窗期的文案也分两种：标题还在动 → 「正在获取歌词…」；标题停住 20 秒仍无行 → 「暂无歌词」。

## 权限状态：两个事实，不能混用

`listenerGranted`（系统设置里是否勾选，读 `enabled_notification_listeners`）与
`listenerConnected`（系统此刻是否已绑定服务）是两件事。只判后者会在「应用关闭后
重新打开」时误报未授予——系统还没 bind，但权限一直勾着，用户进设置看到的也是勾选态。

| 状态 | 界面 | 动作 |
|---|---|---|
| 已授权已连接 | 绿色「已连接」 | 正常显示歌词 |
| 已授权未绑定 | 琥珀「已授权，正在等待系统连接…」 | 自动 `requestRebind`（5 秒节流）+ 约 10 秒轮询；**仍照常出歌词**（见下） |
| 已授权未绑定超 9 秒 | 红色「已授权，但系统没有自动恢复连接」 | 文案改指手工：点「系统设置」把开关关掉再打开一次 |
| 未授权 | 红色「未授予」 | 「去开启」+「系统设置」两个入口 |

**「未绑定」不等于「不能用」**：`getActiveSessions` 的权限边界是授权列表，不要求
`NotificationListenerService` 实例已连接；`MediaController` 的回调也走 MediaSession
自己的 binder。因此未绑定期间 L0/L1 与进度照常工作，缺的只有 L2（通知文本）与推送
事件——由 8 秒一次的低频查询代偿，服务一连上就停。这才是「关掉应用再打开」后仍能出
歌词的原因。

**界面按「是否真的出了歌词」分两种状态**（0.2.14）：已经拿到歌词时显示
「已授权 · 降级运行（歌词正常）」**绿色**，而不是黄色「正在等待系统连接」——
后者会让用户以为坏了，一遍遍去系统设置里关开那个本来就开着的开关。

两个按钮始终并存：修复动作（去开启 / 重新连接）与「系统设置」。「系统设置」优先直跳
本应用的通知使用权详情页（API 30+），失败才退回列表页——手工关开是自动重绑失效时
唯一的自救路径，不该让用户在一长串应用里翻找。

判因分两条：`PERMISSION_LISTENER`（没勾）与 `LISTENER_UNBOUND`（勾着但没绑上，且没拿到
歌词）。已拿到歌词则判 `OK`，只在 evidence 里标 `degraded`。

**无障碍服务是第三个事实**（0.2.11）：「系统设置里勾着」与「服务此刻连着」同样会分叉 ——
车机上服务被 ROM 杀掉、勾还留着是常态。所以设置页「按应用隐藏」那行分三档显示：
未开启 / 已授权但当前未连接 / 已开启，探测报告的 `[HIDE] a11yConnected` 用的是更严的后者。

## 外观与位置（v0.2.1）

外观收敛为**数据**：`OverlayStyle` 一个不可变数据类，默认值只在 `OverlayDefaults`
定义一次，每个可调项都能「重置」写回那里。`LyricRenderer` 只负责把参数变成像素。

| 预设 | 底色 | 描边 | 行数 | 适用 |
|---|---|---|---|---|
| 极简描边 `STRIPE` | 全透明 | 有（2px 轮廓） | 2 | 不想遮挡车机界面 |
| 玻璃胶囊 `GLASS`（默认） | 55% | 无 | 2 | 通用 |
| 实底字条 `SOLID` | 86% | 无 | 2 | 地图 / 视频类复杂背景 |
| 导航态 `NAVI` | 86% | 无 | 1（居中） | 行车中只看一句 |

可调项：字号 14–40sp、行数 1–4（加减步进，v0.2.5 由「1/2/3 三选一」改掉）、对齐左/中/右、
背景不透明度 0–100%、圆角 0–28dp、文字描边、加粗、切换淡入 0/320ms、无歌词时隐藏。
副行从 0.2.7 起**固定为继续的歌词**，不再提供选项 —— 用户原话「没有副行内容这个选项了，
就是继续的歌词」；旧 `Secondary` 枚举与「下一句 / 上一句 / 关闭」三选一随之删除。
左侧那条「播放状态条」在 0.2.4 一并删掉了 —— 它占 10dp 宽度、只在「放/不放」之间变个
颜色，用户反馈是「左边一道亮条很碍眼」。

**行数是总行数，副行是一组行**（v0.2.6）：0.2.5 及以前副行只有一条文本，因此把行数调到
3、4 时屏幕上仍然只有「当前行 + 下一行」两行 —— 预算给了，没文本可填。现在
`SessionHub` 一次给出最多 3 条相邻行，`LinePlan` 按 `maxLines` 的总预算铺：当前行先按需要
折行，剩下的预算逐条给上下文行（单测 `LinePlanTest` 守着这条边界）。空行不占预算。

**标题行**（v0.2.6）：`歌名 · 歌手` 居中画在歌词上方（默认）或下方，**字号、颜色、位置、
开关都独立于正文**，也不占 `maxLines` 的歌词行预算。标题过长按可用宽度做省略，不会为了它
把整块窗口撑宽。原「副行内容 = 歌名 · 歌手」这一档随之删除 —— 同一条信息摆两处只会打架。

**向右错位**：上下文行整体右移 0–48dp（`lineOffsetDp`），形成阶梯感，只在左对齐下生效。
渲染器会把偏移夹在内容宽内，固定宽度 + 长句时不会被顶出窗口；自适应宽度则把偏移量算进
所需宽度，不会裁字。

**标题不再跟着歌词滚**（v0.2.7）：伪歌名判定成立时，元数据 TITLE 本身就是播放器逐行推来的
歌词 —— 旧实现拿它拼「歌名 · 歌手」，标题行就变成了另一份滚动的歌词（真机 0.2.6 反馈
「歌曲名和歌手信息取错了，现在是歌词」）。现在 PSEUDO 期间标题直接不显示，判定恢复
STABLE（真换歌）后标题回来。

0.2.7 真机（HONOR / com.salt.music）仍见「歌曲名取成歌词」，补了一道**强信号**：
TITLE 文本与任何一条已知歌词行完全相同 → 无论判定是什么都不当标题。这是为了堵两个漏网：
换歌后的头几秒判定还是 UNKNOWN（PSEUDO 要两条以上样本），以及长间奏把中位间隔拉大后
判定可能翻回 STABLE —— 这两个窗口里 TITLE 都是歌词。设置页「正在播放」也同步：
TITLE 与歌词相同时显示「TITLE 是歌词（伪歌名）」而不是那句话本身。

**副行锚点与回退**（v0.2.7）：无时间轴的行集由来源显式给出「当前行是第几行」
（`LyricResult.Hit.currentLineIndex`）—— L2 的多行通知第一行才是当前句，旧实现一律取末行，
等于把下一句当当前句画；L1 缓冲末行才是当前句。当前行之后凑不出任何行时（逐行流的常态）
回退取前面的行补位，行数预算不再空着。只能拿到两行（两行通知形态）就按两行显示 ——
这是来源的能力上限，不是 bug。

**四色全部可自定义**（v0.2.5）：当前行、其它行、背景、描边各一项，点「自定义颜色」开
HSV 取色器（色相 / 饱和度 / 亮度三根滑杆 + 实时预览 + 十六进制值）。v0.2.1~0.2.4 那一组
固定色板（`OverlayPalette`）已删除：用户要的是任意颜色，十来颗圆点给不出这个自由度，
还把整屏塞满。描边色单独可调是必须的 —— 浅底 + 深字的组合下，默认黑描边会把字糊成一团。
其它行的实际不透明度还会再乘「副行不透明度」；背景色再乘「背景不透明度」。
**换预设不会冲掉自定义颜色**，只改观感参数。

**位置存比例不存像素**（`xRatio/yRatio ∈ [0,1]`，横竖屏各一套）：

- 换分辨率、改字号、横竖屏切换都不会让窗口跑出屏幕；
- 拖动时先钳制像素再换算回比例，所以**拖不出屏幕**——旧实现能把窗口拖到屏外并落盘，
  用户看到的是「悬浮窗消失了」，无法自查；
- 松手距边 24dp 内自动吸附；v0.2.6 删掉了九宫格「快捷位置」—— 它与「进入编辑态后直接拖」
  重复，还多占六行屏高。

**宽高也可调**（v0.2.1）：`widthRatio / heightRatio` 同样存比例，`0` 表示自适应。
两种调法 —— 编辑态拖四角（对角固定、实时预览、松手换算成比例落盘），或在设置页用
「宽度 / 高度」步进（宽 24–98%，高 4–60%）。固定宽度的额外好处是每句歌词不再改变
窗口尺寸，`requestLayout` 不再牵动窗口重排。

**编辑态**：虚线框 + 四角把手 + 底部提示条，右下角圆形「✓」退出，**12 秒无操作自动退出**
（v0.2.3，原来 60 秒）。编辑态是全应用**唯一**吃触摸的状态，所以这个值等价于「用户最多被挡多久」：
调完尺寸顺手去导航上点一下，落点正好在歌词框里就会点不动，等半分钟才恢复——现场反馈就是
「悬浮窗挡着点不到下面」。

**触摸穿透的保证**（v0.2.3）：
- 非编辑态同时挂 `FLAG_NOT_TOUCHABLE` 与 `FLAG_NOT_TOUCH_MODAL`。前者已足够，但车厂 ROM 里
  出现过只认后者、仍按可触摸窗口分发的版本；
- 退出编辑态**不是**改 flags，而是把窗口拆了重建 —— 新窗口添加时就带 `NOT_TOUCHABLE`，
  比 `updateViewLayout` 改 flag 可靠（车机上出现过改完 flag 输入通道没跟着变）；
- 离开设置页（回桌面 / 切导航）时若还停在编辑态，`onStop` 里强制退出；
- 长按弹出四个操作：锁定位置 / 隐藏 10 分钟 / 打开设置 / 复制当前行。菜单是自绘在同一
  个 View 里的，不起 Dialog —— 车机上弹窗会抢焦点，而且部分 ROM 上直接用 application
  context 弹 Dialog 会 `BadTokenException`。

**左侧收起把手**（v0.2.1，v0.2.5 重做落点）：独立小窗口（30×72dp），竖向居中贴歌词窗左缘，
点一下收起 / 展开。拆成独立窗口是必须的——歌词窗默认 `FLAG_NOT_TOUCHABLE`，为了这颗按钮
把整窗改成可触摸会让歌词区域变成一个挡手的黑洞。把手可随时关掉（设置 → 位置与尺寸）；
关掉时收起功能同时失效，避免留下一个没法恢复的收起态。

**把手不压歌词**（v0.2.5）：两种形态由 `OverlayGeometry.handlePlacement` 纯函数决定 ——
放得下就**挂在窗外**（与窗口零重叠）；歌词窗已经贴到屏幕左边、外面没地方时，把手**塞进窗内**，
同时让 `LyricRenderer.setLeftInset()` 把文字整体右移一条把手宽（内衬 = 把手宽 + 间隙），
按钮落在让出来的空白里。两种形态之间有一道 5dp 迟滞：塞进窗内会让窗口变宽、按比例定位时
左边缘又跟着左移，没有迟滞就会来回抖，屏幕上看到的是连续跳动。

**切换动效**（v0.2.1）：不再改窗口 `alpha`（那会让整块 surface 重新合成，车机上表现为
掉帧），改为 View 内双缓冲交叉淡入——旧行在前 35% 退干净、新行从 12% 浮上来，两条
曲线刻意错开以免叠成重影。一个复用的 `ValueAnimator` + `DecelerateInterpolator`，
提示语 / 菜单 / 编辑态都不淡入。

**空状态**与正文分开：提示语用小一号、约 70% 透明度，第二行补「歌名 · 歌手」，
不会再出现「取到了没取到看起来一样」。

## 应用内更新（v0.2.0）

更新读**公共分发仓库的静态文件**，不碰 GitHub API（无需鉴权，raw 还是 CDN，不占 API 配额）：

```
https://raw.githubusercontent.com/LuckyLearning/Release/main/AnyLyric/latest.json
…/AnyLyric/v0.2.0/AnyLyric-v0.2.0.apk
```

- **按 `versionCode` 判断新旧**，清单缺 `versionCode` 才退回版本名比较 —— 只比版本名会有
  「装过更高版本名、看不到较低版本」的死角；
- **七条线路可选**（v0.2.5，`DownloadRoute`）：自动 / 直连 GitHub / jsDelivr / gh-proxy.com /
  ghproxy.net / ghfast.top / gitmirror，**检查与下载共用同一套线路**，设置页「关于与更新 →
  更新线路」可锁定某一条并附一句适用说明（选了「直连」就不会偷偷退回镜像）。
  自动模式下线路清单是 `fastly.jsdelivr → gcore.jsdelivr → cdn.jsdelivr → gh-proxy.com →
  ghproxy.net → ghfast.top → hub.gitmirror.com → 官方 raw`；
- **多线路并行竞速**（v0.2.3）：所有线路同时发，谁先给出「有新版本」用谁；只拿到
  「已是最新」时继续等别的线路，最后取**版本最高**的结论 —— 镜像的旧缓存盖不掉真正的
  新版。总预算 10 秒，超时就用已拿到的结论。
  改之前是串行、每条 6 秒连接 + 15 秒读超时，最坏要等 40 秒以上，用户只会觉得「点了没反应」。
  手动锁定单条线路时不竞速、直接跑（只起一个线程）；
- ⚠️ **jsDelivr 对 `@main` 的缓存不认 query 参数**：清单 URL 上加 `?t=<时间戳>` 也绕不过 CDN
  缓存（这是 v0.2.3「明明发了新版却说已是最新」的真凶，只加时间戳并不解决）。现在的对策是
  「多线路并行 + 取最高版本」，让官方 raw 与各镜像互相校正；发版后几分钟内镜像仍可能返回旧清单，
  属正常现象，不是检查逻辑坏了；
- 清单版本比本机低时，界面显示**本机版本**，不出现「已是最新（比自己还低）」；
- 下载后三层校验：长度下限 + `PK` 头、清单声明的大小、SHA-256。镜像线路越多越需要摘要这层；
- 安装包经自带的 `ApkProvider`（`content://<applicationId>.apkfiles/…`）交给系统安装器，
  **不引 AndroidX**（FileProvider 在 androidx.core 里，为一个功能引整库不划算）；
  同时带 `FLAG_GRANT_READ_URI_PERMISSION` 与 `clipData`，否则部分 ROM 的安装器读不到文件；
- 「安装未知应用」没开时先把用户送到授权页，而不是等他点完再失败；
- 失败一律在**设置页里**显示成人话并写进探测报告 `[更新]` 段（含耗时与命中线路）——
  车机上不看 adb 也能自查。

检查与下载都在工作线程，结果回主线程；进度只在百分比变化时刷界面。

## 在线补词（可选，默认关闭）

本地通道（L0 / L0b / L1 / L2）全部 miss 时，可选的在线兜底会按「歌名 + 歌手」去酷狗、
网易云取一份带时间轴的歌词。**这是歌词链路里唯一的联网出口**，只有用户在「行为」里打开
「在线补词」才生效，默认关闭。

- **单线程 + 总预算 12 秒**：同一时刻只有一个请求，不会因为频繁换歌堆并发连接；
- **缓存有界**：按 64 首 LRU 缓存 30 分钟（成功与失败都缓存），响应体上限 512 KB；
- **本地优先**：只补本地取不到的，本地命中一定覆盖在线结果；换歌即作废旧结果；
- **可清空**：关掉开关会立即清空缓存与已显示的在线歌词。

## 排障：不依赖 adb

设置页 → 通道探测 → 打开调试日志 → 在别的应用里播放 → 回到探测页看结论卡。

报告里每一段、每个字段的含义见 **[`docs/探测报告字段说明.md`](docs/探测报告字段说明.md)**（含来源 ID、未命中原因、判因码与常见组合读法）。

导出有三条**设备内**路径：

1. 复制到剪贴板
2. 保存到公共下载目录（车机文件管理器可浏览）
3. 系统分享面板

**不需要连接电脑、不需要开发者选项、不需要 USB 调试。**

自动判因按「权限 → 会话 → 通道 → 时钟 → 窗口」顺序给出第一条结论。其中四条会明确标注为**播放器侧事实**，不当成本应用故障：

- 会话数为 0：播放器未发布 MediaSession
- 三通道全未命中：播放器未暴露任何歌词通道
- 标题仅在暂停时更新：发布端 AVRCP 门控丢更新
- 进度多次小幅回跳：发布端进度不自洽（**仅当歌词带时间轴时才报**；L1 逐行流按最后一行定位，与 progress 无关，不应误伤）

另有两条属于**授权侧**，需分开：未勾选（`PERMISSION_LISTENER`，去授权）与勾着但服务未绑定（`LISTENER_UNBOUND`，点重新连接）。

**资源占用**（v0.2.1）：报告里多一段 `[RESOURCE]`，日志里每分钟一条 `[资源]`。数字全部来自本进程可读的接口，不需要任何权限：

| 字段 | 来源 | 用途 |
|---|---|---|
| `pss` | `Debug.getMemoryInfo` | 整进程实际占用；PSS 不涨而 Java 堆涨 = 还没被系统回收压力逼着还 |
| `java` / `native` | `Runtime` / `Debug.getNativeHeapAllocatedSize` | 区分「Kotlin 侧持有」与「原生/图形侧持有」 |
| `cpu` | `/proc/self/stat` 的 utime+stime 差值 | 区间均值，回答「是不是在空转烧 CPU」 |
| `threads` / `fd` | `/proc/self/status`、`/proc/self/fd` | 线程或 FD 只增不减 = 泄漏 |
| `gc` | `Debug.getRuntimeStat("art.gc.gc-count")` | 频繁 GC 会让歌词切句发顿 |

拿不到的值显示 `?`，不显示 `-1` —— 后者会被当成真实数据。

**工作量计数器**（本次）：报告里新增 `[WORK]` 段，日志里每分钟的 `[资源]` 行尾部带增量
（`+refresh / +chain / +skip / +render / +tick`）。单个 `cpu=%` 分不清「事件太多」还是
「某段代码太贵」，两个数字并排才好判：一起涨是事件量放大，只有 CPU 涨是单点开销。

换歌、重播、拖动进度都不计入「进度不稳」：换歌时清零并忽略落到 0 附近的位置，回退超过 5 秒视为用户拖动。

## 性能：事件量放大（真机报告驱动的改造）

第一份真机报告（HONOR / API 37，`cpu=17~21%`、`java=85MB`）里最刺眼的是这一串：

```
[通知] +265s496 pkg=com.github.metacubex.clash.meta
[歌词] +265s498 reason=notification_other … hit=L0 lines=27
…每秒一条，持续整首歌
```

代理类应用每秒发一条通知，而**每条通知都会跑一遍完整歌词链**（读元数据 → 解析 27 行
歌词 → 重算诊断快照 → 推悬浮层，结果每次都一模一样）。也就是说责任链被当成了 1Hz 轮询。
四处改动：

| 改动 | 做法 | 效果 |
|---|---|---|
| 外来通知短路 | 非当前会话包名的通知只更新文本表；会话没换就直接返回 | 链路的触发源从「所有通知」收窄到「真正相关的通知」 |
| 事件合并 | 同一帧内的 `state`/`metadata`/`notification` 回调并成一次刷新，按「根因 > 通知 > 元数据 > 状态」保留原因 | 一次换句连发 3~5 个回调时只算一次 |
| 输入指纹 | 责任链只在「会话 + 元数据对象 + 标题/歌手/时长/媒体号 + 判定 + 通知文本」变化时重跑 | 渲染照旧（进度在推进），解析不再重复 |
| L0 解析缓存 | 按「键名 + 长度 + hashCode」记住解析结果 | 同一段歌词反复问也只解析一次 |

同时修掉两处会随时间恶化的开销：

- **`ValueAnimator` 更新监听器只增不减**：每换一句多挂一个 update 回调，放一小时能挂上千个，
  之后每帧被上千个 lambda 各调一次 `invalidate`。现在 `cancel()` 前先摘干净（顺序也有讲究：
  先摘监听器再 `cancel`，否则上一轮的 `onAnimationEnd` 会把新拍的淡入快照清掉）。
- **定时歌词不再靠别人的通知心跳**：`LyricTick` 按「下一行还有多久」排一次定时器（≤1 秒），
  自己推进当前行。之前通知安静下来歌词就停在那句，通知一多又变成每秒全量重算 —— 两头都不对。

### 0.2.4：把「稳态开销」压到接近零

上一轮掐掉了事件量放大，这一轮针对的是**稳态**：即使在放歌、在空闲、在关着调试的时候，
还有什么在偷偷花资源。

| 改动 | 之前 | 现在 |
|---|---|---|
| 元数据指纹 | 比对象身份（`identityHashCode`），播放器每次回调都新建对象 → 指纹永远「变了」 | 比**内容**（键名 + 文本 hashCode），真没变就一次解析都不跑 |
| 外来通知 | 先拆 `extras`、拼指纹，再判节流 | 先判节流，窗口内连 `extras` 都不碰 |
| 行推进 tick | 每次唤醒都重绘一遍 | 定位行号没变就直接排下一次，不碰绘制 |
| 样式读取 | 每次渲染构造一遍 `OverlayStyle`（16 个 key） | 进程内缓存，`saveStyle` 时失效 |
| 诊断快照 | 每次刷新构建（两次跨进程查询 + 一次显示器查询） | **只在调试开启时**构建 |
| 通知文本表 | 见一个包记一个，永不回收 | 上限 16 个包，超出清空重来 |
| 歌名·歌手标签 | 每次渲染拼一遍 List→map→filter→join | 随标题/歌手变化缓存 |

**调试关闭 = 零监控**（0.2.4 的硬约定）：`Probe` 关闭时不仅不写日志，还不再
采样资源、不再计数（`Perf` 连 `++` 都不做）、不再构建诊断快照、不再为快照做
`Settings.canDrawOverlays` / `Settings.Secure` 的跨进程查询；通道探测页在关闭时
直接显示「调试日志未开启」，并停掉自己每秒一次的重建。

### 0.2.5：把「跨进程调用」和「每次回调的临时对象」再砍一轮

| 改动 | 之前 | 现在 |
|---|---|---|
| 元数据 / 播放状态 | 每次刷新都 `getMetadata()` + `getPlaybackState()`：两次 binder 调用，整个 Bundle 重新反序列化（播放器把整段歌词塞进元数据时等于每次搬几 KB） | 直接用 `onMetadataChanged` / `onPlaybackStateChanged` 递到手上的对象；换会话时清缓存，自然退回主动查询 |
| 时钟锚点 | 每次刷新都用最新进度重锚 —— 读缓存后同一个进度会被反复看到，重锚会让外推恒等于原值 | 只在「进度 / 状态 / 倍速真的变了」时重锚（否则歌词会卡住不动，这是读缓存的必付代价） |
| 通知字段判等 | 每条通知建 `HashMap` + 拼指纹串，再比一次 | 读进复用的 `CharSequence` 数组，`TextUtils.equals` 逐字符比；**没变就一个对象都不分配**，变了才 `toString` + 建表 |
| `TitleTimeline` 判定 | 每次回调都 `zipWithNext` + `sorted` 算中位数（两个临时 List） | 事件集合加版本号，集合没动就返回上次结论（一次整数比较） |
| 绘制字宽 | 每帧对每个 glyph 调一次 `measureText` | 宽度在构造 `Glyph` 时算好，跟着对象走 |
| 换歌附加指纹 | 每次刷新拼 `"包名\|专辑\|音轨"` 再和缓存比 | 三个字段逐个比，没变就不拼串 |
| 布局取屏幕矩形 | `place()` 与 `placeHandle()` 各查一次 `currentWindowMetrics` + insets | 一次算好传下去 |

### 0.2.6：稳态之后再抠一遍「每帧/每秒」的小开销

| 改动 | 之前 | 现在 |
|---|---|---|
| 元数据指纹 | 每次刷新遍历整个 keySet 算哈希 | 按**对象身份**缓存：回调缓存生效后看到的是同一个不可变快照，直接返回上次的哈希 |
| 通知文本表哈希 | 每次刷新遍历 5 个 entry | 同一张表只在通知真变了时才换实例，按身份缓存 |
| 刷新任务 | 每次 `requestRefresh` 都 new 一个 lambda 丢进主线程队列 | 复用同一个 `Runnable`，只读 `pendingReason` |
| 上下文行 | 每次渲染都新建一个 List | 行号 + 策略 + 歌词表三者没变时复用上次结果 |
| 拖动 / 拖角 | 每个 MOVE 事件都查一次 `currentWindowMetrics` + insets（60 次/秒） | 按下时算一次，整段手势复用 |
| 宽高比例换算 | `applyLayoutLimits()` 里 `frame()` 被查两次 | 一次算好传给 `maxWidthPx(box)` |
| 编辑态虚线 | 每帧 new 一个 `DashPathEffect` | 建 View 时算一次；路径间隔只跟 density 有关 |
| 四角命中判定 | 每次按下 new 一个 8 项 `FloatArray` | 用角标直接算坐标，零分配 |
| 设置页重置按钮 | 每项常驻一个「重置」 | 只在偏离默认值时才出现（`INVISIBLE` 占位，不跳动） |

### 0.2.7：长时间运行的资源释放

| 隐患 | 处理 |
|---|---|
| 下载目录只增不清：每次更新都往 `cacheDir/updates/` 落一个约 260KB 的安装包，从不删除 | 开始下载新版本前清空目录（旧包的使命 —— 被安装器读一次 —— 早已结束） |

### 0.2.12：PSS 怎么看，以及为什么降不下去

`[RESOURCE]` 从一行扩成四行，把 PSS 拆开：

```text
pss=110.4MB private=44.1MB java=7.5MB/384.0MB native=31.1MB
code=33.0MB graphics=11.0MB system=22.0MB  (code/graphics/system 为共享部分按比例分摊)
```

**`pss` 不等于「本应用独占」**：它把代码段、中文字体、图形驱动这些共享页按比例摊进来，
所以任何 Android 应用都会背一份 100MB 量级的账。真正该看的是 `private`
（进程被杀后能回收的量）。

实测（HONOR PGT-AN00，0.2.11 探针）：`pss=113.2MB java=7.5MB native=31.1MB` ——
Java 堆只有 7.5MB，其余是 native（Skia 字体与渲染缓存）与共享库分摊。升级后同一条会
多出 `private=` 与 `code/graphics/system`，那才是判断依据。

已核实**没有**这些泄漏：

| 疑点 | 结论 |
|---|---|
| 网络连接 | 更新检查与在线补词都在 `finally` 里 `disconnect()` |
| 线程池 | 更新竞速 `finally shutdownNow()`；在线补词为单个 daemon 线程 |
| 位图 | 只有设置页应用图标，`LruCache(48)` 随对话框销毁即回收 |
| 窗口 surface | 取消/隐藏时 `removeViewImmediate`；按应用隐藏**保留**窗口（这是有意的，拆建会掉帧） |

**唯一有效的降 PSS 手段**：把悬浮窗调小 —— `graphics` 段与窗口面积成正比。
不要为此改软件渲染：那会把绘制推回 CPU，车机上直接掉帧，得不偿失。

## 开机自启与后台保活（v0.2.7）

设置页新增「开机与后台」卡片，两项都**默认关闭**：

- **开机自启**：`BOOT_COMPLETED`（含车机常见的 `QUICKBOOT_POWERON`）到达后，若开关
  打开则 `NotificationListenerService.requestRebind` 补一脚 —— 不少车机重启后迟迟不绑
  通知使用权，表现是「开机后歌词一直不出现，打开一次应用才好」。判定抽成
  `BootPolicy` 纯函数并配单测；receiver 必须 `exported="true"`（false 时系统广播不送达，
  这条经验来自 WindTone 车机真机）。
- **开机后台启动，让悬浮窗出现**（0.2.7.1）：服务绑回来只是第一步，没有音乐时屏上毫无
  动静，用户无从判断自启是否生效。现在刚开机的窗口期内（`elapsedRealtime ≤ 2 分钟`，
  无需状态文件）连接成功且屏上还没有悬浮窗时，画一条「AnyLyric 已启动，等待播放」；
  播放开始后正常歌词接管。
- **后台保活**：申请电池优化白名单（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`），
  个别 ROM 裁掉该 action 时退回应用详情页。开关状态以系统实际结果为准（`onResume` 刷新）；
  白名单没有可编程的撤销通道，关闭要去系统设置。
- **定期自检重绑**（默认关闭）：`JobScheduler` 每 15 分钟检查一次心跳（连接时、收到通知时、
  刷新时写，5 分钟节流）；心跳超过 20 分钟没更新就 `requestRebind`。解决「服务被 ROM 静默
  杀掉、`onListenerDisconnected` 不回调」的死角。不常驻、不持锁，开关关闭时任务直接 cancel。

服务本身仍是「系统绑定、零拉活」：两项开关只是用户主动的补强，默认行为不变。

## 按应用隐藏悬浮窗（v0.2.11）

在「一些界面不想让歌词挡着」的场景（360 影像、视频、导航、车机设置页），勾选对应应用，
它们切到前台时**歌词与左侧把手一起让位**，退出后自动恢复。

### 判定链

```
AccessibilityEvent(TYPE_WINDOW_STATE_CHANGED)
   → 过滤输入法包名（弹键盘 ≠ 切应用）
   → PkgStabilizer 450ms 滞回（挡掉车机上的包名闪烁）
   → ForegroundApps.currentPkg
   → SessionHub.applyHideState()
        ├ 本应用界面可见（Activity onStart/onStop 计数，零权限）
        └ 命中 hiddenApps 名单（需开关 + 无障碍）
   → OverlayHost.setSuppressed()
```

### 关键设计

- **不拆窗口**：隐藏走渲染器的 `setSuppressed`（`onDraw` 直接返回 + 主动重绘一次，
  surface 清成透明），恢复只重绘；与 0.2.10 的收起/展开同一条路，显隐都不掉帧。
- **两个状态独立**：`collapsed`（用户收起）与 `suppressed`（环境隐藏）各记各的 ——
  在名单应用里退出后，用户原来收着的还收着，不会被顺手展开。
- **编辑态例外**：在设置页点「调整位置」时本应用界面不算隐藏，否则用户对着空气拖。
  名单命中仍然优先。
- **零开销底线**：开关关闭或名单为空时，无障碍事件里一次早退，连包名都不解析；
  没有应用切换时服务连一个定时器都没有（延迟提交只在事件后挂一次，不轮询）。
- **本应用页面始终让位**：设置页 / 诊断页由 `BaseActivity` 的 `onStart/onStop` 计数驱动，
  **不需要任何权限**，也不受这个开关影响。

### 权限

系统设置 → 辅助功能 → 已下载的应用 → AnyLyric → 「AnyLyric 前台应用识别」。

订阅面只有 `typeWindowStateChanged`，`canRetrieveWindowContent=false` —— 服务读不到屏幕内容，
每个事件只取一个 `packageName`。设置页那行状态区分三种情况：未开启 / 已授权但当前未连接 / 已开启
（「勾了但服务被杀」在车机上是常态，不区分就会显示假的好消息）。

**自动恢复（0.2.14）**：HONOR/MagicOS 在**应用更新后会把无障碍服务关掉**，
而 Android 没有「应用自己开无障碍」的 API——唯一的自动通道是 `WRITE_SECURE_SETTINGS`
（signature 级，普通安装拿不到，`adb shell pm grant` 才行）。所以：

| 条件 | 行为 |
|---|---|
| 有 `WRITE_SECURE_SETTINGS`（adb 授予） | 开机、打开设置页时自动把服务名写回 `enabled_accessibility_services`，恢复后 toast 提示 |
| 没有该权限（绝大多数设备） | **不假装能做到**：只在设置页显示「未开启 / 已授权但未连接」（**用警示色**），点击直达系统页 |
| 用户从没开过 | 不做任何自动恢复（替没开过的人做主是越权） |

想让它真的自动恢复，一条命令即可（`WRITE_SECURE_SETTINGS` 带 `development` 标志，adb 可以授予）：

```bash
adb shell pm grant com.anylyric android.permission.WRITE_SECURE_SETTINGS
```

授予后无需 root、无需重装；升级或重启后无障碍被 ROM 关掉时会自动写回。

写回只**追加**本服务，绝不覆盖用户已有的其它无障碍服务（写坏一条会让读屏软件整段失效，
所以拼接逻辑 `appendService` 抽成纯函数并单独上单测）。

### 应用选择器

- 后台线程枚举 `ACTION_MAIN` + `CATEGORY_LAUNCHER`，避免主线程卡顿；
- 图标按 32dp 重画进 `LruCache(48)`，不会为几百个应用常驻十几 MB；
- **名单里已有但不可启动**的包（影像 / 挂件类）仍会列出，否则勾错了改不回来；
- 支持直接粘完整包名添加（排障时最省事）；
- 勾选即时生效，没有「保存」按钮。

### 实时前台应用（0.2.12）

设置页「按应用隐藏 → 实时前台应用」：显示最近切过的 20 个应用（应用名 + 包名），
当前前台高亮，**点一下就能加入/移出隐藏名单**。

存在的理由：车机上「勾了名字却不隐藏」时，必须先知道「切过去时系统报的是哪个包」。
列表为空本身就是证据 —— 一个事件都没收到，该去查无障碍，而不是查名单。

- **不落盘**：内存环形 20 条，进程结束即清。写文件既要权限，长跑还会膨胀；
- 去重：同一个包重复上报（窗口内部变化）不会在列表里刷屏；
- 名称查 `PackageManager` 并缓存，这行每秒被 `refresh` 读到但不会每次都问系统。

### 0.2.12 修掉的「勾了却不隐藏」

真机探针（HONOR PGT-AN00 / 0.2.11）给出两个硬证据，都是实现缺陷：

| 现象 | 根因 | 修法 |
|---|---|---|
| `foreground=unknown`，切过去完全不隐藏 | 监听器挂在 `SessionHub.attach()` 里，而 `attach()` 只在**通知服务建连**时调用。该机 `listenerConnected=false`（degraded），`SessionHub` 由设置页创建，`attach` 从未执行 → 前台包名变化一次都没触发重算 | 监听移到 `SessionHub` 的 `init`；`detach()` 也不再移除（监听与 SessionHub 同属进程单例，不存在泄漏） |
| 即使注册了也可能永远收不到包名 | 滞回只 `postDelayed` **一次**：Handler 走 uptime、判定走墙钟，早几毫秒 `tick()` 就不提交，候选永久卡住 | 时钟换 `elapsedRealtime`（单调）；`PkgStabilizer.hasPending()` + 提交失败再排一次，自愈 |
| `a11yConnected=true` 却一个事件没有 | XML 订阅在部分 ROM 上不生效 | `onServiceConnected` 里用代码再设一遍 `eventTypes`，并把实际值写进报告 `[HIDE] events=` |

> 判据：`events` 必须含 **32**（`TYPE_WINDOW_STATE_CHANGED`）。不含 = 订阅没生效；
> 含 32 但 `foreground` 仍是 `unknown` = 系统没派发，或用户从未切过应用。

### 0.2.15 修掉的「打开应用后一直没有歌词」

`SessionHub.attach()` **从未被任何地方调用**（grep 不到调用点），而「服务起来时主动拉一次会话」
正是写在它里面的。

更麻烦的是：degraded 轮询（通知服务没绑时的 8 秒兜底查询）**是在第一次 `refreshNow` 之后才启动的**。
于是形成死循环：

```
没有首次 refresh → 不进入 degraded → 不轮询 → 永远等不到事件 → 没有歌词
```

之前之所以「有时能用」，是因为用户碰巧进出过一次设置页：`OverlayHost.setSuppressed(false)`
在没有窗口时会调 `onRequestRender`，间接触发了一次 refresh。这不是设计，是巧合。

现在两处都补上：

- `SessionHub.init` 末尾投一次 `refresh("init")`（投到主线程下一轮，避免构造期重入）；
- `MediaWatchService.onCreate` 显式调 `attach()`，恢复它本来该有的语义。

判据：报告里 `[SESSION] sessions=0`，但设备上确实在放歌 —— 就是这条链路没跑起来。

## 设置页结构（v0.2.11）

一屏分成 10 张自带标题的卡片：状态（含两项权限与当前播放）、悬浮窗、外观、颜色、标题、
行为、开机与后台、按应用隐藏、诊断、关于与更新。宽屏（≥600dp，车机横屏）自动摆成两栏，
手机竖屏仍是单栏。开关类设置关掉后，其失效的子项整组 `GONE`（标题的位置/字号/颜色、
描边的颜色、按应用隐藏的应用选择与权限行）。

三条约束写在 `BaseActivity` 里，页面只负责摆放：

- 一屏只有一个主操作（进入编辑态），其余都是文字按钮或胶囊；
- 每个可调项都能单独恢复默认，且重置只在改过之后出现；
- 所有控件（卡片 / 步进器 / 胶囊 / 开关行 / 颜色行）只定义一次，避免同一控件两处长得不一样。

## 自测 L1 的发布端

用 WindTone 当发布端时必须先打开 **设置 → 实验室 → 车载蓝牙歌词**（`bt_car_lyric`）。
不开这一项，WindTone 的 `MediaMetadata.TITLE` 只有歌名，探测会如实报 `stable_title` ——
这不是 AnyLyric 的问题。开了之后 TITLE 会被当前歌词行接管，AnyLyric 同机直连
MediaSession 即可读到逐行流（不经 AVRCP 蓝牙栈，绕开其门控）。
